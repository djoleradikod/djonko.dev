<InShort>
Read the task's state first, because it decides the call. `PATCH /v1/tasks/{id}` retries only a failed task, `DELETE /v1/tasks/{id}` cancels only an in-progress one, and password tasks have their own pair under `/v1/credentials/tasks/{id}`. Cancelling the failed password task is the documented release for `Resource is already locked by OPERATIONS_MANAGER service` on 9.0 (<KB id={444986} />). Deleting a row from SDDC Manager's `lock` table comes later, with a snapshot, and only when a KB matches your symptom and release. Stuck 9.1 fleet and SDDC lifecycle tasks are a separate problem with their own check-and-restart script (<KB id={435569} />).
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to show `DELETE /v1/tasks/{id}` as the general way to clear failed work, but the reference allows it only for in-progress tasks. It also said KB 449148 warns that the lock returns, that release notes say to ignore a stuck status, that `lcm_service_support.sh -t` reports services, and that the script beats deleting pods. None of those holds: `-t` checks one task ID, and KB 443718 prescribes pod deletion for its own case. It called its sequence "the supported order", which is this site's synthesis, because no Broadcom page we opened publishes it.
</Callout>

## Which call fits the task

Failed work and running work take different verbs, and `DELETE` on a task that isn't in progress returns a 409. The [9.1.1 Tasks reference](https://developer.broadcom.com/xapis/sddc-manager-api/9.1.1/tasks/) and the [5.2.4 reference](https://developer.broadcom.com/xapis/vmware-cloud-foundation-api/latest/v1/tasks/id/delete/) carry the same rule <AsOf date="2026-11-07" />.

| What you see | Move | Limit |
|---|---|---|
| Generic task, failed | Fix the cause, then [`PATCH /v1/tasks/{id}`](https://developer.broadcom.com/xapis/sddc-manager-api/9.1.1/v1/tasks/id/patch/) | "Only a failed Task can be retried" |
| Generic task, in progress and really hung | [`DELETE /v1/tasks/{id}`](https://developer.broadcom.com/xapis/sddc-manager-api/9.1.1/v1/tasks/id/delete/) | "Only a IN_PROGRESS task can be cancelled" |
| Password task, failed | Offline snapshot, then [`DELETE /v1/credentials/tasks/{id}`](https://developer.broadcom.com/xapis/sddc-manager-api/9.1.1/v1/credentials/tasks/id/delete/) (<KB id={444986} />, 9.0). Or fix the cause and [`PATCH`](https://developer.broadcom.com/xapis/sddc-manager-api/9.1.1/v1/credentials/tasks/id/patch/) the same path | The [9.0 Tasks page](https://developer.broadcom.com/xapis/sddc-manager-api/9.0/tasks/) rules out `/v1/tasks` for retrying these |
| All tasks show complete, locks remain | No task to cancel, so use a lock-row KB (<KB id={439473} />) | 5.x and 9.0.x |
| Backup stuck and can't be cancelled | Lock-row KB (<KB id={422426} />, <KB id={447314} />) | A restart or reboot may not clear it |

```bash
# Get a token from your SDDC Manager (see the API reference for your release)
API_HOST=<sddc-manager-fqdn>
TOKEN=...
# If curl can't verify the certificate, add --cacert <your-ca.pem>

# Failed generic task, after fixing its cause
curl -s -X PATCH -H "Authorization: Bearer $TOKEN" https://$API_HOST/v1/tasks/<task-id>

# In-progress generic task that will not complete
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" https://$API_HOST/v1/tasks/<task-id>

# Failed password task holding a lock
curl -s -X DELETE -H "Authorization: Bearer $TOKEN" https://$API_HOST/v1/credentials/tasks/<task-id>
```

A failed generic task with an unfixable cause has no cancel call, since `DELETE` refuses it. That case needs a KB that matches, or Support. The credential retry is documented with a `CredentialsUpdateSpec` body, so read [its page](https://developer.broadcom.com/xapis/sddc-manager-api/9.1.1/v1/credentials/tasks/id/patch/) before scripting it.

## Find the owner before you pick

SDDC Manager serialises changes with resource locks, and a workflow that dies without finishing can leave its lock behind. Later changes to that domain, host or credential then fail with `Resource is already locked by OPERATIONS_MANAGER service` or `Error in acquiring resource locks`.

The log line usually names the holder: service and task ID, as in <KB id={444986} /> and <KB id={449148} />. Look that ID up in the UI or with `GET /v1/tasks/{id}` or `GET /v1/credentials/tasks/{id}`. On 5.x and 9.0.x, `sos --health-check` fails on active locks even when the UI shows every task complete (<KB id={439473} />), so a clean-looking Tasks panel doesn't clear the system. `select * from lock;` on the `platform` database is a read-only check, the one <KB id={449148} /> uses.

If something is really running, wait. On 9.1.1, VCF Operations for networks installed in parallel with Real-time metrics and Log Management can look stuck for over three hours before it fails, so wait out the workflow's three-hour timeout before retrying. Concurrent certificate replacements can stall any other task running beside them, so run them one at a time ([9.1.1 notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html)).

## Same error, two published routes

`Resource is already locked by OPERATIONS_MANAGER service` has two different answers. <KB id={444986} /> (VCF 9.0, June 2026) cancels the failed credential task through the API, which releases the lock. <KB id={449148} /> (VCF 9.x, July 2026) has a password-rotation task holding the domain lock during a vCenter 9.1 switchover, and deletes the lock row. Neither mentions the other. The [5.1 Operations guide](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-5-2-and-earlier/5-1/vmware-cloud-foundation-operations-5-1/vcf-best-practices-operations/password-operations-operations.html) describes the same mechanism with UI buttons: Cancel releases the lock, or resolve the issue and Retry. The [9.1 rotate page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords/rotate-passwords.html) names Retry and no Cancel, so plan on the API.

<Callout type="analysis" title="Cancel first, then the row">
Try the credential cancel before the database, on any 9.x release, because it goes through a documented API and closes out the task that owns the lock. The row delete in KB 449148 touches neither that task nor the NSX credential it couldn't validate. Broadcom doesn't say the lock returns. The risk is an inference from the rotate page: an auto-rotate that couldn't start retries hourly until the start of the next day, so an account left broken may fail again.
</Callout>

## Fix what made it fail

The KBs here show two causes: an NSX service account the rotation can't validate, and a backup that never ended. For the account, <KB id={449148} /> shows `PASSWORD_MANAGER_RETRIEVE_PASSWORD_EXPIRY_FAILED` with "The credentials were incorrect or the account specified has been locked". Broadcom's [Fleet Management Blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) tells you not to change inter-component account passwords or permissions directly on VCF components, since manual edits can break integrations.

Check the target before believing a failed password task on 9.1.1. An update can be marked failed although the password changed, when an integration credential has no owner. A timeout on `vmware-system-user` can report a false `INVALID_CREDENTIALS` ([9.1.1 notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html)).

Clear failures before the next rotation either way. Both the [9.1 update page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/update-passwords.html) and the rotate page list no failed workflows and no active workflows as prerequisites. On 9.1, the update page sends you to Tasks under Fleet Management in VCF Operations to check.

## The lock-row KBs differ more than they look

Each KB fits one symptom and removes something different, so copying a delete from the wrong one can take out more than you meant to.

| KB (updated, 2026) | Release stated | Symptom | Removes | Afterwards |
|---|---|---|---|---|
| <KB id={449148} /> (31 Jul) | 9.x | vCenter switchover blocked by a rotation task | One row, by ID from the logs | Domain operations should proceed |
| <KB id={407073} /> (7 Oct) | 9.x | Domain inventory sync blocked | The `EXCLUSIVE` row | Restart services, retry |
| <KB id={439473} /> (13 Aug) | 5.x, 9.0.x | Health check fails, tasks look complete | Stale rows, by ID | Restart services, rerun check |
| <KB id={446776} /> (8 Jul) | 9.x | SDDC Manager 9.1.x upgrade goes `CANCELLED` at once | **Every row**, `truncate lock` | Restart `lcm`, retry |
| <KB id={422426} /> (27 Oct) | None | Backup stuck, tasks "Fetching" forever | The `deployment` row | None listed |
| <KB id={447314} /> (8 Jul) | 5.x | Hung backup blocks password remediation | `deployment` row, backup `task_metadata`, and if needed failed password operations | Restart services |

All of them want a snapshot first, in different words: powered-off (439473), non-memory (447314) or plain. A powered-off snapshot satisfies every wording, so take that one. `truncate lock` clears every lock at once, so confirm from the Tasks panel that nothing legitimate is running first, which is this site's advice and not in the KB.

"Fetching task info" has two separate fixes. If it never resolves, a backup is stuck and SOS collection fails on a deployment lock, the row delete in <KB id={422426} /> is the fix, and a restart may not clear it. If it appears for several minutes before tasks load and the UI is slow, <KB id={429753} /> (5.x and 9.x) attaches `sddc_task_fixer.py` for cleaning up stale tasks. Run it only as that KB describes.

One lock lives outside this table. The [SDDC Manager 9.1.1 notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/sddc-manager-9-1-1-0-release-notes.html) describe a background update check holding the package manager lock for about 48 minutes while an upgrade times out after 25. The workaround stops that job, and no database edit is involved.

## What goes to Support

<KB id={424242} /> (stale host records) and <KB id={441253} /> (9.1.x) both route database changes through Broadcom Support. The second matters here because its log shows `Error in acquiring resource locks`, yet the stated cause is an NSX or vCenter record wrongly set to `ERROR`, with `Resources [...] are not available/ready` on screen. Deleting a lock row doesn't address that. Treat any other edit to SDDC Manager's database the same way: if no KB describes it for your symptom, open a case, since a wrong edit to the platform database can be harder to recover from than the stuck task.

## 9.1: fleet and SDDC lifecycle tasks

These aren't lock rows. `fleetbuild`, `fleetupgrade`, `sddcbuild` and `sddcupgrade` run on the VCF services runtime, and a parent task can sit for hours without timing out. <KB id={435569} /> (9.1, September 2026) blames transient connectivity during monitoring: the installer's retry often finishes the job, while the UI may not update the original sub-task.

So log in to the deployed component first. If it's healthy, the task may be a display fault, though the KB stops short of telling you to ignore it. From SDDC Manager, the KB's attached script then takes the runtime FQDN and answers for one task:

```bash
./lcm_service_support.sh -u <admin_user> -s <runtime-fqdn> -t <task_id>
./lcm_service_support.sh -u <admin_user> -s <runtime-fqdn> -r fleetbuild
```

`-t` prints either that the task is normal or that it isn't making progress, and names the service to restart with `-r`: `fleetbuild`, `fleetupgrade`, `sddcbuild` or `sddcupgrade`. For an SDDC lifecycle service, use the runtime in the same VCF instance as the stuck task. An upgrade stalled at "Perform Component Upgrade" has an earlier step in the same KB: match the long-running Kubernetes workflow to your upgrade window, read its logs, delete it.

Pod deletion is documented, for named cases. <KB id={443718} /> covers a log management upgrade from 9.0.2 to 9.1 stuck at "Install VCF services runtime" on VCF Operations 9.1.0, where the upgrade finished in the background and the status was lost. It deletes the fleet and SDDC build and upgrade pods. <KB id={452176} /> (VCF Operations upgrade or patch stuck in progress) edits a `.results` file and falls back to the same pods after 10 minutes. Start with the script and go to pods only when one of these matches.

Dismissing a status takes a named case and a check. The [9.1.1 notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) allow it for specific cases, each after a check: a failed scale task once the component shows its target size, and an SDDC lifecycle restore reported as failed once the target is active.

On a VCF 9.0 deployment, `Another operation: <ID> is already in progress for the environment : lcm` is a stale operation on the Fleet Manager appliance, and a guest reboot clears it before you restart from the failed stage (<KB id={433018} />, which lists 9.x). The [9.1 lifecycle page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management.html) says the fleet and SDDC lifecycle components replace that appliance, so expect this fix only where the appliance still exists.

<Callout type="field">
Hand over a stuck-task ticket with four things: the task ID, the lock owner, the cause you fixed, and what you removed. The next engineer can then tell at once whether the same symptom is the same problem.
</Callout>
