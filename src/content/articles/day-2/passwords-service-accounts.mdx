<InShort>
**Use Update in VCF Operations for any deliberate change, and Rotate from SDDC Manager, the only console that has it.** Remediate is for a password someone has already changed. On 9.1 it runs from SDDC Manager for ESX, vCenter and NSX, and from Fleet Management > Passwords for VCF Operations and its management components. 9.1.1 moves SDDC Manager's `root`, `vcf` and `admin@local` into VCF Operations and lets Update run against a locked or expired account. External PAM tools stay off service accounts.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to say expired passwords are remediated in VCF Operations on all of 9.x, and it credited KB 454943 with the 9.1.1 SDDC Manager change. Remediate now splits by account as shown below, and the 9.1.1 change comes from the accounts page and release notes, because KB 454943 covers interfaces by deployment and entitlement.
</Callout>

## Which console for which job

| Job on 9.1 or 9.1.1 | Console | Action | Limit worth knowing |
|---|---|---|---|
| Change a password on purpose | VCF Operations, Manage > Fleet Management > Passwords | [Update password](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/update-passwords.html) | Validates against the assigned policy. Clear failed workflows and running ones first |
| Get a random password now | SDDC Manager, Security > Password Management | [Rotate or Rotate all](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords/rotate-passwords.html) | ESX, vCenter and NSX only |
| Rotate on a schedule | SDDC Manager | Schedule rotation: 30, 60 or 90 days, or custom by API | Not ESX. Runs at midnight and retries hourly until the next day |
| Record a password already changed on ESX, vCenter or NSX | SDDC Manager | [Remediate](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords/remediate-passwords.html) | One account at a time. Enter the value that works today |
| Record it on VCF Operations, Operations for networks or Automation | VCF Operations, Fleet Management > Passwords | Remediate (<KB id={446310} />) | Filter the grid to disconnected accounts |
| Bring a component's settings back to its policy | VCF Operations, Fleet Management > Passwords | Compliance check, then Remediate (<KB id={447254} />) | Checks run every 6 hours. No password is recorded |
| Replace the VCF Operations service account in vCenter | VCF Operations, Administration > Integrations | Rotate beside System managed credentials | Deletes the account and creates a new one |

## Settling Remediate and Rotate

Two jobs share the word Remediate. [Password remediation](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords.html) gives the client the password that already changed on the server. [Policy remediation](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords.html) pushes length, expiry and lockout settings onto a component that has drifted from its policy. A sentence about one is easily read as being about the other, so check which job a page means.

Rotate is settled. The [9.1 accounts table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) (5 Nov 2026) lists only Update under VCF Operations for ESX, vCenter and NSX, and Update, Rotate, Remediate, look-up and scheduled rotation under SDDC Manager. <KB id={426872} /> reports the missing Rotate button on 9.0.x too.

Remediate is where Broadcom's pages conflict. That same table, and the SDDC Manager page's "Only available in SDDC Manager", put it on SDDC Manager. The [Remediate procedure](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords/remediate-passwords.html) says you "must remediate the password in VCF Operations", then starts its steps with "Log in to SDDC Manager". Against the table, <KB id={436398} /> walks through a Remediate Password button for ESX root in VCF Operations, scoped to 9.0. <KB id={446310} /> and <KB id={428611} /> do the same for management components on 9.x, and William Lam's [June 9.1 tip](https://williamlam.com/2026/06/vcf-9-1-quick-tip-forgot-to-retrieve-auto-generated-passwords-from-vcf-installer.html) remediates through Fleet Management too.

<Callout type="analysis" title="The call for a 9.1 runbook">
Write SDDC Manager for ESX, vCenter and NSX. It's the only console the dated table gives them, and its vault holds the stale value. Write VCF Operations for its management components, whose table rows list no SDDC Manager action. Broadcom doesn't state this split, so try one account of each kind outside production. If VCF Operations offers Remediate on a core account, it's reasonable to use it, but keep SDDC Manager as the fallback: <KB id={449686} /> shows the VCF Operations attempt failing and the repair finishing there.
</Callout>

Update behaves differently across the 9.0 and 9.1 boundary. VCF Operations 9.1 [keeps no password vault](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords.html), so a change at the source doesn't stop it updating that password. On 9.0.x, <KB id={422045} /> has Update failing with `LCMVMSP10019` after an out-of-band change, because it authenticates with the old stored value. On 9.1, entering the working value as the current password should therefore let Update succeed after drift, though that's an inference from the two pages and Broadcom doesn't document it as a repair. Update also sets a new password, while Remediate only records the existing one, so choose Remediate when the current value has to stay.

The [runbook diff for 9.1](/vcf/library/day-2/runbook-diff-91/) moves routine rotation lines to VCF Operations. The button there reads Update and you supply the password, so keep Rotate in a runbook only where SDDC Manager should generate the value. The upgrade-window gaps for management components are in that diff too. SDDC Manager ["will be deprecated in a future VCF release"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords.html) <AsOf date="2026-11-07" />, so new automation shouldn't depend on its Rotate.

## What 9.1.1 changed

The [accounts table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) splits SDDC Manager's local passwords by release, and the [9.1.1.0 notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) confirm it, adding the vCenter SSO account:

| SDDC Manager account | Default expiry | On 9.1 | On 9.1.1 |
|---|---|---|---|
| `root` | 365 days | By hand in the OS | VCF Operations UI or API |
| `vcf` | 365 days | By hand in the OS | VCF Operations UI or API |
| `admin@local` | Never | SDDC Manager API | VCF Operations UI or API |
| `backup` | 365 days | VCF Operations UI or API | VCF Operations UI or API |

The [SDDC Manager accounts page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords/updating-sddc-manager-passwords.html) still gives the 9.1 routes with no version split, including `PATCH /v1/users/local/admin`. Treat those as the 9.1 path. <KB id={454943} /> (4 Sep 2026) answers a different question: Fleet Management's UI needs VCF Management Services and a VCF entitlement. VVF with those services gets the Component API, and without them each product's own interface.

[Lockout handling](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/password-policies-in-vmware-cloud-foundation.html) changes as well. A locked or expired account now accepts Update from VCF Operations and raises an alert. Update doesn't unlock it, though, so the account waits out its lockout duration, 900 seconds by default, even after a successful task. Don't read a failed login in that window as a failed update.

## Policy: who changes what

VCF has three account types. Local accounts are OS logins, application accounts are interactive UI and API logins, and service accounts are system-managed credentials between components. Rotate only what the [accounts table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) gives you.

Leave service accounts to the platform. The [accounts table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) marks nine as rotated automatically every 30 days by default, and four of those also carry a 90-day default expiry, so a rotation that keeps failing leaves those four about 60 days before they expire. ESX service accounts are the exception: [auto-rotate isn't supported for ESX](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords/rotate-passwords.html). A newly deployed vCenter can take [up to 24 hours](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords/rotate-passwords.html) to get its auto-rotate policy. Rotation is also what strands stale runtime secrets, as the table below shows.

PAM tools get human accounts only. Internal service accounts ["must not be rotated, changed, or managed"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) by external PAM, so that's the answer to a security team asking to onboard everything. Offer them the [enterprise vault](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) Broadcom recommends for credentials used through API or manual processes, plus VCF Operations expiry alerts and audit records.

A policy can expire passwords the moment it lands. With an N-day expiry, [any password last updated N+1 or more days ago expires on apply](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords.html), so read last-update dates first and update stale ones. Complexity settings [don't apply to existing passwords](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html), so change those immediately afterwards. Non-expiring accounts are exempt from expiry and lockout unless you enforce it through the API on 9.1.1. Changing the expiry on ESXi hosts carries the same trap: in <KB id={408659} /> (VCF 5.x), lowering 180 days to 90 on passwords older than 90 days disconnected the root and service accounts.

Make "change it through VCF, or remediate straight afterwards" a written rule for every team with root access, since an out-of-band change is what starts drift. Before an upgrade, rotate in a separate change and confirm no failed task remains, because a failed task can leave a lock behind.

On 5.2, rotation and remediation ran from the SDDC Manager UI, with the vSphere Client as an option from 5.2.1 and a [rotate-every-80-days instruction](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-5-2-and-earlier/5-2/map-for-administering-vcf-5-2/manage-passwords-admin.html) in the 5.2 guide.

## Breaking a lockout loop

Unlocking first fails, because the service still holding the old value locks the account again. <KB id={449684} /> sets the order. Snapshot SDDC Manager, add its IP to the lockout-immune list, and rotate the NSX service account from SDDC Manager's UI. Retrieve the stored value (<KB id={327195} />) and retrieve it again after 5 to 10 minutes to verify the service account has stayed connected. A secret that differs between reads is one of the KB's symptoms, so expect the same value. That's an inference, since the steps don't state the comparison. Only then rotate root, admin and audit, and remove the exception. Leaving the IP immune removes NSX's protection against that address, so treat the exception as temporary.

## Locks

A failed password task holds a lock at VCF instance level, which blocks later tasks. Take an offline snapshot of SDDC Manager, then cancel with `DELETE /v1/credentials/tasks/{id}` (<KB id={444986} />). To retry, the [credentials API](https://developer.broadcom.com/xapis/vmware-cloud-foundation-api/latest/credentials/) documents `PATCH /v1/credentials/tasks/{id}` on the same list of resources, and it doesn't cover retrying through `/v1/tasks`, so stay on the credential path. Deleting a lock row from the database belongs only inside a KB procedure such as KB 449686. [Stuck tasks and locks](/vcf/library/day-2/stuck-tasks-locks/) covers the wider mechanism.

## One KB to read with care

<KB id={435599} /> (13 Apr 2026, "VCF 9.x") calls SDDC Manager "the authoritative source for account lifecycles", says "Never Expire" isn't supported, and lists ESXi root under rotation intervals. The 9.1 pages dated 5 Nov 2026 prefer VCF Operations, give ESX root a default expiry of Never, and say auto-rotate isn't supported for ESX. On 9.1, follow the dated pages, as the [runbook diff](/vcf/library/day-2/runbook-diff-91/) does. The KB's useful point remains that Fleet Management, VCF Operations, its logs and networks products and VIDB sit outside automated rotation, so their expiry dates need someone watching the alerts.
