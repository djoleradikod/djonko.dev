<InShort>
`/opt/vmware/sddc-support/sos` on SDDC Manager is still where health checks and log bundles start. `sos --health-check` is the fastest way to see **stale locks** and **disconnected accounts** before they block a change (<KB id={439473} />, <KB id={436398} />). What changed in 9.x is everything around it. VCF Operations shows fleet and component health, 9.1 adds a **management services** dashboard with volume and pod health (<KB id={417255} />), and bundles for VCF Operations, VCF Automation and the runtime come from their own consoles or from fleet lifecycle, not only from SoS.
</InShort>

## The health check before every change

Run it before an upgrade, a password rotation, a host commission or a certificate replacement. It takes minutes and it answers the two questions that most often stop a workflow halfway: is something already holding a lock, and are the stored credentials still valid?

```bash
# On SDDC Manager, as root
/opt/vmware/sddc-support/sos --health-check

# Narrow the scope when the full run is slow
/opt/vmware/sddc-support/sos --health-check --domain-name MANAGEMENT
```

Read the output for three things:

- **Active locks** owned by `OPERATIONS_MANAGER` or `LCM`. If no task is running, a lock is stale. See [stuck tasks and locks](/vcf/library/day-2/stuck-tasks-locks/).
- **"Failed to get details"** against an account. That usually means the stored password no longer matches the component, often after an out-of-band change (<KB id={436398} />).
- **Red items you can explain.** Some checks have known false positives in specific releases, so read the release notes before chasing a red line that only appeared after an upgrade.

## Log bundles, by situation

| Situation | What to collect |
|---|---|
| SDDC Manager workflow failed | `sos --sddc-manager-logs --zip` |
| Failure spans hosts, vCenter or NSX | `sos --collect-all-logs --zip --domain-name <name>` |
| 9.1 runtime, fleet lifecycle or depot | Add `--vcf-mgmt-svcs-logs`. If it fails with `access_denied`, restart `commonsvcs` and retry (<KB id={451560} />). |
| Runtime unhealthy, fleet lifecycle down | The standalone runtime bundle script (<KB id={444466} />) |
| VCF Operations | Its Control Panel: Support Bundles, Light or Full (<KB id={443789} />) |
| VCF Automation, identity broker | Fleet lifecycle: component > Logs > Generate (<KB id={433768} />) |
| Deployment from the installer | The installer UI support bundle in 9.1, or `--vcf-installer-logs` (<KB id={402476} />) |

Use `--log-dir <path>` when the default location is short on space, and check `/var/log/vmware/vcf/sddc-support/` for the output.

<Callout type="field">
Attach the health check output to the change record. It costs nothing, it proves the platform was clean before you started, and it is the first thing a support engineer asks for if the change goes wrong.
</Callout>

## Pitfalls

- **Collecting everything, every time.** A full bundle across every domain can take an hour and fill a partition. Start narrow and add scope when the logs point somewhere else.
- **Cleaning before collecting.** If a disk is full mid-incident, collect a bundle first, then clean. The rotated logs are often the evidence.
- **Waiting for support to ask.** Collect the bundle when you open the case, with the exact time of the failure, so the first reply can be analysis rather than a request.
