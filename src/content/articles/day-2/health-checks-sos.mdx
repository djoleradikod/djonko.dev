<InShort>
A green `sos --health-check` covers less than it appears to. On 9.1 it [leaves out VCF management services, VCF Automation and VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html), and SoS operations default to the management domain. Before a change, run it with `--domain-name ALL` and read the Health and Diagnostics dashboard in VCF Operations as well. For a support case, use Log Assist for the components it covers while VCF Operations is up, and the table below otherwise.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to say `--domain-name MANAGEMENT` narrows a slow run, but MANAGEMENT is already the SoS default. </Callout>

Anything that scripts SoS against the older flags needs a re-test on 9.1. TechDocs points to `sos --help` for what a given appliance supports <AsOf date="2026-11-07" />.

## The health check before a change

Locks and disconnected accounts are findings that can stop a workflow halfway. On VCF 5.x and 9.0.x a stale lock [fails backup and password rotation tasks and takes host commissioning and backup target editing out of the UI](https://knowledge.broadcom.com/external/article/439473), so run the check before any of those, before an upgrade and before a certificate replacement.

```bash
# On SDDC Manager: SSH as vcf, then su to root
/opt/vmware/sddc-support/sos --health-check --domain-name ALL

# The same, showing failures and warnings only
/opt/vmware/sddc-support/sos --health-check --domain-name ALL --short
```

`--domain-name` [defaults to MANAGEMENT and takes ALL](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html). The page states that for SoS operations in general and doesn't spell it out for `--health-check`, so a plain run reading as management-only is an inference: confirm it on your appliance before trusting a clean result for a workload domain change.

After deployment, run health checks from SDDC Manager. The Installer carries a subset of the options, and `--dns-health`, `--password-health`, `--storage-health` and `--version-health` (bill of materials drift) are SDDC Manager only. Their narrow scope suits a re-test after a fix, which is inference rather than TechDocs advice. `--force` runs SoS while workflows are in progress, and TechDocs says to use it with caution. Health checks are among the [workflows that can leave a lock behind](https://knowledge.broadcom.com/external/article/439473) if they time out, so a quiet window is the safer call. That advice is inference from the KB's cause.

Two results have a documented fix:

- **An error naming active locks for `OPERATIONS_MANAGER`** when the UI shows earlier tasks finished. The cause is a stale record in the `lock` table of the `platform` database, and the fix is a database edit after a powered-off snapshot of SDDC Manager. <KB id={439473} /> is scoped to VCF 5.x and 9.0.x, so on 9.1 start from [stuck tasks and locks](/vcf/library/day-2/stuck-tasks-locks/).
- **`Failed to get details` in the State column for an ESXi root account**, while root login still works. The stored password no longer matches, which may follow a change made outside SDDC Manager or VCF Operations. On SDDC Manager 9.0 the fix is Remediate Password in VCF Operations, using the password that works today (<KB id={436398} />). On 9.1 read [passwords and service accounts](/vcf/library/day-2/passwords-service-accounts/) first.

## The management services dashboard

Use the [VCF Management Services: Health and Diagnostics](https://knowledge.broadcom.com/external/article/417255) dashboard for the management services, which the health check leaves out. The KB names no release, but its paths run through Build > Lifecycle, [where Lifecycle sits on 9.1.0](https://knowledge.broadcom.com/external/article/433768), so read it as 9.1 guidance. Most of what the KB adds is how long to wait before acting on a red item:

| Dashboard signal | When to act | What to do |
|---|---|---|
| Component unhealthy (any replica down) | Status refreshes every 15 minutes, so watch for 30 minutes | Check maintenance, alerts and stability, try a lifecycle restart, then collect logs and open a case |
| Kernel deadlock or Kubelet not ready | Replacement starts after 3 minutes and takes up to 1.5 hours | Wait for the node to be replaced |
| Disk pressure on a node | After 15 minutes or more | Check VM network and storage latency and APD or PDL alerts, then reduce load or add instances |
| Memory pressure | Sustained over an hour | One node: reduce its load. Several nodes: scale up |
| Component volume near capacity | The KB gives no percentage | Resize through the lifecycle component action |
| Backup failures | On failure | Check SFTP reachability, free space and the password in Backup and Restore |

On 9.1.0, watch the logging disk as well. VCF Operations 9.1.1.0 lists as resolved a services runtime issue where a [full logging disk fails platform health checks and blocks platform operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html). When the dashboard isn't enough, the next step is the read-only commands in [services runtime and kubectl](/vcf/library/troubleshooting/services-runtime-kubectl/).

## Log bundles, by what failed

[Log Assist can send bundles to Broadcom support from the VCF Operations console](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs) (FAQ, 4 Nov 2026), and 9.1 [adds automatic bundle generation](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/what-s-new/whats-new-vcf-ops.html) for the VCF Operations cluster, VCF management services, cloud proxies, log management and the identity broker. That makes Log Assist look like the shorter path for those components while VCF Operations is up, though neither page says so. For everything else, and when it's down:

| What failed | What to collect |
|---|---|
| SDDC Manager workflow | `sos --sddc-manager-logs --zip` (<KB id={385749} />) |
| Hosts, vCenter or NSX | `sos --collect-all-logs --zip --domain-name <name>`, or `ALL`. On SDDC Manager this [excludes WCP and system debug logs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html), so add `--wcp-logs` for a WCP problem |
| 9.1 management services, including the runtime, fleet lifecycle or depot | `sos --sddc-manager-logs --vcf-mgmt-svcs-logs --zip` (<KB id={385749} />) |
| Same, ending in `access_denied` | A bundle still appears, with the subtask FAILED in `report.json`. Run `systemctl restart commonsvcs` on SDDC Manager and collect again, because `svc-sddc-manager-admin` is out of sync (<KB id={451560} />) |
| Fleet lifecycle UI or API unavailable | The script in <KB id={444466} />. Its lookback defaults to 2 days, so extend it for an older fault |
| VCF Operations | Operate tab (9.1), Administration > Control Panel > Support Bundles > Add, Light or Full (<KB id={443789} />). SoS `--operations-logs` needs `--setup-json` on SDDC Manager and omits cloud proxy logs |
| VCF Automation | `sos --automation-logs` ([TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html)) |
| Identity broker | Fleet Management > Lifecycle (Build > Lifecycle on 9.1.0) > VCF Management > Components > Identity Broker > More Actions > Logs > Generate Logs (<KB id={433768} />) |
| Deployment, on the Installer | 9.1: Support-bundle in the Installer's top-right menu, or `sos --vcf-installer-logs --vcf-mgmt-svcs-logs --zip` (<KB id={402476} />). [SoS collects only from the latest deployment](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html) |

Output lands in [`/var/log/vmware/vcf/sddc-support/`](https://knowledge.broadcom.com/external/article/385749) unless `--log-dir` points elsewhere, which you'll want when that location is short on space. Check two defaults before a second run: SoS [removes existing log folders unless you pass `--no-clean-old-logs`](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html), so copy the first bundle off or pass that flag, and collection runs a health check unless you pass `--no-health-check`.

<Callout type="analysis" title="Where SoS fits in an incident">
["The SoS Utility is not a debug tool"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html), and the method in Broadcom's [Troubleshooting Blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/troubleshooting-guide/troubleshooting-methods.html) (5 Nov 2026) runs through VCF Operations instead: narrow to the exact period, check events for a change, and use the Workbench "Potential Evidence" tab rather than scanning logs by hand. So diagnose in VCF Operations and treat a bundle as the evidence you hand to support. Collect it when you open the case and give the failure time, starting narrow and adding scope when the logs point somewhere else. If a disk fills mid-incident, collect to another `--log-dir` before cleaning, since what you'd delete may be the evidence. For a change record, `--json-output-dir` writes the health check results to a file, and that file says nothing about the components the check excludes, so record the dashboard state beside it.
</Callout>
