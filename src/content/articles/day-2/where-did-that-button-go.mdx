<InShort>
Write each runbook against the release you run, because many 9.0 paths changed again in 9.1. Tasks on hosts, clusters, network pools and edges [moved to vCenter](https://blogs.vmware.com/cloud-foundation/2025/09/18/10-vmware-cloud-foundation-9-enhancements-simplifying-your-day-2-operations/), and platform tasks moved to VCF Operations: domains, certificates, passwords, backup, DNS and NTP, licensing and lifecycle. Don't start a new runbook in SDDC Manager, whose UI has been [deprecated since 9.0](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes.html), unless it needs rotation or Remediate on a core account. Keep the appliance healthy, because on 9.1 it [still provides](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/vcf-management-appliances.html) core lifecycle and workload domain deployment behind VCF Operations.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to say the SDDC Manager UI was "still present" in 9.0 and deprecated in 9.1, when the deprecation starts in 9.0. It also gave one 9.x path for tasks whose paths differ between 9.0 and 9.1, and offered a tip about a greyed-out Add Host button that this site couldn't find in any public source, so that tip is gone.
</Callout>

## What the vCenter paths need first

Settle access before retraining anyone. On 9.1 the vSphere Client tasks for [pools](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/host-management/about-network-pools/create-a-network-pool.html), [commissioning](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/host-management/commission-hosts.html), [clusters](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/working-with-workload-domains/expand-a-workload-domain/add-a-cluster-to-a-workload-domain-using-the-sddc-manager-ui.html) and [adding hosts](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/working-with-workload-domains/expand-a-workload-domain/add-a-host-to-a-vsphere-cluster-using-the-sddc-manager-ui.html) each require access to the management domain vCenter, or an instance configured with VCF SSO and vCenter linking. [Hahn](https://blogs.vmware.com/cloud-foundation/2025/09/18/10-vmware-cloud-foundation-9-enhancements-simplifying-your-day-2-operations/) draws the 9.0 line the same way: the management domain needs no extra setup, while workload domains need SSO and linking.

Those four pages also name the SDDC Manager UI as an alternative, which can help while SSO and linking aren't ready. Treat it as a stopgap and leave it out of a new runbook, given the deprecation. Creating a workload domain has no such fallback on [its 9.1 page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/working-with-workload-domains/deploy-a-vi-workload-domain-using-the-sddc-manager-ui.html), which describes only VCF Operations. [Hosts, network pools and clusters](/vcf/library/day-2/hosts-network-pools-clusters/) has the task detail, and [What SDDC Manager still owns](/vcf/library/architecture/what-moved-from-sddc-manager/) covers the appliance.

## Where the simple split breaks

The object-versus-platform rule doesn't send ESX or vCenter certificates to vCenter. The 9.1 fleet management blueprint says to manage certificates [exclusively through VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html), to avoid SDDC Manager for them, and to stay off the vCenter API, UI and CLI for ESX and vCenter certificates once VCF Operations manages them. Q55 of the [4 Nov 2026 FAQ](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs) also describes certificate management as centralised under VCF Operations.

Backup is no longer one screen. On 9.1 the [blueprint's table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-backup-and-restore.html) splits it by component: management services, VCF Automation and NSX Manager are file-based over SFTP, and VCF Operations is image-based, with all cluster nodes backed up at once. SDDC Manager allows either method, and the design recommends file-based. The license server has no backup, so recovery means deploying a new one and reconfiguring licensing. So the single 5.2 procedure becomes at least three on 9.1, plus a recovery line for the license server.

DNS and NTP became fleet settings. They sat under each instance's settings on 9.0, while on 9.1 you build a named setting and assign it, so check which setting an instance uses before changing it.

Upgrade documentation points two ways. The [9.1 workload domain upgrade chapter](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management/upgrade-workload-domains-to-vcf-5-2.html) says either VCF Operations or the SDDC Manager UI works for 5.2 domains and writes its own steps for the UI, while warning that the UI "is being deprecated and will be removed in a future release". The [planning page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-the-management-domain-to-vmware-cloud-foundation-5-2/plan-an-upgrade.html) it links uses VCF Operations. Write the VCF Operations path into the runbook.

## Passwords keep a foot in SDDC Manager

[Update in VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/update-passwords.html) is the preferred way to change a password, and it doesn't create configuration drift. A change made outside both consoles does, and that drift can later break upgrades. [Rotate, Remediate for core components and scheduled rotation](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords.html) still need the SDDC Manager UI on 9.1, on a page that also says using SDDC Manager for passwords "is not advised". The [password blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) nonetheless recommends enabling SDDC Manager auto-rotation for inter-component accounts only it can manage, and rules out changing those accounts directly on components.

<Callout type="analysis" title="Reading the password guidance together">
These fit if SDDC Manager is kept for what only it can do, though Broadcom doesn't spell out that split. So use Update in VCF Operations for deliberate changes and keep scheduled rotation on in SDDC Manager for those inter-component accounts. The [Update page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/update-passwords.html) requires that no workflows are running or scheduled during an update, so check the rotation schedule first. Where Remediate runs for each account is in [the passwords note](/vcf/library/day-2/passwords-service-accounts/), because Broadcom's pages conflict on it.
</Callout>

<KB id={435599} /> (VCF 9.x, last modified 13 Apr 2026) still calls SDDC Manager's password subsystem the authoritative source for account lifecycles. The [9.1 passwords page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords.html), dated 5 Nov 2026, prefers VCF Operations, so on 9.1 follow the newer page.

SDDC Manager's own accounts changed in a point release. On 9.1 you change `root` and `vcf` in the OS and `admin@local` through the SDDC Manager API, and [from 9.1.1](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) all three move to the VCF Operations UI or API. In 9.1.1 an update [doesn't change an account's lockout state](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html), so plan the unlock separately. If you take 9.1.1, change the runbook for those three accounts in the same window.

## Rolling this out

1. **Pick the column you run** and print it without the others, so nobody follows a 9.0 path on 9.1. KBs written for one release may use the other release's paths. Jonathan McDonald's [December 2025 upgrade FAQ](https://blogs.vmware.com/cloud-foundation/2025/12/18/upgrading-vmware-cloud-foundation-5-2-to-9-0-the-top-10-questions-answered/) is a good companion for teams still on 5.2, and it places the SDDC Manager interface under fleet management in the VCF Operations console.
2. **Re-record the procedures** the team runs most: host commissioning, cluster expansion, certificate renewal and password rotation. Use a lab or a quiet production window.
3. **Sort scripts against the deprecations.** Scripts that drive Day-2 tasks through the SDDC Manager API may still work in places. The [9.1 notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/vcf-91-product-support-notes.html) don't name the 21 operations, so diff your calls against the "What's changed in SDDC Manager API" changelog they point to, and plan migrations before those endpoints go. The [certificate blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html) keeps SDDC Manager APIs only for backward compatibility during the move to the VCF Operations fleet management API.
4. **Move expiry alerting.** The blueprints say to use VCF Operations' built-in alerts for [certificate](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html) and [password](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) expiry, and [9.1.1 generates expiry alarms](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) for all certificates across VCF components.
