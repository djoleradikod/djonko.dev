<InShort>
On 9.1, backup is several jobs in several places. Management services and VCF Automation go to SFTP from VCF Operations, SDDC Manager and NSX Manager have their own SFTP target, and each vCenter schedules itself. VCF Operations needs a third-party image-based tool, and the license server has no backup at all. Only NSX Manager gets a documented default schedule, and it writes to the SDDC Manager appliance until you redirect it. Point every SFTP job at an external server, start from Broadcom's once-a-day, seven-day baseline, and plan NSX cleanup yourself, because NSX retention isn't enforced.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to list VCF Operations as backed up over SFTP, say non-standard SFTP ports fail host key validation, and call every four hours a better default. On 9.1 VCF Operations is image-based, custom ports are supported from 9.1.1, Broadcom's recommended cadence is once a day, and the four-hour figure is one KB's remedy for a stuck precheck.
</Callout>

## What each component needs

Methods come from the [9.1 backup blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-backup-and-restore.html) and the [component list in TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation.html). Cadence is the [recommended schedule table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/file-based-backups-for-sddc-manager-and-vcenter-server.html) <AsOf date="2026-11-07" />.

| Component | Method | Where | Cadence and retention |
|---|---|---|---|
| VCF management services (services runtime, fleet and SDDC lifecycle, identity broker, depot, Salt, log management, telemetry, real-time metrics) | File, SFTP only | Build > Lifecycle > VCF Management > Backup & Restore, per VCF instance | Daily, 7 days |
| VCF Automation | File, SFTP only | Same | Daily, 7 days |
| SDDC Manager | File, which the design recommends, or image | Target under Operate > Administration > SDDC Manager > Backup Settings | Daily, 7 days, starting within the same 5-minute window as every vCenter |
| vCenter | File, which the design recommends, or image | Management interface on port 5480, per vCenter. Select Supervisors Control Plane if a Supervisor runs there. | Daily, 7 days, same window |
| NSX Manager | File, SFTP only | Set by SDDC Manager at bring-up | Hourly, 7 days on paper (see below) |
| NSX Edge | Inside the NSX Manager backup | Recovery: failed nodes are redeployed from NSX Manager | |
| VCF Operations | Image, third-party tool | VADP-compatible backup job, quiescing off | Daily, keep at least 3 days |
| VCF Operations for networks | Image, third-party tool | VADP-compatible backup job, quiescing on | Daily, keep at least 3 days |
| Distributed switch configuration | Export, on demand | | Keep the last 3 configurations |
| SDDC Manager credential store | JSON from the API, if you have no external vault | SDDC Manager developer center or REST API | [At least daily](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/on-demand-backups-in-vmware-cloud-foundation/backup-sddc-manager-credential-store.html) |
| License server | None | Recovery: deploy a new one and reconfigure licensing | |

Two rows need action before anything else. VCF Operations has no SFTP path, so an estate without a [VADP-compatible tool](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/configure-vmware-cloud-foundation-operations-vm-level-backup.html) has an unprotected operations cluster. Back up all its nodes at the same time, cloud proxies included, offline if you can and unquiesced if you can't. Keep the job away from dynamic threshold calculations, which [run at 2 a.m. by default](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-backup-and-restore.html), because an overlap can cause performance problems or loss of nodes. The license server belongs in the recovery runbook as a redeployment.

## Set schedules before the first upgrade

Only NSX Manager has a documented default schedule, so treat everything else as unprotected until someone configures it. NSX and SDDC Manager backups [sit on the SDDC Manager appliance](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/reconfigure-sftp-backups-for-sddc-manager-and-nsx-manager.html) until redirected, and an external server is [a prerequisite for restoring SDDC Manager](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation.html). The management services SFTP target is also a [prerequisite for patching or upgrading](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/configure-sftp-backup-target-in-vmware-cloud-foundation-operations.html) those services, which makes a broken target an upgrade blocker.

Use once a day unless a recovery point objective demands more. Incrementals exist only for fleet lifecycle, SDDC lifecycle, identity broker and Salt RaaS, and TechDocs says to [enable them if hourly backups are needed](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/file-based-backups-for-sddc-manager-and-vcenter-server/configure-backup-schedule-in-vcf-fleet-management.html). Tighter schedules can have a cost: incrementals every 15 minutes kept a VCF Automation 9.0.2 to 9.1.1 precheck queued, and <KB id={456790} /> fixes that by moving all components to every 4 hours. The pages don't reconcile the two figures. This site reads 4 hours as that failure's remedy and once a day as the design baseline.

Don't rely on Back Up Now alone. Scheduled backups capture telemetry and real-time metrics, and on-demand ones [don't](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/file-based-backups-for-sddc-manager-and-vcenter-server.html). After a restore from a manual backup those components show as Unknown and have to be cleaned up and reinstalled (<KB id={459138} />). TechDocs still recommends an [on-demand backup immediately before an upgrade](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation.html), so take it and confirm a recent scheduled backup exists as well.

Recheck schedules after moving to 9.1. Any schedule created before VCF Automation was deployed or upgraded to 9.1 [must be reconfigured by re-entering the password](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/file-based-backups-for-sddc-manager-and-vcenter-server/configure-backup-schedule-in-vcf-fleet-management.html), while the schedule picks up log management and identity broker automatically. Confirm the services runtime appears in the backup configuration and that a recent backup exists. With many instances, William Lam's [17 July script](https://williamlam.com/2026/07/vcf-9-1-automating-vcf-backup-scheduling-with-the-fleet-lcm-api.html) shows the same per-instance schedule through the Fleet LCM API's `backupConfigSpec`. That payload holds the SFTP password and passphrase, so keep it out of source control.

## What the SFTP server has to satisfy

One server should be able to serve every SFTP job, but the pages set different requirements. Offering both RSA and ECDSA host keys meets all the host key lists, FIPS mode aside. That's an inference from the pages below, and Broadcom doesn't state it.

| Setting | Do this | Why |
|---|---|---|
| Host keys, management services | Offer ssh-ed25519, rsa-sha2-512 or rsa-sha2-256 | [Target page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/configure-sftp-backup-target-in-vmware-cloud-foundation-operations.html). The [schedule page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/file-based-backups-for-sddc-manager-and-vcenter-server/configure-backup-schedule-in-vcf-fleet-management.html) lists only the two RSA options. |
| Host keys, SDDC Manager and NSX | 256-bit ECDSA and 2048-bit RSA | [Target page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/reconfigure-sftp-backups-for-sddc-manager-and-nsx-manager.html), which adds FIPS-mode algorithm limits |
| OpenSSH 9.8 or later | Add SDDC Manager and NSX Manager IPs to `PerSourcePenaltyExemptList` | Same page |
| Server name | All-lowercase FQDN | Known-hosts validation is case-sensitive, and an uppercase name stopped the pre-upgrade backup on 9.1.x (<KB id={453300} />) |
| Username | `user@domain` or a plain service account, not `domain\user` | A script defect on 9.1.0.x fails the fleet lifecycle upgrade at `vmsp_upgrade` on the backslash (<KB id={450561} />) |
| Port | 22, or a custom port [from 9.1.1](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/configure-sftp-backup-target-in-vmware-cloud-foundation-operations.html) | Runtime control plane and worker nodes must reach the server, or fingerprint retrieval fails (<KB id={451514} /> covers TCP 22) |
| Directory rights | Full access on the path and its parents | The configuration precheck fails on permissions (<KB id={456277} />) |

On 9.1.1, vCenter doesn't insist on a verified server by default. Its default mode transfers as before and [records a non-blocking advisory](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcenter-9-1-1-0-release-notes.html). Enable strict validation if you need the connection to fail instead.

## NSX retention is yours to enforce

Broadcom's pages conflict here. The schedule table recommends 7 days for NSX Manager, but <KB id={442696} /> calls unenforced retention a known limitation in 9.0 and 9.1, with backups piling up until storage runs out. It defers a fix to a future release. Hourly for 7 days is 168 backups, and past that point nothing removes the older ones.

Keep the hourly schedule, run the NSX cleanup script that <KB id={448811} /> points to, and alert on SFTP free space. The KB's alternative is a move to daily through properties files on the appliance. That slows growth without enforcing retention and gives up the hourly recovery point, so it suits an estate that can't run the script.

## What a restore needs

A backup job doesn't produce everything a restore requires, and these items should be in place before a failure.

- The SFTP passphrase [is required to restore](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/configure-sftp-backup-target-in-vmware-cloud-foundation-operations.html), so store it in the vault with an owner. vCenter's encryption password can't be recovered from the backup, so [record it outside the VCF instance](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/file-based-backups-for-sddc-manager-and-vcenter-server/configure-a-backup-schedule-for-vcenter-server.html).
- [SDDC Manager restores](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/restoring-vmware-cloud-foundation/file-based-restore-for-sddc-manager-vcenter-server-and-nsx-t-data-center/vcf-52-restore-sddc-manager.html) onto a new appliance at the backup's version, and vCenter must already be available. vCenter needs a same-version replacement appliance too, so [TechDocs says](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/configure-backup-target-and-schedules-in-vmware-cloud-foundation/file-based-backups-for-sddc-manager-and-vcenter-server/configure-a-backup-schedule-for-vcenter-server.html) to store that image with your backups and refresh it after each patch.
- The [instance recovery blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-instance-recovery.html) wants backups at a remote site or duplicated off-site, plus as-built records on secure secondary storage. Its rebuild stays in the same site, so site loss needs the separate [fleet disaster recovery blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-disaster-recovery.html).

Management services recovery depends on how much is left. A single lost node redeploys automatically, while losing two or three means [redeploying the services cluster and then restoring](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/restoring-vmware-cloud-foundation/restore-vcf-management-services.html). Component corruption takes an in-place restore.

Rehearse two restores in a lab: SDDC Manager onto a new appliance, and Log Management onto a rebuilt runtime, which has extra steps. Its [log data isn't in the backup](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation.html) and must be archived separately, so a restore returns the service without the history. On a rebuilt cluster, ingestion may need the recovery bundle's `--post-restore` mode (<KB id={436904} />). Step 1 of that KB still shows placeholders for the download location <AsOf date="2026-11-07" />, so get the bundle from Broadcom before you schedule the rehearsal. On 9.1.1, a [restart of the service clears an "Unable to access logs" error](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) after restoration, and an SDDC Lifecycle restore that reports failure may be a reporting error, so check the component before you restore again.

## Snapshots and stale locks

Snapshots aren't backups. They belong to the upgrade plan, and the blueprint's method table doesn't list them. For 9.0.2 to 9.1, <KB id={450430} /> takes VCF Operations offline, snapshots "all primary nodes", brings it back online, then installs. That wording is narrower than the node list for image-based backups, so use [Rollback checkpoints](/vcf/library/upgrades/rollback-checkpoints/) for the per-component list. Never snapshot NSX Managers or Edges, because that can destabilise the cluster or corrupt its database (<KB id={433822} />).

A hung SDDC Manager backup can leave a stale lock that blocks password remediation (<KB id={447314} />, 5.x) or host commissioning and backup target edits (<KB id={439473} />, 5.x and 9.0.x). Neither KB lists 9.1 and both fixes edit the appliance database, so open a support case if you see this on 9.1.
