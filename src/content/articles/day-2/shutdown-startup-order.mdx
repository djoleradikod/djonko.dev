<InShort>
The principle hasn't changed since 5.x: shut down consumers before what they depend on, and start in reverse. Workload domains go before the management domain, and the management components go before the infrastructure that hosts them. VCF 9 adds a fleet rule: **the instance that runs VCF Operations goes down last and comes up first**. 9.1 adds two components to the management domain sequence. The **License Server** is an ordinary VM. The **services runtime** is shut down only with its script, which knows the runtime's internal order. After an unclean power event, the runtime comes back control plane first.
</InShort>

## Shutdown, 9.1 management domain

After every workload domain is down (customer workloads, protection, edges, NSX managers if not shared, hosts, then the workload domain vCenter):

1. VCF Automation
2. VCF Operations for networks
3. Cloud proxies
4. License Server
5. **Management services:** `vcf_services_runtime_shutdown.sh` (<KB id={440874} />). Run it with `--dry-run` first. Don't stop runtime VMs by hand.
6. **VCF Operations:** take the cluster offline, then shut the nodes down in the documented order (<KB id={341964} />)
7. Protection and recovery, if deployed, as late as possible
8. NSX edges, then NSX managers
9. SDDC Manager
10. Hosts and the management vCenter through the vSAN shutdown wizard. DNS, NTP and AD VMs go last if they live here.

For 9.0, the list differs in the middle. There is no License Server or runtime, but VCF Operations for logs, the identity broker appliance and the fleet management appliance are shut down before VCF Operations.

## Startup, 9.1 management domain

1. Hosts, powered on out of band
2. SDDC Manager
3. NSX managers (wait for the cluster to be stable), then edges
4. Protection and recovery
5. **VCF Operations:** power on in order, then bring the cluster online
6. **Management services:** control plane nodes first, then workers. Allow about 20 minutes, and confirm no workers are still being replaced.
7. License Server
8. Cloud proxies
9. VCF Operations for networks
10. VCF Automation

Then each workload domain: vCenter, hosts, a cluster restart to re-establish principal storage integration (easy to miss), NSX, edges and workloads. With shared NSX, bring up the other workload domains first, then the domain that runs the shared edges.

## After an unclean power event

If the runtime came back on its own in the wrong order, services can stay at zero replicas and nodes at "Ready,SchedulingDisabled". The documented recovery is to power on the control plane first, wait five minutes, power on the workers, then wait 15 to 20 minutes (<KB id={440862} />). The same KB covers the power-off marker that the shutdown script leaves behind.

<Callout type="field">
Write the order for the actual estate, not the generic one. List which optional components exist, where DNS, NTP and AD run, and which domains share NSX. Then time a planned shutdown in a maintenance window. Allow for the hour each way that VCF Operations takes.
</Callout>

## Pitfalls

- **Forgetting the backup tools.** Stop VADP-based backup jobs first, or they fail noisily and hold snapshots.
- **Running management VMs on snapshots** through a shutdown. Consolidate first.
- **Credentials.** Save the host and vCenter credentials before you start. SSO may not be available halfway through.
