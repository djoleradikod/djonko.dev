<InShort>
A remote plugin is a vCenter extension with a key, a download URL and a thumbprint. The client [checks the thumbprint before downloading](https://knowledge.broadcom.com/external/article/432196), so a plugin fails when the URL is unreachable, the certificate changed or the registering product is gone. Let the owner decide the fix. If the product is alive, repair trust and re-push from it. If it's gone, redeploy it or unregister the extension in the MOB. Delete a cached package only when a KB for your symptom names the folder.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to say two NSX plugins on one vCenter are expected with Federation, a claim the NSX and SDDC Manager plugin KBs here (406976, 426389, 434625, 404182) don't mention (checked 7 November 2026), so it's gone. It also cited the Emulex local-plugin KB for a remote-plugin cleanup that used a different cache path, described KB 395813 as a plugin stuck at an old version when its symptom is a blank Lifecycle Manager pane, and told readers to redeploy the SDDC Manager plugin where the KB removes it and restarts a service.
</Callout>

## Repair from the owner first

Unregistering comes last, because re-registering from the owner is what puts the plugin back and an extension with a recent heartbeat is [still in use](https://knowledge.broadcom.com/external/article/344648). Plugin status is under Administration > Solutions > Client Plugins.

| Owner | Route that re-pushes the plugin | What to check first |
|---|---|---|
| VCF Operations | [Edit the vCenter account, then Manage Integrations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/connect-to-data-sources/vsphere/configuring-a-vcenter-server-cloud-account-in-vrealize-operations.html). VCF Operations registers its plugin when plugin management is enabled on the account. | Without the required privileges the account is added for monitoring only. Replacing another instance's integration means assigning a new licence to that vCenter. A pre-9.0 vCenter gets plugin management only. |
| SDDC Manager | Remove "SDDC Manager Remote Plugin" under Client Plugins, then run `systemctl restart sddc-manager-ui-app`, or run the KB's `vcRootCaSync` script if the trust store is what's stale (<KB id={419087} />). | Back up SDDC Manager and vCenter first. The KB names no versions. |
| NSX | System > Compute Managers, add or re-register the vCenter (<KB id={426389} />). | Deleting the compute manager normally unregisters the extension, but not once the NSX Manager has gone (<KB id={434625} />). |
| vCenter's own vSAN plugins | No product to push from. Correct the stored thumbprint in VCDB (<KB id={432196} />). | Snapshot first, because this edits the database directly. |

## The VCF Operations plugin version

An older VCF Operations plugin on its own isn't a fault. The plugin [stayed at 9.0.0.0 after VCF Operations and vCenter both went to 9.0.1.0, by design](https://knowledge.broadcom.com/external/article/427228), and that KB says it updates only when the VCF Operations SSL certificate is renewed.

A second KB gives a different trigger. When a vCenter upgrade precheck warns that VCF Operations "is not at desired version" because the plugin failed or its version doesn't match, [Administration > Integrations > Accounts, Manage Integration and the integration toggle](https://knowledge.broadcom.com/external/article/440761) push the updated plugin to the management vCenter. That KB lists the plugin under Client Plugins as "VMware Aria Operations", so look for that name.

<Callout type="analysis" title="Reading the two KBs together">
Leave a lagging plugin alone until the precheck warns or its status shows failed, then use the toggle before considering a certificate renewal, since renewing changes far more than the plugin. Neither KB addresses the other, so treat that order as this site's reading and open a support case if the toggle doesn't move the version.
</Callout>

## Match the symptom

Download and deploy failures log to `/var/log/vmware/vsphere-ui/logs/vsphere_client_virgo.log`, as DOWNLOAD_FAILED or DEPLOYMENT_FAILED lines, and <KB id={312247} /> adds `/var/log/vmware/rhttpproxy/rhttpproxy-##.log` for proxy privileges. Of the KBs here, only <KB id={440761} /> names 9.1 explicitly, and the [vCenter](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcenter-9-1-1-0-release-notes.html) and [VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) 9.1.1 notes list no client plugin change <AsOf date="2026-11-07" />. So check the scope column before applying a fix to a 9.1 system, and snapshot.

## Removing a stale extension

<Steps>

1. **Snapshot vCenter.** For linked vCenters, take offline snapshots of every node. The local-plugin KB warns that skipping this [can corrupt the replication database on a revert](https://knowledge.broadcom.com/external/article/426913).
2. **Turn the MOB on if needed.** It's [off by default in VCF 9.0, to meet STIG requirements](https://knowledge.broadcom.com/external/article/401669), so set `enableDebugBrowse` to true in `vpxd.cfg` and restart vpxd. The KB's environment is vCenter 9.x and it gives no 9.1 default, so try the URL first.
3. **Check it's dead.** Open `https://<vcenter>/mob/`, then content > ExtensionManager. A recent [Last heartbeat time means the extension is in use](https://knowledge.broadcom.com/external/article/344648), so stop there. Run [FindExtension](https://knowledge.broadcom.com/external/article/406976) to confirm the exact key. Under the multi-NSX feature more than one NSX can register against a vCenter, as the [NSX compute manager note](/vcf/library/integrations/nsx-compute-manager/) explains, so confirm which one has gone.
4. **Run UnregisterExtension** with that key. A `void` result is success. In linked mode, [run it on the vCenter that installed the plugin, then restart services on the linked vCenters](https://knowledge.broadcom.com/external/article/344648).
5. **Remove a cached package only if your KB says to.** Remote plugin folders sit under `/etc/vmware/vsphere-ui/cm-service-packages/com.vmware.cis.vsphereclient.plugin/`, and <KB id={417767} /> and <KB id={445047} /> delete one named folder there.
6. **Restart the client** with `service-control --restart vsphere-ui`.
7. **Re-register from the owner**, using the first table.

</Steps>

Step 2 reverses a hardening default, so setting the flag back afterwards is sensible if your baseline follows that STIG. That's an inference from the KB's stated reason, and the KB doesn't ask for it.

## Local plugins and 9.1.1 extension logins

[vCenter 9.0 discontinues support for local plug-ins](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes/product-support-notes-vsphere.html), so any solution that still ships one needs a remote replacement from its vendor before the upgrade. The [2022 announcement by Todor Raykov](https://blogs.vmware.com/code/2022/07/15/vsphere-client-sdk-changes-in-the-upcoming-major-release-of-vsphere/) and <KB id={313839} /> set out that path without version numbers. <KB id={426913} /> is stricter than the support notes, describing local plugins as already unsupported and blocked on 8.x. Its cleanup, for a failed Emulex plugin whose Remove button doesn't work, uses `vc-packages/vsphere-client-serenity/` rather than the remote plugin path above.

The 9.1.1 change to plan for concerns extension logins. Under resolved issues, the 9.1.1.0 notes say [`LoginExtensionBySubjectName` fails after upgrading to vCenter 9.1.1.0](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcenter-9-1-1-0-release-notes.html) with an InvalidLogin SOAP fault and "certificate not pinned in VCDB" in `vpxd.log`, and the entry says the fix effectively removes that deprecated API. They say extensions using `LoginExtensionByCertificate` or SSO are not affected. The notes assign no action, so ask the vendor of each third-party extension which login it uses before moving to 9.1.1.

<Callout type="analysis" title="Certificate changes are the trigger to plan for">
The 9.1 blueprint says to ["perform certificate management for all supported components exclusively through VCF Operations"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html), and not to use vCenter for ESX host or vCenter certificates once VCF Operations manages them. Follow it, because the SDDC Manager row above shows what follows when a certificate is renewed outside the manager that tracks it. That page doesn't mention thumbprints, though, and doesn't say VCF Operations refreshes them, so check Client Plugins after every replacement and keep that check in the runbook.
</Callout>
