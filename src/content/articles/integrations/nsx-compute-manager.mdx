<InShort>
From 9.0 a compute manager **service account is mandatory**: NSX creates `nsxt_<id>` in vCenter and renews its password every 90 days. vCenter is also the **OIDC provider** for NSX by default. So the registration depends on a valid vCenter certificate chain, a service account NSX can renew, and the right privileges for the user who registered it. When the status is **Down**, click it: the message and code map to a KB (<KB id={317794} />). The most common in 9.x: **7058** after a vCenter root CA change (edit, save, confirm the thumbprint) (<KB id={451125} />), **90011** for OIDC trust (<KB id={431963} />), and expired service account passwords (<KB id={413178} />).
</InShort>

## Error codes worth knowing

| Code or message | Cause and fix |
|---|---|
| 7058 "trusted root certificate cannot be found" | vCenter root CA replaced. Edit the compute manager, save with no changes, confirm the new thumbprint (<KB id={451125} />). |
| "The certificate for the Compute Manager has expired or is invalid" | Thumbprint mismatch. Fix vCenter's certificate, then edit and accept (<KB id={446711} />). |
| 90011 "Failed to enable trust ... OIDC endpoint" | Two certificate entries for the same vCenter in NSX trust. Update the thumbprint through the API (<KB id={431963} />). |
| "Invalid credentials provided or extension not valid" | The `nsxt_` service account password expired. **Resolve** with vCenter admin credentials (<KB id={413178} />). |
| "Registered with Errors", service account creation denied | The registering user lacks `LicenseService.Administrators` (<KB id={433425} />). |
| "already registered with other NSX manager" | A stale extension from a decommissioned NSX. Unregister both NSX extension keys in the MOB, then re-add (<KB id={426389} />). |
| 7061 | Registering with a federated identity provider user. Use a local vCenter account (<KB id={433085} />). |
| 7059 when registering vCenter 9 into NSX 4.2 | Not supported for new registrations. Use NSX 9.0.2 or later (<KB id={451344} />). |

Logs on NSX Manager: `/var/log/cm-inventory/cm-inventory.log` for registration and trust, and `/var/log/syslog` for service account events.

<Callout type="field">
When planning a vCenter certificate or CA change, list every system that pins vCenter's certificate: NSX compute managers, VCF Operations accounts, VCF Automation cloud accounts, vSphere Client plugins and backup tools. Re-trust them in that order straight after the change.
</Callout>

## Pitfalls

- **Re-registering instead of editing.** Edit and confirm the thumbprint first. Re-registration can create duplicates.
- **Registering with an SSO-federated personal account.** Use a dedicated local account.
- **Ignoring "Registered with Errors".** vLCM features on NSX hosts depend on a clean registration.
