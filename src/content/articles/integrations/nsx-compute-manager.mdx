<InShort>
**In VCF 9 one vCenter registers with one NSX.** Broadcom documents multi-NSX as not supported from 9.0 (<KB id={417789} />, <AsOf date="2026-11-06" />). It was an opt-in NSX feature from 3.2.2 (<KB id={419414} />), and 9.0 is where it ends. One NSX serving several vCenters is a separate arrangement and still exists. If an estate runs several NSX on one vCenter today, the table below picks the exit. The exits range from a settings change to a new vCenter. Whichever applies, turn the flag off last, because a vCenter with the flag off can't take another NSX.
</InShort>

<Callout type="note" title="Corrected on 6 November 2026">
This note used to say several NSX Managers per vCenter was supported in 9.x and not in 5.x. It is the other way round.
</Callout>

## Which exit fits the estate

Broadcom gives two routes: switch the flag off, or map each NSX to its own vCenter ([Manage Unsupported Features page, updated 2 Nov 2026](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/deployment/upgrading-cloud-foundation/upgrade-the-management-domain-to-vmware-cloud-foundation-5-2/upgrading-nsx--to-version-9/manual-upgrade-to-nsx-9-by-using-upgrade-coordinator/manage-deprecated-nsx-features.html)). It does not say which to choose. The audit in step 1 below sorts the estate into one of these rows.

| What the audit shows | Decision | Cost |
|---|---|---|
| Flag on, one NSX registered | Edit that compute manager and set Multi NSX to No. | A settings change. <KB id={411878} /> lists no host work for this case. |
| Two NSX registered, the second owns no prepared hosts | Delete the second compute manager, then turn the flag off on the survivor. | Low. Check vCenter for leftover extensions afterwards. |
| Both own hosts, and the reason for two has gone or was only about policy | Consolidate onto one NSX. | Rebuild the retiring NSX's segments, groups, rules and gateways on the survivor, then move its hosts. |
| Both own hosts, and they must keep separate management planes or upgrade cycles | One vCenter per NSX. | A new vCenter, a cluster move, and an import path for the new pair. |

<Callout type="analysis" title="Choosing between the last two rows">
This is this site's reasoning. Broadcom publishes no such test. Ask what the second NSX was for. If the answer is tenant or policy separation, projects and VPCs on one NSX may express it (see [NSX in 9.x](/vcf/library/architecture/nsx-in-9/)), and consolidating leaves one NSX to upgrade. If the answer is a separate change window, a separate admin team or a boundary that requires its own management plane, one NSX can't give that, so split the vCenter. With no written reason, consolidate. The answer changes if the second NSX's hosts retire before the upgrade date: let them go, and the estate falls into row two.
</Callout>

## The order that avoids a dead end

<Steps>
1. **Audit every NSX.** [`GET /api/v1/fabric/compute-managers`](https://developer.broadcom.com/xapis/nsx-t-data-center-rest-api/9.1.0/method_ListComputeManagers.html) on each manager returns its compute managers, whose schema carries `multi_nsx`. In vCenter, `/mob/?moid=ExtensionManager` shows how many NSX are registered (<KB id={411878} />). Under this feature NSX rewrites its extension key to `com.vmware.nsx.management.nsxt.<computemanager-id>` ([NSX 4.2 guide](https://techdocs.broadcom.com/us/en/vmware-cis/nsx/vmware-nsx/4-2/installation-guide/host-transport-nodes/multiple-nsx-managers-managing-a-single-vcenter-server.html)), so that suffix is a likely tell. A cluster that shows read-only in one NSX belongs to the other.
2. **Clear what blocks a host move.** A host that is a static member of an NSGroup on its current NSX can't have NSX removed or be prepared by the new one (<KB id={419414} />). The NSX 4.2 guide says this can happen even without the flag.
3. **Empty the NSX you are retiring.** Moving a host into a cluster owned by the other NSX makes the first uninstall its VIBs and drop ownership, and only then does the second install. Edge VMs work only for the NSX that deployed them. To the other NSX they are ordinary VMs, and its distributed firewall rules can apply to them (<KB id={419414} />).
4. **Delete the retiring compute manager.** <KB id={411878} /> has you remove all NSX components from that NSX Manager cluster first. Extensions left behind have to be deleted by hand, according to the NSX 4.2 guide.
5. **Turn the flag off on the survivor, last.** Every NSX on a vCenter must carry the same setting, so there is no supported half-way state. The NSX 4.2 guide also says a vCenter with the flag off can't then register with another NSX, so settle the target layout before this step.
6. **Then convert to images and upgrade.** VCF 9.0 installer validation rejects clusters that aren't on vLCM images (<KB id={443265} />), and converting a cluster to an image fails while the flag is on and NSX is on its hosts (<KB id={411878} />). So this step can't come sooner. The upgrade precheck also fails if a registered compute manager has no enabled service account ([Manage Unsupported Features page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/deployment/upgrading-cloud-foundation/upgrade-the-management-domain-to-vmware-cloud-foundation-5-2/upgrading-nsx--to-version-9/manual-upgrade-to-nsx-9-by-using-upgrade-coordinator/manage-deprecated-nsx-features.html)).
</Steps>

Splitting the vCenter adds two version constraints. New registration of NSX 4.2.x to vCenter 9.0.x fails with error 7059, and only pairs registered before the vCenter upgrade carry over (<KB id={451344} />). This site's reading is to register the new pair while vCenter is still on 8.x, or take that NSX to 9.0.2 or later first. The first route has a catch: <KB id={425164} /> reports the vCenter 8.x to 9.x precheck failing on NSX 4.2.2.1 with "Unsupported NSX version registered with vCenter", and limits that pairing to upgrade scenarios managed by SDDC Manager. NSX 4.x outside a VCF instance reaches 9.0.x only after import as a workload domain (same KB).

Close two gaps with Broadcom Support before committing. None of the sources cited here describes a tool that merges one NSX's configuration into another, or a procedure for moving an NSX-prepared cluster to a different vCenter in this scenario (checked 6 Nov 2026). The rebuild in row three and the cluster move in row four are this site's inference from the host-move behaviour above.

## Where the sources disagree

- **The pre-check.** <KB id={417789} /> says the NSX Manager pre-check returns an error if the flag is still on when upgrading to 9.0 or later. <KB id={431174} /> reports an estate on NSX 9.0.1.0 with extra 4.2.3 managers on the same management vCenter, where all prechecks passed on the way to 9.0.2.0 and the job then cancelled with no error in the UI. The KB doesn't say whether the flag was on or how the estate got there. A green pre-check therefore doesn't prove the topology is clean, so run the audit yourself.
- **Scoping the upgrade doesn't help.** Per <KB id={431174} /> the engine scans every compute manager registered in vCenter, so selecting only the 9.x NSX in Fleet Management still cancels.
- **The workaround.** The same KB's fix is to run the upgrade from Upgrade Coordinator on the NSX Manager, then a full inventory sync. Broadcom calls this a workaround and "not the expected behavior". It gets a stuck upgrade moving, and none of its steps removes the older NSX, so this site's reading is that the exit above is still owed.
- **"Deprecated" or "not supported".** <KB id={431174} /> says 9.0.x deprecates the topology. <KB id={417789} /> and the Manage Unsupported Features page both say not supported from 9.0. Plan on the stronger wording. The [9.1 version of that page, updated 5 Nov 2026](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-the-management-domain-to-vmware-cloud-foundation-5-2/updating-vcenter-and-nsx/checklist-for-upgrading-nsx/manage-deprecated-nsx-features.html) says the same, and the [VCF 9.1 import guide, updated 5 Nov 2026](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/working-with-workload-domains/import-an-existing-vcenter-to-create-a-workload-domain.html) also lists "Multiple NSX Manager instances managing a single vCenter instance" as not supported for import.
- **The API still has the field.** `multi_nsx` remains in the [9.1 schema](https://developer.broadcom.com/xapis/nsx-t-data-center-rest-api/9.1.0/schemas_ComputeManager.html) and the [9.1.1 schema](https://developer.broadcom.com/xapis/nsx-t-data-center-rest-api/latest/schemas_ComputeManager.html), default `false`, with no deprecation text, so its presence says nothing about support.
- **Old documentation.** The [NSX-T 3.0 page](https://techdocs.broadcom.com/us/en/vmware-cis/nsx/nsxt-dc/3-0/administration-guide/operations-and-management/add-a-compute-manager-1.html), still online, says a vCenter can't register with more than one NSX. That predates 3.2.2.
- **VCF 5.x.** The 5.x column below reports NSX's position. No VCF 5.x document found says whether SDDC Manager supports the feature (checked 6 Nov 2026), so ask Broadcom if contractual support matters.

## What the connection does

Registering vCenter as a compute manager gives NSX a line into vCenter for four jobs:

- **Inventory.** NSX polls vCenter for cluster information (worded this way in the [NSX-T 3.0 guide](https://techdocs.broadcom.com/us/en/vmware-cis/nsx/nsxt-dc/3-0/administration-guide/operations-and-management/add-a-compute-manager-1.html); registration and inventory errors in current KBs land in `cm-inventory.log`).
- **Extension.** NSX registers extension keys in vCenter, which is why a decommissioned NSX can block a new registration (<KB id={426389} />).
- **Service account.** NSX creates an `nsxt_<id>` account whose password expires after 90 days by default and which NSX renews (<KB id={413178} />). The [9.1 schema](https://developer.broadcom.com/xapis/nsx-t-data-center-rest-api/9.1.0/schemas_ComputeManager.html) says features such as vLCM need it for vAPI authentication, and that it is mandatory from VCF 9.0. Without it the registration shows Registered with Error and vLCM can't be enabled on NSX clusters (<KB id={433425} />).
- **OIDC trust.** `set_as_oidc_provider` is described as "specific to wcp feature", which this site takes to mean Supervisor. It defaults to `true` in the 9.1 schema and `false` in the [4.2 schema](https://developer.broadcom.com/xapis/nsx-t-data-center-rest-api/4.2/schemas_ComputeManager.html).

Multi-NSX added ownership on top. Each NSX stamps the managed objects it prepares, and another NSX can't take them until the first gives up ownership or it is forced across ([NSX 4.2 guide](https://techdocs.broadcom.com/us/en/vmware-cis/nsx/vmware-nsx/4-2/installation-guide/host-transport-nodes/multiple-nsx-managers-managing-a-single-vcenter-server.html)). The instances otherwise run independently, each with its own managers and edges (<KB id={417789} />). The same guide lists vLCM and vSphere with Tanzu as not interoperable with it, and the [Supervisor 8.0 install page](https://techdocs.broadcom.com/us/en/vmware-cis/vsphere/vsphere-supervisor/8-0/installing-and-configuring-vsphere-supervisor/networking-for-vsphere-with-tanzu/install-and-configure-nsx-and-nsx-advanced-load-balancer/deploy-and-configure-the-nsx-manager.html) says to leave the option unselected. This site infers that the vLCM conflict is why the feature couldn't survive 9.0's requirement for images. Broadcom doesn't state its reason.

## Errors, and the KB for each

When the status is **Down**, click it. The message maps to a KB (<KB id={317794} />).

| Code or message | Cause and fix |
|---|---|
| "Multiple-NSX managers per vCenter feature is enabled but NSX-T Data Center is installed on the following host(s)" | vLCM and multi-NSX can't coexist. Shows up on image conversion (<KB id={411878} />) and on host upgrade (<KB id={413969} />). Use the table at the top. |
| "trusted root certificate cannot be found" | vCenter root certificate replaced, or a race during an NSX upgrade left the Machine SSL certificate out of sync. Edit the compute manager, save with no changes, confirm the new thumbprint (<KB id={451125} />). |
| 7058 "could not be connected, server might be un-reachable" | The message points at certificate validity and firewall ports. One rare cause is a missing root endpoint in vCenter's reverse proxy configuration (<KB id={319050} />). |
| "The certificate for the Compute Manager has expired or is invalid" | Thumbprint mismatch. Apply a new vCenter certificate, then edit, re-enter credentials and accept (<KB id={446711} />). |
| 90011 "No thumbprint is configured for the OIDC endpoint" | Two certificate entries for the same vCenter FQDN in NSX trust. Update the thumbprint through the API (<KB id={431963} />). |
| "Invalid credentials provided or extension not valid" | The `nsxt_` service account password expired. **Resolve** with vCenter admin credentials (<KB id={413178} />). |
| "Registered with Error", service account creation denied | The registering user lacks `LicenseService.Administrator`. Add it to the license service administrators group (<KB id={433425} />). |
| "already registered with other NSX manager" | A stale extension from a decommissioned NSX. Unregister both NSX extension keys in the MOB, then re-add (<KB id={426389} />). The KB's cause is a decommissioned manager, so confirm the other NSX is gone before removing anything. |
| 7061 | Registering with an SSO user who signs in through an external identity provider such as Okta. Use a local vCenter account (<KB id={433085} />). |
| 7059 when registering vCenter 9.0.x into NSX 4.2 | Not supported for new registrations. Use NSX 9.0.2 or later (<KB id={451344} />). |

On NSX Manager, look in `/var/log/cm-inventory/cm-inventory.log` for registration and service account creation errors (<KB id={319050} />, <KB id={433425} />), and in `/var/log/syslog` for service account password failures (<KB id={413178} />).
