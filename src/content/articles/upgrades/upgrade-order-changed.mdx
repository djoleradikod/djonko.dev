<InShort>
The rule is that **whatever manages a component is upgraded before the component**. In 5.x, SDDC Manager managed everything, so it went first. In 9.x, VCF Operations is the console, the licence holder and, in 9.1, the orchestrator of fleet and SDDC lifecycle, so it goes first. After it come the services it uses, then SDDC Manager, then the management services, then each domain's core. The 9.1.1 patch rules apply the same logic one level down. Fleet lifecycle is patched first, and a service is patched before anything that runs on it.
</InShort>

## The 9.1 sequence, and the reason for each step

The sequence is a table in [Broadcom's upgrade guide](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html) (updated 5 Nov 2026), listing components "in the order that you must upgrade each component". <KB id={440630} /> says the sequence is mandatory and sends you to that guide. The table doesn't give reasons, so these are this site's:

On a 9.0 source one step can come first: a broker appliance on an NSX overlay segment outside the VCF management network has to be redeployed before VCF Operations, as [the Identity Broker note](/vcf/library/architecture/identity-broker/) explains.

1. **VCF Operations first.** It holds the lifecycle UI and the licence file, and on a 9.0 source it receives the fleet appliance's inventory during its own upgrade. The 9.1 binaries do not even appear in VCF Operations 9.0 until it is upgraded (<KB id={440282} />).
2. **vSphere Replication, Live Site Recovery, vSAN Data Protection and Avi.** These are compatibility gates. Avi must already be supported by the SDDC Manager you are about to install.
3. **SDDC Manager.** This is the engine that will deploy the management services and later upgrade the core.
4. **Management services, License Server and software depot (9.1).** Fleet lifecycle and SDDC lifecycle must exist before they can upgrade anything. Configure the depot before any further component upgrades.
5. **Identity broker, then VCF Automation, then the rest of the management components** (Orchestrator, Operations for networks, log management). These are clients of the runtime and of SSO.
6. **Core, per domain.** HCX, then NSX and vCenter according to the plan, then ESX, NSX edges and finalize.

## The 9.1.1 patch rules follow the same logic

Within 9.1, patches arrive per component as Express Patches. The release notes set dependencies that only make sense with the manager-before-managed rule in mind:

- **Patch fleet lifecycle first.** It is the tool that applies every other patch.
- **Don't use "Upgrade All"** until the dependencies below are met.
- **Never patch VCF Operations in parallel** with anything else.
- **Patch VCF Operations and the License Servers before moving ESX** from 9.1.0.x to 9.1.1.
- **Patch the services runtime before the identity broker and Salt RaaS** that run on it. The broker precheck enforces this with `VCFMS-PRECHECK-VIDB-VMSP-VERSION-001` (<KB id={457245} />).
- **Patch VCF Automation before the migration service engine.**
- **Let a software depot patch finish.** It blocks all other patches while it runs.

Express Patches are cumulative, so you can skip intermediate ones. If an Express Patch contains fleet lifecycle, apply that one first.

<Callout type="warn" title="The 9.0 fleet appliance after the upgrade">
Once VCF Operations is upgraded from 9.0, the fleet management appliance is decommissioned and powered off. Its inventory is kept until the management services are deployed. Powering it back on causes authentication failures later in the upgrade (<KB id={449075} />). Delete it once the management services are in place.
</Callout>

## Pitfalls

- **Starting with SDDC Manager out of 5.x habit.** On a 5.2 source the SDDC Manager UI still drives its own upgrade, but only after the management components are ready.
- **Running lifecycle tasks in parallel to save time.** Fleet lifecycle serializes work for a reason. A stuck "In Progress" subtask blocks later patches until it is cleared.
- **Assuming a patch order that worked last time.** Re-read "Getting to 9.1.1" in the target's release notes before every window. The rules change between patches.
