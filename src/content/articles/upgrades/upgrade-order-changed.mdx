<InShort>
On a path to 9.1, **upgrade VCF Operations first** (Aria Operations on a 5.2 source) and then follow Broadcom's table for your source version, step by step. The 9.1 lifecycle tools don't exist until step 7, and the table requires the steps before it first. Go straight to 9.1.1 where your source allows it. The 9.1.1 patch dependencies below bind environments already on 9.1.0.x. Express Patches are a separate matter and can go in any order, though William Lam suggests considering one that contains fleet lifecycle first.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to apply the 9.1.1 dependency rules to Express Patches, say an async patch tool was built into SDDC Manager, and say a powered-on fleet appliance causes authentication failures later in a 9.0 upgrade. The rules bind the move from 9.1.0.x to 9.1.1, 5.2 added async patching from the UI, and the appliance failure on record is a 401 at precheck on a 9.1.0.x patch.
</Callout>

## Why VCF Operations moved to the front

In 9.1, VCF Operations [uses fleet lifecycle, SDDC lifecycle and the software depot to orchestrate lifecycle work](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management.html). Broadcom's table gives no reasons, so reading that as why it goes first is this site's call. Several early steps are stated as dependencies. The 9.1 binaries won't appear on a 9.0 environment until VCF Operations has been upgraded by PAK file, and SDDC Manager and the depot follow (<KB id={440282} />). Management services [need VCF Operations and SDDC Manager at 9.1.x](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/deploy-vcf-management-services.html), and the fleet-level depot has to be configured before the remaining components can proceed. Starting with SDDC Manager out of 5.x habit therefore gets you nowhere on a 9.0 source: the symptom is an empty binary list.

The 5.x sequence was SDDC Manager, Aria Suite, NSX, vCenter, ESX (<KB id={405275} />). Allen at humbledgeeks [describes the common pre-9.1 order differently](https://humbledgeeks.com/vcf-91-lifecycle-one-control-plane-and-the-real-work-to-get-there/), with the Aria stack first through Aria Suite Lifecycle, and his summary of the new world is the one to remember: "Fleet gates instance, never the reverse." A move to a 9.0 target rather than 9.1 has one extra step at the front: Aria Suite Lifecycle, if you have it, gets patched to 8.18 Patch 2 before VCF Operations (<KB id={390634} />).

<Callout type="analysis" title="How far the manager-first reading goes">
Manager before managed explains steps 1, 6 and 7 and fleet before instance. Broadcom's table gives no reason for the placement of the replication and data protection products, or for Automation and the other management components sitting ahead of the core, so don't use the principle to reorder them.
</Callout>

## The sequence for your source

Broadcom [publishes one table for a 9.0.x source and one for 5.2.x](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html) (updated 5 Nov 2026), each listing components "in the order that you must upgrade" them, and <KB id={440630} /> calls the sequence mandatory. Only fleet-level components and management domains have to reach 9.1.x. Start with the instance hosting the fleet's VCF Operations, move to the other instances' management domains, and upgrade workload domains whenever suits after their instance's management domain.

Where you can, target 9.1.1 directly. The guide allows it from 5.2.x and 9.0.x, the forward-only rule makes it the only choice from 5.2.4 (9.1.0 was released earlier), and the [Fleet Management blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint.html) says to use the latest available binaries when you deploy, upgrade and patch. It carries no upgrade order of its own and defers to the release notes.

| 9.0.x step | 5.2.x step | Component | What to know |
|---|---|---|---|
| 0 | | Identity broker appliance on an NSX overlay segment outside the VCF management network | Redeploy first; [the Identity Broker note](/vcf/library/architecture/identity-broker/) has the rule. Embedded mode upgrades with vCenter. |
| 1 | 1 | VCF Operations and cloud proxy (5.2: Aria Operations) | [Needs the fleet appliance root password](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore/install-a-software-update.html) on 9.0.x. Aria Operations [must be at 8.18 first](https://blogs.vmware.com/cloud-foundation/2026/06/18/how-to-upgrade-to-vmware-cloud-foundation-9-1/). |
| 2-5 | 2-5 | vSphere Replication, Live Site Recovery, vSAN Data Protection, Avi | [Verify Avi's version is compatible](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/apply-cloud-foundation-5-2-update-bundle.html) before SDDC Manager. |
| 6 | 6 | SDDC Manager | From 5.2, [start in the SDDC Manager UI](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/apply-cloud-foundation-5-2-update-bundle.html). From 9.0.x, start in VCF Operations. |

| 8 | 8 | Identity broker (5.2: VMware Identity Manager) | vIDM has no upgrade path. The 9.1 broker arrives with management services, and vIDM keeps serving VCF Automation until you [migrate it](/vcf/library/architecture/identity-broker/). |

The vCenter method depends on the source. [McDonald's June guide](https://blogs.vmware.com/cloud-foundation/2026/06/18/how-to-upgrade-to-vmware-cloud-foundation-9-1/) says a 5.2 source must use reduced downtime upgrade, while 9.0.x can choose it or in-place, so don't write an in-place fallback into a 5.2 runbook. VCF Operations can also schedule [an optimized scenario](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/what-s-new/whats-new-vcf-ops.html) that shortens the window: reduced downtime preparation runs first with no outage, then the window holds the NSX Manager update followed by the vCenter switchover.

McDonald's guide also disagrees with the table on where the management components sit. It lists the core management domain as step 5 and Automation, Operations for networks and logs as step 6, on the grounds that they aren't required for the core stack upgrade. The table puts them ahead of NSX, vCenter and ESX, and contains no exception for reordering. Plan from the table, which was updated in November and says "must", and run the [VCF Upgrade Planner](https://vmware.github.io/vcf-upgrade-planner/) against your own source if a window forces a different split.

## What step 1 takes away until step 7

A 9.0.x source loses capability once VCF Operations moves. Until management services are deployed and the data has transferred, [certificate, password and lifecycle operations aren't available from VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore.html), and Automation, the identity broker, logs and networks stay out of reach for those tasks until each reaches 9.1. So renew anything that would expire inside that span before you begin, and keep steps 1 to 12 close together.

A license sync error, "Licenses could not be synchronized with vCenter instances", [clears once the license server is deployed and registered](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore/install-a-software-update.html), so don't chase it between those steps. The 4 Nov 2026 [FAQ](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs) describes the license server as deployed during the VCF Operations upgrade, and the upgrade guide gives it a step of its own. Plan for the step, since the guide is the procedure.

<Callout type="warn" title="The 9.0 fleet appliance stays off">
The VCF Operations upgrade transfers the fleet appliance's inventory, then decommissions and powers off the appliance, and [VCF Operations holds that inventory until management services are deployed](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore/install-a-software-update.html). Keep it powered off, do no upgrades with it, and delete it once the environment is on 9.1 (<KB id={440630} />). If it's left on, it keeps authenticating with an outdated `lcm-ops` password, which fails VCF Operations prechecks with HTTP 401 on a move from 9.1.0.0100 to 9.1.0.0400 (<KB id={449075} />). FAQ questions 76 and 77, on upgrading and being notified through fleet management, read as older text: <KB id={440630} /> says the appliance is no longer available in 9.1.
</Callout>

## Getting from 9.1.0.x to 9.1.1

These dependencies come from the [9.1.1 release notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes.html). Patch fleet lifecycle to 9.1.1 before any other component, and leave "Upgrade All" alone until you've met the rest.

| Before you patch | Do this first |
|---|---|
| Any other component | Fleet lifecycle to 9.1.1 |
| VCF Operations | Confirm no other lifecycle operation is running. It must not be patched in parallel with other components, and nothing else should start until it finishes. |
| ESX, 9.1.0.x to 9.1.1.0 | VCF Operations and its connected license servers |
| Identity broker | The services runtime hosting it. The precheck fails with `VCFMS-PRECHECK-VIDB-VMSP-VERSION-001` otherwise (<KB id={457245} />). |
| Salt RaaS | The services runtime hosting it |
| Migration service engine | VCF Automation |
| VCF Automation, with Data Services Manager integrated | Review the DSM upgrade guidance |

A software depot patch also blocks other patching until it finishes, so give it its own slot in the window.

These rules don't carry over to Express Patches. [TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management.html) says no patch order is enforced in general and warns that dependencies may apply for certain releases, which is why the release notes for your target need reading before every window. [William Lam's July post](https://williamlam.com/2026/07/vcf-9-1-understanding-vcf-express-patches.html) is the clearest account: Express Patches "can be applied in any order", 0100 needn't precede 0200, and the latest version of a component includes earlier fixes. If one contains fleet lifecycle, he says to consider applying it first because fleet lifecycle drives the rest, and [McDonald's walkthrough](https://blogs.vmware.com/cloud-foundation/2026/06/29/installing-express-patches-with-vmware-cloud-foundation-9-1/) starts there too, management components before core.

On 5.2 the equivalent was [async patching from the SDDC Manager UI](https://blogs.vmware.com/cloud-foundation/2024/08/19/deploying-workload-domains-with-async-patches-in-vcf-5-2/), which Eric Gray's 2024 post compares favourably with the Async Patch Tool CLI.
