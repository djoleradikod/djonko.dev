<InShort>
Upgrading 9.0 to 9.1, or 5.2 straight to 9.1, follows this sequence: upgrade VCF Operations, upgrade SDDC Manager, then run **Deploy VCF Management Services and License Server**. That step builds the services runtime, a small Kubernetes cluster of VMs, on the management network. It installs fleet lifecycle, SDDC lifecycle, the software depot, Salt and telemetry on it, deploys the License Server appliance, and imports the existing management components into fleet lifecycle. It needs addresses, lowercase DNS records, certificates with proper SANs, a healthy cloud proxy, and firewall paths from the runtime's addresses. Once it completes there is no going back to the 9.0 fleet appliance.
</InShort>

## What to have ready

**Addresses**
- A runtime pool of 12 to 30 addresses on the management network, with a /27 recommended (<KB id={440630} />).
- Separate addresses, outside the pool, for the fleet, instance and runtime FQDNs, the License Server and, if it is not already deployed, the identity broker.
- An internal pod and service range that does not clash with anything routed. The default is `198.18.0.0/15`.

**Names.** Lowercase A and PTR records for every FQDN, resolving before you start.

**Binaries.** Nine depot items must be present: services runtime, fleet lifecycle, SDDC lifecycle, software depot, identity broker, Salt RaaS, Salt master, telemetry and License Server. All of them are **INSTALL** binaries, not upgrades (<KB id={450430} />).

**Cloud proxy.** A unified cloud proxy in the first instance, with every VCF instance adapter pointed at it (<KB id={443106} />).

**Credentials.** The VCF Operations FQDN and admin login, plus a password for the runtime admin account.

**Licensing mode.** Connected mode transfers licences automatically. Disconnected mode needs a manual licence transfer after the step (<KB id={450430} />).

## Where it stops, and what it usually means

| Stage | Typical cause | KB |
|---|---|---|
| Bootstrap | The bootstrap VM cannot reach vCenter on 443, or the NSX DFW exclusion step fails | <KB id={440449} />, <KB id={448888} /> |
| Bootstrap after storage moves | A component was moved to another datastore, leaving a stale datastore ID behind | <KB id={446929} /> |
| Component import (stalls around 46%) | A firewall blocks runtime pods from reaching VCF Operations on 443 | <KB id={446831} /> |
| Register components with VCF Operations | The Operations for Logs API on 9543 hung | <KB id={452059} /> |
| Import fails right after midnight, or another fixed time | A race with the 9.0 lifecycle daily inventory sync | <KB id={452077} /> |
| Failed or duplicate components afterwards | A partial run left entries behind | <KB id={441333} /> |

The pattern behind most of them is the same. The runtime is a new set of source addresses on the network, and it needs the same reachability to vCenter, VCF Operations and the depot that SDDC Manager had. Firewall rules written for SDDC Manager don't cover it (<KB id={443216} />).

<Callout type="warn" title="Before you click Install">
Take and verify backups of VCF Operations, SDDC Manager and the 9.0 fleet appliance. This is the last point at which the 9.0 management layout can be restored.
</Callout>

## Pitfalls

- **Testing reachability from SDDC Manager only.** Test from an address in the runtime pool, or from a pod once the runtime exists, as the KBs show.
- **Treating the License Server as an afterthought.** It needs its own FQDN, IPv4 address and records. Its address must not fall in `172.17.0.0/16` on early 9.1.0 builds.
- **Moving runtime VMs afterwards.** Don't Storage vMotion them, and don't change their folder or resource pool. Later upgrades depend on their recorded placement.
