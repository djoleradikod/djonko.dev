<InShort>
Upgrading 9.0 to 9.1 follows this sequence: upgrade VCF Operations, upgrade SDDC Manager, then run **Deploy VCF Management Services and License Server**. Broadcom's page requires both at 9.1.x for that step and gives licensing follow-up for 5.2.x as well, so a straight 5.2 upgrade reaches it too. The step builds the services runtime, a small Kubernetes cluster of VMs, on the management network unless you choose another. It installs fleet lifecycle, SDDC lifecycle, the software depot, Salt and telemetry on it, deploys the License Server appliance, and imports the existing management components into fleet lifecycle. It needs addresses, lowercase DNS records, a healthy cloud proxy, and firewall paths from the runtime's addresses. Once it completes, reseller WWT's walkthrough says there is "no supported path to reverse the upgrade", and Broadcom's page describes none (checked 7 Nov 2026).
</InShort>

## What to have ready

**Addresses and size.** The runtime pool, the addresses outside it, the internal range, the network choice and the footprint of each size are in [VCF Management Services: choosing size, HA and network](/vcf/library/architecture/aria-lifecycle-to-services-runtime/).

**Names.** Five lowercase FQDNs, each with A and PTR records and resolving before you start, as [ithinkvirtual's lab write-up](https://ithinkvirtual.com/posts/vcf-9-1-upgrade-part-2-sddc-manager-management-services/) lists them. Broadcom's page bars capitals on four of the five and requires each name to resolve to a unique, unused address outside the pool.

**Binaries.** Nine depot items must be present: services runtime, fleet lifecycle, SDDC lifecycle, software depot, identity broker, Salt RaaS, Salt master, telemetry and License Server (<KB id={450430} />).

**Cloud proxy.** A healthy unified cloud proxy, with the VCF instance adapters for every workload domain and vCenter in that instance pointed at it (<KB id={443106} />).

**Credentials.** The VCF Operations FQDN and admin login, plus a password for the runtime admin account.

**Licensing mode.** Connected mode transfers licences automatically. Disconnected mode needs manual registration with the VCF business services console after the step (<KB id={450430} />).

## Where it stops, and what the KBs blame

| Stage | Cause the KB gives | KB |
|---|---|---|
| Bootstrap | A firewall blocks the bootstrap VM from vCenter on 443 | <KB id={448888} /> |
| Bootstrap, failing at the NSX firewall exclusion step | SDDC Manager cannot reach the bootstrap VM's health API on 5480 | <KB id={440449} /> |
| Bootstrap after storage moves | A component was moved to another datastore, leaving a stale datastore ID behind | <KB id={446929} /> |
| Component import (stalls around 46%) | A firewall blocks runtime pods from reaching VCF Operations on 443 | <KB id={446831} /> |
| Register components with VCF Operations | The Operations for Logs API on 9543 hung | <KB id={452059} /> |
| Deploy VCF Management Components | The VCF Operations upgrade overlapped its daily inventory sync (03:00 UTC in the KB's example), which recorded 9.1 too early. The fix is reverting to snapshots and restarting after the sync | <KB id={452077} /> |
| Retry blocked by failed or duplicate components | Duplicate imports or failed components need cleaning up first; the KB doesn't say what produces them | <KB id={441333} /> |

The firewall rows share one pattern, and this is inference from those KBs: the bootstrap VM and the runtime are new source addresses on the network. Afterwards the depot also moves onto runtime pool addresses, and Broadcom warns that "firewall rules may not be in place for this shift" (<KB id={443216} />).

<Callout type="warn" title="Before you click Install">
Take and verify backups of VCF Operations, SDDC Manager and the 9.0 fleet appliance. Broadcom's deploy page describes no way back after the step (checked 7 Nov 2026), and the recovery <KB id={452077} /> gives for a failed run starts from pre-upgrade snapshots.
</Callout>

## Pitfalls

- **Testing reachability from SDDC Manager only.** Test from an address in the runtime pool, or from a pod once the runtime exists, as the KBs show.
- **Treating the License Server as an afterthought.** It needs its own FQDN, IPv4 address and records.
- **Moving runtime VMs afterwards.** Don't Storage vMotion them, and don't change their folder or resource pool. Broadcom warns that later patching, deployment and scale-out can then fail.
