<InShort>
**Spend your pre-window session on the failures whose published fix is going backwards.** Six KBs make a snapshot revert or a support-led rollback the main way out, so check root passwords, the VCF Operations database, the daily sync time and any VM moved by hand before step 1. Then work through the stage tables below. They map what Broadcom and named practitioners have published as of 7 Nov 2026. None of it was reproduced here, and the number of articles on a stage says nothing about how often it fails <AsOf date="2026-11-07" />.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note said KB 409353 ties clock drift to hung upgrades, but that KB ties clock drift to an SSO login failure on 9.0 and doesn't mention upgrades, so it's gone. It also said the default NSX distributed load balancer must be attached to a group. <KB id={440901} /> gives an error only for the "ALL" path, and other configurations get a warning you can acknowledge.
</Callout>

## What to do with the map

Run the session a week before the window, and again the day before, because passwords and certificates age in between. Take the snapshots described in [Rollback checkpoints](/vcf/library/upgrades/rollback-checkpoints/) before step 1, since these are the articles that need them:

| What failed | Way out the article gives | KB |
|---|---|---|
| Expired root password on a VCF Operations node | Revert or restore, set the password, restart | <KB id={445418} />, <KB id={442719} /> |
| Orphaned rows in the VCF Operations database | Revert all nodes, run the KB's script, reapply. No snapshot means Support | <KB id={440200} /> |
| Daily inventory sync overlapping the upgrade | Revert VCF Operations and LCM to 9.0.x, restart | <KB id={452077} /> |
| A node rebooting during the assessment precheck | Revert, or edit the pack history by hand if you took no snapshot | <KB id={452677} /> |
| VCF Automation VMs moved to another datastore | Support-led rollback to 9.0 | <KB id={448384} /> |

Read together, the stated causes point to three habits that head off several rows at once:

- **Leave VMs where VCF put them, or list every move.** Moves between datastores or folders sit behind <KB id={446929} />, <KB id={448384} /> and scenario 5 of <KB id={441285} />. The first needs Support to edit the SDDC Manager database, so a move discovered late can cost you the window.
- **Power off the 9.0 fleet appliance and keep its DNS record.** Left on, it causes 401 errors in later prechecks (<KB id={449075} />). With the record deleted, the VCF Automation precheck can't confirm the address is unused and fails (<KB id={443874} />).
- **Replace certificates through VCF Operations, not directly on the component.** A certificate changed directly on NSX Manager leaves SDDC Manager distrusting it (<KB id={442766} />). That KB, from 3 Jun 2026, names SDDC Manager as the managed route, but the 5 Nov 2026 [blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html) says "Avoid using the SDDC Manager for certificate management", so follow the newer page.

[The route chooser](/vcf/library/upgrades/upgrade-route-chooser/) sends you to 9.1.1, which may close some of these, but the articles won't always tell you: <KB id={450225} /> names 9.1.0 in its Environment line, while <KB id={444283} /> says only "VMware Cloud Foundation 9.x". Read each article's Environment line against your source and target before acting on it. Several fixes edit a database or a pod, so take the snapshot or backup the article asks for first.

## Certificate SANs: use the strictest rule

Four Broadcom pages set the requirement, and they differ. Build one SAN list per component now, because a failure here surfaces at step 7 or later, well after the first changes.

| Component | SAN must hold | Source |
|---|---|---|
| VCF Operations | Each node's FQDN and IP address, from the KB, plus the load balancer or VIP FQDN, from the upgrade page. The page asks only for FQDNs, and the KB doesn't mention the VIP, so the list needs both. On a CSR generated before 9.1, add each node's shortname as the KB asks. [On 9.1 a shortname fails the whole CSR](/vcf/library/day-2/certificates-in-9/#getting-sans-and-replacements-right) | <KB id={453793} />, [TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore/install-a-software-update.html), 5 Nov 2026 |
| VCF Operations for networks | FQDN as a DNS entry and IP as an IP Address entry. An IP listed as a DNS entry also fails | <KB id={440459} /> |
| NSX Manager VIP | Every required FQDN and IP address | <KB id={440910} /> |

## The stage tables

Steps follow [Broadcom's order](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html) from 9.0 (updated 5 Nov 2026). From 5.2, NSX and everything after it sit one step lower, and a KB titled for the 9.0 path, such as <KB id={441285} />, may not apply. <KB id={440630} /> lists a few related issues and links out, and these tables go further. Quoted text is the source's. A cell starting "Suggested" is reasoning from the stated cause, not a published check, and it hasn't been run. An empty cell means the source gives no early check and its cause doesn't suggest one. Dates are each page's last modification.

### Steps 8 and 9: Identity Broker and VCF Automation

The VCF Automation prechecks run in five groups, from connectivity to application, per [Mohammed Aakhil's post](https://blogs.vmware.com/cloud-foundation/2026/07/27/modernizing-infrastructure-a-deep-dive-into-the-vmware-cloud-foundation-automation-9-0-to-9-1-upgrade-precheck-and-execution-stages/) (27 Jul 2026), which lists what to confirm beforehand: node readiness, DNS for allocated IPs and those IPs being unused. <KB id={441285} /> also offers a fallback: skip Identity Broker to finish the upgrade, and it stays on 9.0.x without the 9.1 features.

| Symptom | Spot it before the window | What clears it | Source |
|---|---|---|---|
| Identity Broker: "Errors occurred during running prechecks" | Compare its network with the management services runtime network | Redeploy to a supported network and datastore, the route chooser's Identity Broker blocker | <KB id={441285} />, 30 Jun 2026 |
| "Step vmsp_upgrade_vidb failed" at Power Off Source Cluster | Check for hand-moved VMs and leftovers of an earlier broker | KB 442400 for moved VMs, KB 444724 for leftover records | <KB id={441285} />, 30 Jun 2026 |
| "The source system is not a VCF Automation (VCFA) 9.x product" | Suggested: log in to each node as `vmware-system-user` | Reset the password on every node (KB 419010), rerun | <KB id={443988} />, 25 Jun 2026 |
| Prechecks "fail due to a certificate chain validation failure" | `tls.crt` of `vmsp-tls` in `istio-ingress` holds leaf, intermediate and root | Patch the secret with the full chain | <KB id={441974} />, 29 May 2026 |
| `VCFMS-HEALTH-002` with "no such host" on the powered-off Fleet Manager name | That name resolves, and its IP doesn't answer ping | Recreate the record, on an unused IP if the old one is taken | <KB id={443874} />, 10 Jun 2026 |
| `VCFMS-HEALTH-002` with "logging-operator-fluentd" | `logging-operator-fluentd` pods show 2/2 Ready | Purge buffers and delete the pod. This discards unsent logs. Broadcom plans to remove the check | <KB id={449659} />, 7 Sep 2026 |
| "Target VSP cluster IP pool CIDR is required" | Have a contiguous /29, or apply the bundles in the fix | Fleet Lifecycle and SDDC Lifecycle to 9.1.0.0400, then Services Runtime to 9.1.0.0200, then enter IPs one by one | <KB id={448617} />, 6 Aug 2026 |
| "Step vmsp_run_vcfa_prechecks failed", task queued behind backups | Is the incremental backup set to every 15 minutes? | Move it to every 4 hours, retry | <KB id={456790} />, 29 Sep 2026 |
| "Ready for upgrade pre checks failed" on single-node VCF Automation | `kubectl -n vmsp-platform get pods`: more than 300 `cluster-info-dump` pods, or `OutOfPods` | Back up, then KB 450243 | <KB id={450225} />, 18 Aug 2026 |

Silencing a health alarm is the KB's route through <KB id={444283} />, but it carries a hardware fault into the upgrade. Clear NVMe and SCSI controller faults before the window instead, so you never have to choose that during it. The KB doesn't state this, but it follows from its instruction to repair the hardware afterwards. Lam's Edge check is written for 9.0.2 only. Run it anyway on a 9.1 path, because it takes two read-only commands per Edge.

### Patching 9.1.0.x to 9.1.1

## Before you close the session

Run Broadcom's readiness set from <KB id={454898} /> (3 Nov 2026): the SoS health check on SDDC Manager, the diagnostic tool on each vCenter, and the runtime health and service account check from 9.0 on. Build the ordered plan in the Upgrade Planner, as the [route chooser](/vcf/library/upgrades/upgrade-route-chooser/) describes, and keep the checks you can script in [Scripted health checks](/vcf/library/labs/scripted-health-checks/). Put each revert decision and its deadline in [Go or no-go](/vcf/library/leadership/go-no-go-and-rollback/) rather than deciding during the window.
