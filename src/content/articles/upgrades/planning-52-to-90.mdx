<InShort>
Upgrades to 9.1.x are supported from **5.2.x** and **9.0.x**. Anything older goes to 5.2 first. VCF checks the path, and the target must be released *after* the build you run. That rule blocks some combinations that look reasonable, such as 5.2.4 to 9.1.0. The order is now top-down: VCF Operations and the management components first, then SDDC Manager, then each domain's NSX, vCenter and ESX. Plan the preparation around what 9.x adds: VCF Operations, fleet management or the services runtime, a License Server, new IP addresses and FQDNs, stricter certificates, and vLCM images on every cluster.
</InShort>

## Step 1: choose a path the product will accept

- **Check the exact build pair** in the Interop Matrix Upgrade view, with *Hide Patch Releases* unticked, or you will not see the pairs that matter.
- **Watch for back-in-time blocks.** 5.2.4 (27 May 2026) was released after 9.1.0, so 5.2.4 to 9.1.0 is blocked (<KB id={450972} />). The KB says support is targeted for a future 9.1.x patch and names none. The 9.1.1 release notes (3 Sep 2026) allow a direct upgrade from a 5.2.x build released before 9.1.1, which by date covers 5.2.4, so confirm that pair in the matrix. Component builds can trigger the same block, for example an NSX patch newer than the target (<KB id={446313} />, <KB id={430825} />).
- **Prefer the latest target.** The 9.1.1 release notes ask you to use the latest available binaries, and from 5.2.x or 9.0.x you can go straight to 9.1.1.
- **Use the planner.** The VCF Upgrade Planner, covered in William Lam's posts, produces a per-environment runbook, and its October 2026 update exports plans for change boards.

Workload domains are Day-N. They can follow their instance's management domain in later windows.

## Step 3: prepare what 9.x adds

Give each item an owner and a date:

- **IP addresses and DNS.** You need records for VCF Operations, fleet management, the cloud proxy and, for 9.1, the runtime pool of <a href="https://williamlam.com/2026/05/vcf-9-1-additional-ip-allocation-options-for-vcf-management-services-vcfms-in-vcf-installer-and-sddc-manager.html" target="_blank" rel="noopener">12 to 30 addresses</a>, fleet, instance and runtime FQDNs, the License Server and the identity broker. <a href="https://blogs.vmware.com/cloud-foundation/2026/07/28/modernizing-infrastructure-vmware-cloud-foundation-9-0-x-to-9-1-upgrade-guide/" target="_blank" rel="noopener">Broadcom's 9.0 to 9.1 guide</a> asks for forward and reverse records, in lowercase.
- **Certificates.** SANs must list every node FQDN, and in some cases IP addresses too. See <a href="/vcf/library/upgrades/prechecks-that-fail/">the prechecks note</a>.
- **vLCM images.** Convert every baseline cluster, and build images that include the vendor add-ons.
- **Products with no upgrade.** Plan a new identity broker, a new log platform and, if you run VCD, the supported migration to VCF Automation 9.1, which needs VCD 10.6.2 and the Environment Assessment Tool (<a href="https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs" target="_blank" rel="noopener">FAQ Q44</a>). See <a href="/vcf/library/upgrades/vcf-automation-side-by-side/">which route applies</a>.
- **Binaries and depot access.** Plan for the 9.1 activation code from the VCF Business Services console. For a site without internet access, Broadcom documents the VCF Download Tool as the only supported method.

## Step 4: treat every phase as a checkpoint

<a href="https://blogs.vmware.com/cloud-foundation/2025/12/18/upgrading-vmware-cloud-foundation-5-2-to-9-0-the-top-10-questions-answered/" target="_blank" rel="noopener">Broadcom's December 2025 post</a> says there is no "easy button" rollback for all of VCF and treats each upgrade step as a checkpoint. Back up each component before its step. This matters most immediately before deploying 9.1 management services. <a href="https://www.wwt.com/blog/before-you-upgrade-to-vcf-91-what-you-need-to-have-ready" target="_blank" rel="noopener">WWT's July 2026 post</a>, written by a third party about the 9.0 to 9.1 upgrade, says there is no supported rollback once they are deployed. See <a href="/vcf/library/upgrades/rollback-checkpoints/">Rollback in practice</a>.

<Callout type="analysis" title="This site's advice">
Give the plan three columns per step: the action, the evidence that it worked (a screenshot, a health check or a task ID), and the rollback point if it didn't. Writing the evidence column first catches missing prerequisites while there is still time to fix them.
</Callout>

## Pitfalls

- **Choosing the target by version number alone.** Check release dates and patch builds too, because the path validation does.
- **Upgrading Aria Operations for Logs.** There is no upgrade path. On 9.0, deploy the log platform new, reconfigure the integrations, and keep the old one for history (<KB id={402314} />). On 9.1 there is no separate log appliance: add log management as a Day-N task and migrate the logs through VCF Operations (<KB id={440630} />).
- **Leaving workload domain planning until later.** Mixed versions are a transition state with limits. See <a href="/vcf/library/upgrades/mixed-versions/">Running mixed versions</a>.
