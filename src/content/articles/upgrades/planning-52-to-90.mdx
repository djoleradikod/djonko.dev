<InShort>
Upgrades to 9.1.x are supported from **5.2.x** and **9.0.x**. Anything older goes to 5.2 first. VCF checks the path, and the target must be released *after* the build you run. That rule blocks some combinations that look reasonable, such as 5.2.4 to 9.1.0. The order is now top-down: VCF Operations and the management components first, then SDDC Manager, then each domain's NSX, vCenter and ESX. Most of the effort goes into preparing what 9.x adds: VCF Operations, fleet management or the services runtime, a License Server, new IP addresses and FQDNs, stricter certificates, and vLCM images on every cluster.
</InShort>

## Step 1: choose a path the product will accept

- **Check the exact build pair** in the Interop Matrix Upgrade view, with *Hide Patch Releases* unticked, or you will not see the pairs that matter.
- **Watch for back-in-time blocks.** 5.2.4 was released after 9.1.0, so 5.2.4 to 9.1.0 is blocked. Go to 9.1.1 instead (<KB id={450972} />). Component builds can trigger the same block, for example an NSX patch newer than the target (<KB id={446313} />, <KB id={430825} />).
- **Prefer the latest target.** Every 9.x release note asks you to use the latest available binaries. From 5.2.x or 9.0.x you can go straight to 9.1.1.
- **Use the planner.** William Lam's VCF Upgrade Planner produces a per-environment runbook, and its October 2026 release exports plans for change boards.

Workload domains are Day-N. They can follow their instance's management domain in later windows.

## Step 3: prepare what 9.x adds

This is where most projects slip. Give each item an owner and a date:

- **IP addresses and DNS.** You need records for VCF Operations, fleet management, the cloud proxy and, for 9.1, the runtime pool of 12 to 30 addresses, fleet, instance and runtime FQDNs, the License Server and the identity broker. Every record needs forward and reverse entries, in lowercase.
- **Certificates.** SANs must list every node FQDN, and in some cases IP addresses too. See <a href="/vcf/library/upgrades/prechecks-that-fail/">The prechecks that fail most often</a>.
- **vLCM images.** Convert every baseline cluster, and build images that include the vendor add-ons.
- **Products with no upgrade.** Plan a new identity broker, a new log platform and, if you run VCD, a separate conversation with the account team.
- **Binaries and depot access.** Plan for the 9.1 activation code, or a VCF Download Tool workflow for dark sites.

## Step 4: treat every phase as a checkpoint

There is no single rollback for VCF. Each component is backed up before its step, and each step is a point you can return to. This matters most just before deploying 9.1 management services, which cannot be undone. See <a href="/vcf/library/upgrades/rollback-checkpoints/">Rollback in practice</a>.

<Callout type="field">
The plan that survives contact with the customer has three columns per step: the action, the evidence that it worked (a screenshot, a health check or a task ID), and the rollback point if it didn't. Writing the evidence column first catches missing prerequisites while there is still time to fix them.
</Callout>

## Pitfalls

- **Choosing the target by version number alone.** Check release dates and patch builds. The path validation will.
- **Upgrading Aria Operations for Logs.** There is no upgrade. Deploy the 9.x log platform new, reconfigure the integrations, and keep the old one for history (<KB id={402314} />).
- **Leaving workload domain planning until later.** Mixed versions are a transition state with limits. See <a href="/vcf/library/upgrades/mixed-versions/">Running mixed versions</a>.
