<InShort>
Broadcom's own answer is that there is no single rollback for VCF. Each serial step is a checkpoint. You back up the component before it is upgraded, and if the step fails, you return that component to its pre-step state. 9.x keeps that model and adds two hard edges. Once 9.1 management services are deployed, the 9.0 fleet appliance cannot be reinstated. VCF Automation's old nodes are only powered off, not upgraded, so they are a fallback only until you delete them. Most failed steps don't need a rollback at all. They need the right *retry*, at the right level.
</InShort>

## Checkpoints per component

| Component | Before the step | Way back |
|---|---|---|
| VCF Operations | Take the cluster offline, snapshot every node, bring it back online, then install (<KB id={450430} />) | Revert all node snapshots together |
| SDDC Manager | SFTP file backup confirmed, plus a VM snapshot | Revert the snapshot, or restore from backup |
| vCenter | File-based backup | RDU: cancel before switchover (<KB id={454467} />). In place: restore from backup. |
| NSX | NSX backup confirmed | Restore is a support-led process. Prevent rather than cure. |
| ESX | Hosts healthy, image validated | Failed hosts don't block the others. Remediate them in a new batch. |
| Management services (9.1) | Backups of everything above, plus the 9.0 fleet appliance | None after deployment |
| VCF Automation (9.0 to 9.1) | Healthy 9.0 cluster and backups | The old nodes, powered off, until you delete them |

Delete snapshots when each checkpoint is confirmed good. Long-lived snapshots on management appliances cause problems of their own.

## Retry before rollback

Most 9.x failures are recoverable in place, as long as you choose the right level:

- **Fix the cause, then use Retry Task.** Lifecycle tasks resume at the failed step. In 9.1 the underlying task has a retryable flag. When it is false, a reset is needed, and that is a support action (<KB id={451010} />).
- **"Stuck" isn't always stuck.** If the work finished but the status didn't update, restarting the fleet and SDDC build and upgrade pods clears it (<KB id={443718} />).
- **Version drift after manual actions** is fixed with a version sync on SDDC Manager, not a re-upgrade (<KB id={440807} />).
- **Stale plans and locks** can be cleared through documented API calls or database edits, after a snapshot (<KB id={444168} />, <KB id={449148} />).
- **RDU keeps failing?** Fall back to a standard in-place vCenter upgrade (<KB id={442134} />, <KB id={446672} />).

Revert to a checkpoint when the KB says so, for example after an expired root password (<KB id={445418} />), an interrupted precheck (<KB id={452677} />) or an inventory sync race (<KB id={452077} />), or when the window is closing and the fix is unknown.

<Callout type="field">
Agree the "go back" criteria with the customer before the window. For example: "If SDDC Manager is not upgraded by 02:00, we revert the snapshot and stop." Making that decision at 02:00 under pressure is how windows overrun into business hours.
</Callout>

## Pitfalls

- **Snapshots as backups.** A snapshot is a checkpoint for minutes or hours, not a backup.
- **Running database fixes from a KB without a snapshot.** Every KB that edits a database says to snapshot first, for good reason.
- **Retrying the whole upgrade.** Retry the failed step. Re-running an earlier step on a partly upgraded system creates new problems.
