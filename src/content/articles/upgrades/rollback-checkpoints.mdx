<InShort>
Broadcom documents no whole-platform rollback, so the plan needs one line per component. **VCF Operations:** snapshot every node and cloud proxy with the cluster offline. Reverting those snapshots after a failed upgrade is documented, so "never revert" was wrong. **NSX:** file backup only, because VM snapshots on NSX Managers and Edges are unsupported. **Management services:** no Broadcom page opened for this note gives a way back after they are deployed. **VCF Automation:** one KB gives a rollback for one failure, and only through support (<KB id={448384} />). Plan to fix forward with support for both. **VDS and vSAN on-disk format:** one-way, and both sit near the end of Broadcom's order.
</InShort>

<Callout type="note" title="Corrected on 6 November 2026">
This note called NSX restore support-led, but TechDocs publishes the procedure. It also presented VCF Automation's old nodes as a fallback and the fleet appliance limit as Broadcom's: no page opened documents the first, and the second is WWT's wording.
</Callout>

## The table for your plan

**Documented** means a Broadcom page opened on 6 November 2026 describes that way back. **Reasoned** means it is this site's inference, so get it confirmed in your Broadcom pre-upgrade review before relying on it. Rows follow the order in [Upgrading to VCF 9.1.x](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html), leaving out components this note doesn't cover. Two rows merge steps: Identity Broker comes just before VCF Automation with the other two just after it, and NSX Edges come after ESX. <AsOf date="2026-11-06" />

| Component | Checkpoint and how | Way back | Fallback if a step fails |
|---|---|---|---|
| Fleet management appliance (from 9.0.x) | Reasoned: VM snapshot before the VCF Operations upgrade. TechDocs lists no snapshot for it. | **Documented** for one failure: revert the environment "including VCF Ops and LCM" (<KB id={452077} />). This note reads LCM as this appliance. | Keep the powered-off VM. It is decommissioned after the inventory transfer and [deleting it is manual](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore/install-a-software-update.html). Delete it after the fleet is on 9.1 (<KB id={440630} />). |
| VCF Operations cluster | Cluster offline in the admin UI, memoryless unquiesced snapshot of each node, back online before installing ([TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore/create-a-snapshot.html)). Image-based backup too. | **Documented:** revert all VMs, power on, bring online (<KB id={402329} />, <KB id={445418} />, <KB id={452677} />). | If the cluster drops offline during the PAK install, take it online and use [Finish Installation](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore/install-a-software-update.html). Otherwise revert, or restore the image backup. |
| Cloud proxies | Same offline snapshot (<KB id={342576} />). The TechDocs snapshot page doesn't mention proxies. | **Documented:** reverted with the cluster (<KB id={402329} />). | A failed automatic proxy upgrade is [fixed with the CLI](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-backup-and-restore.html). |
| SDDC Manager | SFTP file backup plus a snapshot ([TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/apply-cloud-foundation-5-2-update-bundle.html)). Make it cold, as the [core prerequisites](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-the-management-domain-to-vmware-cloud-foundation-5-2/upgrade-prequisites.html) specify. | **Reasoned** for the snapshot: TechDocs requires one and gives no revert steps. **Documented** for the backup: [new appliance from OVA, then restore](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/restoring-vmware-cloud-foundation/file-based-restore-for-sddc-manager-vcenter-server-and-nsx-t-data-center/vcf-52-restore-sddc-manager/restore-sddc-manager-from-a-file-based-backup.html). | Retry, then revert the snapshot if the step never completed. |
| VCF management services | Fresh backups, with the snapshots from the rows above still in place. | **Reasoned:** none once deployed. WWT states [no supported path](https://www.wwt.com/blog/the-vcf-91-upgrade-step-by-step-what-actually-happens); TechDocs doesn't address it. <KB id={452077} /> does revert when the "Deploy VCF Management Components" step fails. | Fix forward with support. A later failed state has a [redeploy procedure](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/-vmware-cloud-foundation-instance-recovery/recovery-task-library/vcf-management-services-restore-tasks/redeploy-and-restore-vcf-management-services-components.html) needing a recent backup. |
| VCF Automation (9.0 to 9.1) | [File-based backup](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation.html). The workflow also [starts a full source backup](https://blogs.vmware.com/cloud-foundation/2026/07/27/modernizing-infrastructure-a-deep-dive-into-the-vmware-cloud-foundation-automation-9-0-to-9-1-upgrade-precheck-and-execution-stages/). | **Documented** for one failure, through support only: a failure at "Power Off Source Cluster" from a datastore path mismatch rolls back to 9.0, and the KB says this isn't a standalone user task (<KB id={448384} />). Otherwise none documented. Blue-green: old nodes [shut down automatically](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/phase-3-import-and-upgrade-aria-automation-8-to-vcf-automation-9.html) and their IPs are freed. | Keep the old nodes until validated. Ask support before powering them on, because those IPs may be reused. |
| Identity Broker, Operations for networks, Log Management | [Backup method per component](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation.html): networks image-based, the others file-based. | NSX Manager and Edges | Manual file backup, confirmed on the SFTP target. **No VM snapshots** (<KB id={433822} />). The KB doesn't detail Edge rollback; TechDocs lists a separate Edge restore topic. | Retry. Version drift after a manual NSX upgrade is fixed with a version sync (<KB id={440807} />). |
| vCenter | File-based or image-based backup. RDU creates a new VM at a newer hardware version, 17 instead of 10, and hardware upgrades [can't be reversed](https://blogs.vmware.com/cloud-foundation/2026/05/12/vcenter-virtual-hardware-upgrade/). | **Documented:** RDU cancel before switchover (<KB id={313288} />, written for 8.0), source recovery after it (<KB id={311902} />, lists 9.1). In place: [new appliance, restore](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/backup-and-restore-of-cloud-foundation/restoring-vmware-cloud-foundation/file-based-restore-for-sddc-manager-vcenter-server-and-nsx-t-data-center/restore-vcenter-server/restore-the-management-domain-vcenter-server.html) using the failed version's ISO. | From 9.0.x, if RDU fails at preparation on a certificate download, fix the source's proxy settings. It comes near the end of the order, so hold it until the hosts have run on 9.1 for a while. |

## VCF Operations: three situations the old notes blurred

| Situation | Status | Plan |
|---|---|---|
| Planned offline snapshot before an upgrade | Documented in TechDocs, <KB id={450430} /> and <KB id={342576} /> | Take it on the widest scope below. |
| Revert after a failed upgrade | Documented. <KB id={445418} /> (expired root password) and <KB id={452677} /> (interrupted precheck) both say revert. | Collect a full support bundle first if support will be involved, then revert all VMs. |
| Revert after some other failed change, such as a disk expansion | Reasoned. No article found prohibits or endorses it. <KB id={436047} /> reports one such case going badly. | Only with a full offline set including proxies, and ask support first if you don't have one. |

The old "never revert" line came from <KB id={436047} />. It covers one environment, where a revert after a failed disk expansion was followed by a vCenter adapter duplicating thousands of times. Broadcom says the exact cause wasn't determined, and notes the proxies had no backups or snapshots. Its fix was a full restore from an older backup, and it doesn't advise against reverting.

Sources disagree on what to snapshot. <KB id={450430} /> says "all primary nodes", TechDocs says each node in the cluster, and <KB id={342576} /> says all nodes "including Cloud Proxies". Use the last. <KB id={402329} /> reverts the proxies too, and that needs a snapshot to exist. That KB lists Aria Operations as its environment and names no version, so <KB id={342576} /> (which lists VCF Operations 9.x) and the 9.1 failure KBs are what carry it forward.

Two limits go in the plan:

- **72 hours.** <KB id={342576} /> says snapshots older than that cause performance issues, and TechDocs says to delete them after the upgrade. Delete too soon and you lose the way back for the next phase, so write the removal time down per phase.
- **SSO after a revert.** <KB id={342576} /> rates the risk of breaking the VCF SSO integration high on 9.0.x and slight on 9.1 and newer.

<Callout type="analysis">
This is inference: a failed 9.0.x to 9.1 upgrade reverts to 9.0.x, and the KB doesn't say whether the source or target version sets the risk. Plan for the high figure. <KB id={429013} /> restores the link by rotating the client secret, or by unjoining and rejoining if you can give up existing role assignments, so allow time for it.
</Callout>

## Retry before reverting

Each of these is one KB's specific failure, so match the symptom before using it.

- **Log Management, Salt master or other VSP component failed but shows the new version:** apply the KB's task patch, then check the retryable flag. When it is false, contact support (<KB id={451010} />).
- **Log Management stuck at "Install VCF services runtime":** deleting the fleet and SDDC build and upgrade pods clears it (<KB id={443718} />).
- **vCenter and NSX upgrade option greyed out by stale target version metadata:** delete the stale domain release entry through the SDDC Manager API (<KB id={444168} />).
- **Switchover blocked by a lock:** delete the lock row, with an SDDC Manager snapshot first, as the KB requires (<KB id={449148} />).
- **Daily inventory sync collided with the upgrade:** this one has no retry. Revert to the 9.0.x snapshots and start again at least 10 minutes after the sync (<KB id={452077} />).

From 5.2 the [vCenter upgrade must be RDU](https://blogs.vmware.com/cloud-foundation/2026/06/18/how-to-upgrade-to-vmware-cloud-foundation-9-1/), so don't write in-place as your fallback on that path. <KB id={446672} /> does mention a standard upgrade, for vCenter 8.0 to 9.0, so ask support if you need it. In the optimized window, NSX Manager [is upgraded before switchover](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/what-s-new/whats-new-vcf-ops.html). Cancelling the vCenter upgrade at that point doesn't undo NSX, by this site's reading.
