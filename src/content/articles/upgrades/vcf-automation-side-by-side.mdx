<InShort>
Choose by what you run today. **VCD:** Broadcom now documents a tool-assisted migration with VCF Automation 9.1 as the target. It needs VCD 10.6.2 and the Environment Assessment Tool, and the guide comes by email. **Aria Automation 8.18.1 or later:** import it into VCF Operations and let the upgrade build a new cluster. Your environment becomes a VM Apps organization. **Neither:** deploy new, after the platform upgrade if you like, and start on All Apps. **Both VCD and Aria Automation:** no public page covers this, so raise it with Broadcom before you design anything.
</InShort>

<Callout type="note" title="Corrected on 6 November 2026">
Earlier versions of this note said VCD had no official path. [FAQ Q44](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs) now calls it "a supported, documented, and UI-based tool-assisted path".
</Callout>

## Pick your route

| You run today | Route | Where you land | First gate |
|---|---|---|---|
| VCD 10.6.x | Migration Tool in VCF Automation 9.1 | Not stated publicly. The sources point to All Apps (see below). | Run the assessment tool and upgrade to VCD 10.6.2 |
| VCD 10.4 or 10.5 | The same, after reaching 10.6.x | The same | [The release notes](https://techdocs.broadcom.com/us/en/vmware-cis/cloud-director/vmware-cloud-director/10-6/release-notes/vmware-cloud-director-1062-release-notes.html) list upgrades to 10.6.2 only from 10.6.x |
| Aria Automation 8.18.1 or later | Import, then side-by-side upgrade straight to 9.1 | [VM Apps organization](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/vcf-automation-deployment-models-9-x/multi-tenancy-design-patterns/shared-tenancy-design.html), first in the new instance | Import into VCF Operations, new addresses and FQDN |
| VCF Automation 9.0.x | Side-by-side upgrade to 9.1 | Your existing organizations | New addresses and FQDN, consistent credentials |
| Neither product | New deployment, in the VCF Installer or as a Day-N operation | [All Apps, Broadcom's recommendation for greenfield](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/vcf-automation-deployment-models-9-x/multi-tenancy-design-patterns/shared-tenancy-design.html) | Supervisors, plus a services runtime with five addresses and its own FQDN |
| VCD and Aria Automation together | Undocumented in public | Unknown | See "What would change the answer" |

Two dates frame the plan. [KB 456708](https://knowledge.broadcom.com/external/article/456708) lists end of service for VCF 5.2.x, vCenter 8.x, NSX 4.x and Aria Automation 8.18.x on 11 October 2027, and for VCD 10.6.2 on 12 August 2028. After those dates it promises no technical support and no new patches. <AsOf date="2026-11-06" />

<Callout type="analysis" title="This site's reading: the VCD date buys time only on 9.1">
VCD 10.6.2 outlives VCF 5.2.x by 10 months, and its release notes say it supports VCF 9.1.1 with vSphere 9.1.1 and NSX 9.1.1. So the platform and the tenant move can be two projects: bring the infrastructure under VCD to 9.1.1 by October 2027, then finish moving tenants by August 2028. Check the Interoperability Matrix for your exact builds before you rely on this, because this is inference from those two pages and no Broadcom page sets out that plan. Aria Automation has no such margin, since 8.18.x ends with VCF 5.2.x.
</Callout>

## Route 1: from VCD

### What Broadcom documents

- **Three steps.** [The 2 September post](https://blogs.vmware.com/cloudprovider/2026/09/announcing-vmware-cloud-director-10-6-2-enabling-your-migration-to-vmware-cloud-foundation-9-1.html) lists them: run the assessment tool, request the 10.6.2 migration documentation, connect the Migration Service to VCD. [KB 455238](https://knowledge.broadcom.com/external/article/455238/vmware-cloud-director-migration-option-t.html) adds that the tool is required and that you upgrade to 10.6.2 before the transition.
- **The assessment tool.** It [runs on VCD 10.4, 10.5 and 10.6](https://blogs.vmware.com/cloudprovider/2025/06/eat-the-vmware-cloud-director-environment-assessment-tool.html) from a cell, collects structural metadata and writes an Excel report you can edit before sending. Nothing uploads automatically. The 2 September post says to resubmit if your last submission is more than six months old.
- **The upgrade.** Into 10.6.2 from 10.6.0 or 10.6.1, including their patch releases (the post leaves out the first 10.6.0 patch; the release notes include it).
- **The migration UI.** Providers work in VCF Services, Migration Tool, Migrate, and [run an evaluation](https://techdocs.broadcom.com/us/en/vmware-security-load-balancing/vdefend/vdefend-firewall/9-1/edge-gateway-firewall-migration/auditing-and-remediation-workflow.html) for infrastructure, organization or workload.
- **HCX.** [KB 442369](https://knowledge.broadcom.com/external/article/442369/vmware-cloud-director-106x-and-hcx-9x-co.html) says HCX 9.x has no direct VCD integration. To reach VCF Automation 9.1 with it, install HCX 9.1 at both ends, register it to the vCenter 8.x under VCD, and move VMs to a Namespace over the vCenter-to-vCenter connection.

The guide itself comes only by email, and this note uses public pages only, so it says nothing about the guide's contents.

### What to check before you commit to a date

| Check | What Broadcom says | What to do first |
|---|---|---|

| VCD Availability, vRealize Orchestrator | Supported, per the post | Confirm your versions in the matrix |

| Edge gateway firewall | [One unsupported rule](https://techdocs.broadcom.com/us/en/vmware-security-load-balancing/vdefend/vdefend-firewall/9-1/edge-gateway-firewall-migration.html) rejects or skips the whole gateway's firewall migration | Audit for IPv6, non-L4 protocols, context profiles and user-defined services. | VCD 10.6.2 upgrade failures | [Known issues](https://techdocs.broadcom.com/us/en/vmware-cis/cloud-director/vmware-cloud-director/10-6/release-notes/vmware-cloud-director-1062-release-notes.html): PostgreSQL certificate without the database IP in its SAN, FIPS mode on, upgrade from the Broadcom repository, duplicate key on `pk_api_externalservice` | Fix the certificate, deactivate FIPS for the upgrade and use an update package. | Any VCD cloud account in Aria Automation | [No longer supported](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes/product-support-notes-vcf-automation.html) from 9.0 | Remove the dependency before upgrading Aria Automation |

### Where tenants land

<Callout type="analysis" title="Inference: expect All Apps">
No public page states the mapping. The firewall page migrates gateway rules to Transit Gateway firewall policies, KB 442369 names a Namespace as the HCX target, and the [All Apps design page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/vcf-automation-deployment-models-9-x/organization-consumption-model/understanding-vcf-automation-all-apps-organization-multi-tenancy-model.html) ties Namespaces to All Apps organizations on Supervisors. So plan for Supervisors and VPC networking at the target, and confirm against the guide. If it says otherwise, this section is wrong and the target sizing changes.
</Callout>

### An order to work from

Broadcom publishes the three steps above. The sequence below is this site's own, built around them, and each linked item is the documented part.

1. **Inventory.** Extensions, management packs, HCX use, and firewall rules against the list above.
2. **Run the assessment tool now,** on whatever 10.4 to 10.6 build you have. It counts your organizations, VDCs, networks and edge gateways, which the plan needs anyway.
3. **Replace VCD monitoring,** then [upgrade VCD to 10.6.2](https://knowledge.broadcom.com/external/article/455238/vmware-cloud-director-migration-option-t.html). Re-run the assessment tool, because the report records the system version.
4. **Request the guide** by email, [once the assessment is done](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs). Read it before the next step: the steps below may change once you have.
5. **Upgrade the platform** to VCF 9.1.1, in [the published order](/vcf/library/upgrades/planning-52-to-90/). The release notes name 9.1.1 as what 10.6.2 supports, so don't stop at 9.1.0 with VCD still running on it.
6. **Stand up the target:** VCF Automation 9.1 and, under the All Apps reading, Supervisors.
7. **Clean up in VCD, then evaluate.** [Fix rules in VCD and regenerate the plan](https://techdocs.broadcom.com/us/en/vmware-security-load-balancing/vdefend/vdefend-firewall/9-1/edge-gateway-firewall-migration/auditing-and-remediation-workflow.html) until each gateway module reads Completed, with none Skipped or Rejected.
8. **Migrate.** The public firewall page fixes only part of the order: [provider and organization infrastructure first, then IPSets to Network Security Groups, then firewall rules](https://techdocs.broadcom.com/us/en/vmware-security-load-balancing/vdefend/vdefend-firewall/9-1/edge-gateway-firewall-migration.html). The rest belongs to the guide.
9. **Retire VCD** before 12 August 2028.

## Route 2: from Aria Automation

### What Broadcom documents

The [9.1 upgrade guide](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/phase-3-import-and-upgrade-aria-automation-8-to-vcf-automation-9.html) offers two entries: import 8.x and upgrade to 9.1, or upgrade 9.0.x directly. [8.18.1 is the minimum](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/phase-3-import-and-upgrade-aria-automation-8-to-vcf-automation-9/upgrade-to-vcf-automation.html), so 9.0 isn't a required stop. It is a blue-green build: a new cluster on its own services runtime, data moved across, traffic switched, source nodes shut down.

- **Position in the upgrade.** In the [5.2.x sequence](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html) Aria Automation is step 9, after SDDC Manager, management services and the License Server, and ahead of NSX, vCenter and ESX.
- **Downtime.** For 8.18.1, [Broadcom's deep dive](https://blogs.vmware.com/cloud-foundation/2026/07/27/modernizing-infrastructure-vmware-aria-automation-8-18-1-to-vmware-cloud-foundation-automation-9-1-upgrade-technical-deep-dive/) says downtime starts at stage 9 of 16, when the source powers off. It calls the pre-upgrade snapshots the rollback point. The upgrade guide says the old nodes are shut down and you can delete them once they're no longer needed.
- **Addresses.** For targets 9.1.0.0 to 9.1.0.300, a dedicated CIDR, with /29 as Broadcom's example: eight addresses, of which VCF Automation needs five (three for nodes, two as a lifecycle buffer). From 9.1.0.400, five unique addresses that need not be contiguous. The runtime can't share the management services CIDR or FQDN.
- **FQDN.** One new lowercase runtime FQDN, resolving outside the node addresses. The existing FQDN carries over. From 8.18.x the old node addresses become VIPs. From 9.0.x they are freed.
- **Passwords.** At least 15 characters with upper case, lower case, a digit and one of `@ ! # $ % ? ^`, with no dictionary words or parts of the username.
- **Certificates.** SANs must cover the FQDNs and IPs of all nodes and the load balancer or VIP.
- **Binaries.** From 8.18.x, the 9.1.x install binaries for VCF Automation and the migration service engine. From 9.0.x, the upgrade binary for VCF Automation and the engine's install binary.
- **Topology and placement.** Scale a single extra-large 8.18.x node to three nodes first. If the instance isn't on the primary datastore, upgrading to 9.1.1.0200 or later needs fleet lifecycle, SDDC lifecycle and SDDC Manager at 9.1.1.0200 or later.
- **Sizing.** Medium stays Medium, Extra Large becomes Large.
- **Identity.** Aria Suite Lifecycle stops managing VCF Automation but keeps managing VMware Identity Manager, so keep both. [Move authentication to the Identity Broker](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/phase-3-import-and-upgrade-aria-automation-8-to-vcf-automation-9/migrate-vcf-automation-single-sign-on-configuration-from-vmware-identity-manager-to-vcf-identity-broker.html) after the upgrade. Only when that is complete are they no longer needed for VCF Automation.
- **Several instances.** [FAQ Q45](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs): all can upgrade, but only one can be fully integrated with VCF Operations. You upgrade and patch the others individually.

The [9.0 to 9.1 stages](https://blogs.vmware.com/cloud-foundation/2026/07/27/modernizing-infrastructure-a-deep-dive-into-the-vmware-cloud-foundation-automation-9-0-to-9-1-upgrade-precheck-and-execution-stages/) are initialization and staging, create the cluster, discover it, component upgrade (backup, shut down source services, final transfer, restore, power off the old nodes, finalize Postgres), install back-end services including the VCD migrator, then inventory sync and clean-up. Prechecks run in dependency order: connectivity, source validation, health, topology, application. Start troubleshooting at the first group that fails.

### What to decide

**Do you need All Apps?** The upgrade gives you VM Apps. [KB 409610](https://knowledge.broadcom.com/external/article/409610), scoped to 9.0, says there is no supported path from Classic and VM Apps to All Apps, and that an identity broker instance using All Apps must be a greenfield setup. For 9.1, the [design page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/vcf-automation-deployment-models-9-x/multi-tenancy-design-patterns/shared-tenancy-design.html) describes running both side by side and adopting All Apps progressively.

<Callout type="analysis" title="This site's advice">
Upgrade into VM Apps and treat All Apps as a separate build, so content moves by being rebuilt on your schedule. Leave tenancy redesign out of the upgrade. Allan Kjaer's [April post](https://www.virtual-allan.com/when-legacy-multi-tenancy-meets-vcf-automation-why-cloud-accounts-fail-after-migration/), a practitioner's account, argues some legacy multi-tenant designs need rebuilding and recommends piloting the organization models first. If you run several classic tenants on one vCenter, take that seriously, because two VM Apps organizations can't share one (<KB id={408990} />).
</Callout>

### Failures with a public fix

| Message or symptom | Meaning | KB |
|---|---|---|
| `VCFMS-PRECHECK-GENERIC-001` on the SSH check | Automation was imported with damaged or expired credentials | <KB id={443723} /> |
| `The source system is not a VCF Automation (VCFA) 9.x product` | An SSH password was changed on one node only. Reset it on all of them. | <KB id={443988} /> |
| `vmsp_run_vcfa_prechecks` failed, tasks queued | 15-minute backups keep the precheck waiting. The KB moves them to every 4 hours. | <KB id={456790} /> |
| `requires VCF services runtime version 9.1.#` | The plan's runtime version isn't the one the target needs. Update the plan to the version named in the error and download its INSTALL binary. | <KB id={449628} /> |
| Backup precheck times out after six hours or more | Going from 9.1.x to 9.1.1, the migration engine was upgraded first, which "Upgrade All" can trigger. Upgrade VCF Automation first, or target 9.1.1.0100, which fixes it. | <KB id={455559} /> |
| `vmsp_upgrade_vcfa failed` at Power Off Source Cluster | Cluster VMs were moved to another vCenter folder. Match the folder path and retry. | <KB id={441260} /> |
| VCF Automation 9.0 missing from fleet management | An inventory migration gap. Add it with the "Import 8.x appliance" option. | <KB id={447155} /> |
| Endpoint certificate precheck or TLS errors from 8.18.1 | Implicitly trusted endpoint certificates were never stored, and the upgrade moves only the database | <KB id={425489} /> |
| FIPS precheck blocks the upgrade | IPAM skipping certificate checks, plain LDAP, or an Aria Operations endpoint | <KB id={447667} /> |

Three problems show up only after the upgrade. Native AWS, Azure and GCP management is [off by default in VM Apps organizations](https://knowledge.broadcom.com/external/article/448993) from 9.1.1. From 8.18.x the switch can only be made after the upgrade; from 9.0 or 9.1 it can be made before or after. Custom actions [can disappear](https://knowledge.broadcom.com/external/article/454245) on 9.1.0 and 9.1.1, with the fix due in 9.1.1.0200. Classic tenants' Orchestrator endpoints may [not remap to the embedded Orchestrator](https://knowledge.broadcom.com/external/article/443720/embedded-orchestrator-integration-shows.html). Put all three on the post-upgrade test list.

## Route 3: starting with neither

[The VCF Installer](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/deploy-a-new-vcf-fleet-or-a-new-vcf-instance.html) can deploy VCF Automation or skip it for a Day-N deployment, and the [upgrade guide](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html) also allows Day-N after an upgrade. The [deployment models](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/vmware-cloud-foundation-concepts/vcf-automation-deployment-models.html) are a single small node for proof of concept and development, with no application-level HA, or three medium or large nodes for production.

<Callout type="analysis" title="This site's advice">
On a 5.x upgrade with nothing to carry over, defer it. TechDocs allows that, and it keeps five addresses, a runtime and an organization design out of the platform project. Deploy it when a tenant or self-service requirement exists, and start with All Apps unless you know you need VM Apps.
</Callout>

## What would change the answer

- **You run VCD and Aria Automation together.** Each VCF Operations pairs 1:1 with VCF Automation, and an upgraded Aria Automation becomes the instance's first organization. No public page says whether VCD can migrate into that same instance. This one decides fleet count, so ask first.
- **The RPQ comes back negative** for Container Service, Data Solutions or Object Storage. Those tenants' services need a replacement before the VCD route is viable for them.
- **The guide contradicts this note's All Apps reading.** Re-size the target from the guide.
- **You can't reach 9.1.1 by 11 October 2027.** VCD's August 2028 date then doesn't help, because the platform under it is out of support first.
