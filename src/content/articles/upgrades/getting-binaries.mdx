Take the online depot if the firewall team will open the paths. If they won't, build an offline depot before considering side-load: one tree then serves the Installer and the fleet, while side-loading uploads to two places, including 15 component IDs into the Fleet Depot Service. Lam makes the same recommendation for air-gapped sites in his June post.

HTTP is the offline depot with TLS removed. [TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management/binary-management-for-vmware-cloud-foundation/set-up-an-offline-depot-web-server-for-vmware-cloud-foundation.html) lists HTTP without authentication as supported from 9.1, with no production caveat, and Lam calls it a customer choice that helps development and PoC work. Use HTTPS unless the depot sits on an isolated segment, because no-auth HTTP gives whoever shares that network read access to the binaries and leaves the Installer no way to verify the server. That's an inference from how HTTP works, and Broadcom doesn't state it.

Whichever route you take, finish downloads before the change window and confirm each binary shows as available, so a blocked path surfaces while there is still time to fix it.

## From download token to activation code

On 9.1, register a Software Depot ID and use the depot activation code, the only credential Broadcom documents for 9.1 downloads. "Download Tokens are no longer used for depot authentication" (<KB id={443647} />), and the TechDocs download pages of 5 November 2026 mention only codes.

Practice looks looser, and the conflict is worth writing down in a runbook. Lam's May cheat sheet says "all VVF/VCF downloads support both download token and activation codes", with no date for tokens to end, and his September `--latest` examples still pass a token file. Broadcom's own KBs split too: <KB id={441349} /> fixes a 9.1 403 by generating a new token, and <KB id={442857} /> uses both flags. A token may therefore still work in the tool, but ESX downloads accept only a code, so a token-based script already fails on ESX. Move scripts to the code now.

The ID comes from the Installer, [the software depot in VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management/binary-management-for-vmware-cloud-foundation/connect-sddc-manager-to-a-software-depot-for-downloading-bundles.html) or the tool, and is registered in the VCF Business Services console, under the tenant and Site ID that hold the entitlement. Keep the registered name lowercase (<KB id={443166} />). The appliance side is simpler than the download side: connected mode takes the code, an offline depot takes only a URL and credentials if authentication is on, and in disconnected mode binaries arrive by upload from a machine with internet access. The switch to codes starts with 9.1 (<KB id={443647} />), which leaves 9.0 and earlier on the 32-character token (<KB id={420374} />). That's an inference, because neither KB says it about older releases.

This code isn't the licence activation code: see [Two activation codes](/vcf/library/licensing/two-activation-codes/).

## Depot layout rules

An offline depot is a web server over the tree the tool writes, and in this mode the software depot forwards requests there without keeping a local copy ([TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management/binary-management-for-vmware-cloud-foundation/connect-sddc-manager-to-a-software-depot-for-downloading-bundles.html)). The Download Tool is the only supported way to fetch binaries without internet access, so let it build the tree and don't rearrange it.

- Point `--depot-store` at the depot root. A subfolder produces a wrongly built depot that later fails on the ESX sync (<KB id={446454} />).
- Give every release the same destination folder and the tool merges them, Lam's cheat sheet says. Don't merge trees by hand.
- Copy the whole root when moving a depot. Building by hand means the metadata zip plus binaries in `PROD/COMP/<product>/` with original filenames (<KB id={421477} />). That KB is 9.0-scoped, and its first method is the old bundle transfer utility, which is unsupported on SDDC Manager 9.x (<KB id={447995} />).
- Three metadata files must be current: `vcfManifest.json`, `productVersionCatalog.json` and `VmwareCompatibilityData.json`. Turn caching off on the web server and on any proxy in front of it (<KB id={447589} />).
- Refresh the vSAN HCL file at least every 90 days, or host commissioning fails (<KB id={424728} />, written for 9.0.x).
- If you turn on basic authentication, copy the access split from TechDocs' Apache example, where `PROD/COMP` and `PROD/metadata` need credentials and `PROD/vsan/hcl` stays open.
- For HTTPS, issue the certificate with both DNS name and IP address as SANs, as TechDocs' example does. A reader on Lam's May post reported sync failures without them.

Two configuration behaviours matter on a rebuild. Configuring an offline depot on the Installer deactivates and deletes the online connection ([TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/preparing-your-environment/downloading-binaries-to-the-vcf-installer-appliance/connect-to-an-online-depot-to-download-binaries.html)). And HTTP settings applied on the Installer before the fleet deploys carry over to the Fleet Depot Service, Lam reports, so set it there and skip the second API call.

## Runtime egress

Downloads change source address when the fleet deploys. The depot moves off the Installer into a container on the VCF Management Services Platform, using addresses from the VCF Services Runtime IP pool, and Broadcom warns that "firewall rules may not be in place for this shift" (<KB id={443216} />). A rule written for SDDC Manager won't cover it (<KB id={443166} />). The 90-to-91 note covers [when that happens in an upgrade](/vcf/library/upgrades/90-to-91-management-services/).

Allow outbound 443 from the VCF Installer, vCenter, VCF Operations, the Download Tool host and every runtime IP pool hosting a software depot, per the [Public URLs page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/planning-and-preparation/public-urls-required-for-vmware-cloud-foundation.html) (5 Nov 2026):

- `dl.broadcom.com`, `eapi.broadcom.com`, `vvs.broadcom.com`, `vsanhealth.vmware.com`
- `vcf.packages.broadcom.com` from 9.1.1
- `projects.packages.broadcom.com` for Supervisor and VCF services, from the runtime pools

<KB id={453116} /> also calls `depot.broadcom.com` mandatory, and the Public URLs page doesn't list it. Use the Public URLs page as the request and add that host only if the depot still fails with the others open.

Test with curl from VCF Operations and a control-plane node. A working path returns 403 from `dl` and `vvs` and 500 from `eapi` and `vsanhealth` (<KB id={443216} />), so a 403 in this test is good news and a timeout is the failure. The reverse trap sits in SDDC Manager: "Depot Connection Active" only proves reachability, so a 403 during download points at the credential (<KB id={420374} />).

Proxies and TLS inspection are set per component. On the runtime, `vmsp-utility.py` on a control-plane node configures the proxy (option 2, <KB id={447542} />) and adds an inspection CA to the truststore (option 4, <KB id={442978} />). Exempting `dl.broadcom.com` from inspection removes the manual imports on SDDC Manager (<KB id={442735} />). The runtime's failures also involve `eapi.broadcom.com` (<KB id={442978} />), so exempt both and the runtime truststore step should fall away too. That's an inference from those two KBs, and Broadcom doesn't state it. If deep inspection has to stay, the Public URLs page lists CDN wildcards you also need. The Download Tool has its own trust store: an HTTPS proxy's certificate goes into the tool's bundled JRE ([TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/preparing-your-environment/downloading-binaries-to-the-vcf-installer-appliance/download-install-binaries-to-an-offline-depot.html)).

<Callout type="field">
Put the depot path in the network design as its own flow: source addresses, destinations, ports, proxy and inspection exemptions. A firewall request carried over from 5.x won't cover it.
</Callout>

## Lab only

None of this belongs in a production design. Any web server that serves the tree unchanged with caching off is enough for a lab rebuild, and one shared depot means every rebuild tests identical binaries. Lam's 9.0 workaround, HTTP with basic authentication, still works on 9.1 and he calls it more of a hack. TechDocs doesn't list that combination, so on 9.1 use plain HTTP without authentication in the lab instead.
