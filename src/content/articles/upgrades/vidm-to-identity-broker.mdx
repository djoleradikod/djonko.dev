<InShort>
Workspace ONE Access (vIDM) 3.3.x has no in-place upgrade to 9.x. It stays managed by Aria Suite Lifecycle 8.x for as long as you keep it. The VCF Identity Broker is deployed new, and only after VCF Operations, SDDC Manager and the management domain vCenter are on 9.x (<KB id={390634} />). Every consumer of vIDM, above all VCF Automation, then has to be pointed at the broker. Plan it as an identity cut-over with users, groups, roles and a test list, and give it its own change.
</InShort>

## A sequence that works

1. **Inventory what uses vIDM.** List the products, directories, groups, role mappings and any third-party applications federated through it. Some customers find vIDM fronting more than VMware products.
2. **Decide mode and scope.** Embedded, appliance (9.0) or instance mode (9.1), and fleet-wide, cross-instance or single-instance SSO. See <a href="/vcf/library/architecture/identity-broker/">Identity in VCF 9</a>.
3. **Prepare the identity provider side.** Create the directory connection or OIDC or SAML application, and the groups that will map to VCF roles.
4. **Deploy and configure VCF SSO** from VCF Operations, Fleet Management, Identity and Access. The page needs a working management domain cloud proxy (<KB id={437258} />).
5. **Cut over consumers one at a time.** vCenter and NSX first, then VCF Operations, then VCF Automation, testing a named user's login and authorisation at each step.
6. **Keep vIDM running** until the last consumer is moved and tested. Then retire it, along with Aria Suite Lifecycle if nothing else needs it.

## If you are on 9.0 already

A 9.0 appliance-mode broker is migrated into 9.1 instance mode during the upgrade, and its old VMs are powered down. If it sits on a non-management network, the migration is a disruptive backup-and-restore that needs its own window, and its certificate must not carry an IP SAN (<KB id={444734} />). In 9.1.1, the services runtime hosting the broker must be patched before the broker itself (<KB id={457245} />).

After any transition, check that VCF Operations has recorded the broker in the right mode. A stale "embedded" record makes the broker appear unavailable (<KB id={444003} />).

<Callout type="field">
Identity cut-overs fail on authorisation, not authentication. Users can sign in but see nothing because group-to-role mappings didn't carry over. Write the role mapping table first, and test with a non-admin account from each role.
</Callout>

## Pitfalls

- **Promising "single sign-on everywhere".** SDDC Manager stays on local accounts.
- **Retiring vIDM too early.** Anything still federated through it breaks when it goes.
- **Putting the broker in the platform upgrade window.** It has different stakeholders, such as identity and security teams, and different tests. Give it its own change.
