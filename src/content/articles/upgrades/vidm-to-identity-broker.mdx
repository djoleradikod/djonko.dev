<InShort>
Workspace ONE Access (vIDM) 3.3.x has no in-place upgrade to 9.x. It stays managed by Aria Suite Lifecycle 8.x for as long as you keep it (<KB id={390634} />). The VCF Identity Broker is always a new component: on 9.0 you install it after VCF Operations, SDDC Manager and the management domain vCenter are on 9.0 (<KB id={390634} />), and in an upgrade to 9.1 it is deployed with VCF management services. Every consumer of vIDM, above all VCF Automation, then has to be pointed at the broker, and 9.1 gives you a script for part of that. Plan it as an identity cut-over with users, groups, roles and a test list, and give it its own change.
</InShort>

## A suggested sequence

1. **Inventory what uses vIDM.** List the products, directories, groups, role mappings and any third-party applications federated through it. Check whether vIDM fronts more than VMware products.
2. **Decide mode and scope.** Embedded, appliance (9.0) or instance mode (9.1), and fleet-wide, cross-instance or single-instance SSO. The 9.1 migration only targets instance mode. See <a href="/vcf/library/architecture/identity-broker/">Identity Broker in 9.1</a>.
3. **Prepare the identity provider side.** Create the directory connection or OIDC or SAML application, and the groups that will map to VCF roles.
4. **Deploy and configure VCF SSO** from VCF Operations, Fleet Management, Identity and Access. The page can fail to load when the management domain's cloud proxy is offline (<KB id={437258} />).
5. **Cut over consumers one at a time.** vCenter and NSX first, then VCF Operations, then VCF Automation, testing a named user's login and authorisation at each step.
6. **Keep vIDM running** until the last consumer is moved and tested. Then retire it, along with Aria Suite Lifecycle if nothing else needs it.

## If you are on 9.0 already

A 9.0 appliance-mode broker [transitions](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-vcf-identity-broker.html) to 9.1 instance mode during the upgrade, and you can remove the old appliance once your management components are on 9.1. If it sits on a network or datastore different from management services, the migration is a disruptive backup-and-restore that needs its own window, and its certificate must not carry an IP SAN (<KB id={444734} />). In 9.1.1, the services runtime hosting the broker must be patched before the broker itself (<KB id={457245} />).

After any transition, check that VCF Operations has recorded the broker in the right mode. A stale "embedded" record makes the broker appear unavailable (<KB id={444003} />).

<Callout type="analysis" title="Test roles as well as sign-in">
[The 9.1 script](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/migrating-vmware-identity-manager-to-vcf-identity-broker.html) doesn't carry previous VCF Automation roles, and <KB id={444734} /> has you verify role assignments after a restore, so a working sign-in doesn't show that anyone has the right access. This is inference from those pages. Write the role mapping table first, and test with a non-admin account from each role.
</Callout>

## Pitfalls

- **Promising "single sign-on everywhere".** [SDDC Manager's UI](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/points-to-consider-while-setting-up-vmware-cloud-foundation-sso.html) stays on local accounts.
- **Retiring vIDM too early.** Anything still federated through it breaks when it goes.
- **Putting the broker in the platform upgrade window.** It has different stakeholders, such as identity and security teams, and different tests. Give it its own change.
