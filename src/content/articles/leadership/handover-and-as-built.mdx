<InShort>
Keep the pack on storage that survives the platform, because [manual recovery of a VCF Instance requires the as-built record](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/-vmware-cloud-foundation-instance-recovery.html). The [9.1 blueprint index](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for.html) lists no handover blueprint (checked 7 Nov 2026), so the structure here is this site's, built from Broadcom's recovery, certificate and password guidance. Call the handover finished when the receiving team can open the pack with the platform down, a named person holds every duty in the calendar, and they have run one runbook without help.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to compare 5.x and 9.x with unsourced lists. "Services runtime pool" isn't the name on Broadcom's 9.1 management services page, which says VCF services runtime. Licensing and identity owners were stated as platform requirements when they are this site's advice, and management pack updates were listed as a recurring task when the documented issue comes with the 9.1.1 upgrade. The as-built section also omitted Broadcom's own record list and its instruction to keep that record on secondary storage.
</Callout>

## The pack

| Section | Contents |
|---|---|
| As-built | One table per instance: Broadcom's recovery list, plus FQDN, IP, version, role and owner for each component |
| Decisions | Records for topology, identity, certificates and configuration, plus any departure from the blueprints |
| Access | Who holds which role and owns which credentials and certificates, where credentials live, how break-glass retrieval works. No passwords in the pack |
| Calendar | Each duty with its interval and a named person |
| Runbooks | [Shutdown and startup](/vcf/library/day-2/shutdown-startup-order/), weekly health check, support bundle ([Log Assist sends it from the VCF Operations console](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs)), License Server replacement, escalation |
| Contacts | Support contracts, account team, internal escalation path |
| Open items | Known issues, accepted risks, planned changes |

[Fleet architects make the topology, identity, certificate and configuration calls](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint.html), so those are the records the operations team will need when someone asks why. Michael Nygard's [2011 format](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) still fits: title, context, decision, status, consequences, with a reversed decision kept and marked superseded. Daniele Procida's [Diátaxis](https://diataxis.fr/) sorts documentation into tutorials, how-to guides, reference and explanation. Applied here, runbooks are how-to, the as-built is reference and decision records are explanation. Keep them apart so that refreshing the as-built after an upgrade doesn't mean rewriting a runbook.

## What the as-built must record

The record is [mandatory for the manual recovery process, and still advised for automated recovery](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/-vmware-cloud-foundation-instance-recovery.html), which restores much of it from the SDDC Manager backup. That sets the minimum:

- Topology: physical, distributed switch and NSX networking, workload domains, clusters and the hosts in each.
- Host and VM networking: vmnic-to-switch port mappings, VM vNIC to port group mappings, VMkernel and VM addresses, and DNS, NTP, AD and similar services.
- Each vCenter: FQDN, IP settings, version and build, deployment and storage sizes, SSO domain name.
- The easy ones to forget: custom VIBs on hosts, the root SSH authorized keys file, and custom scripts used by alarm actions or cron jobs.

Save it on [secure secondary storage](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-instance-recovery.html), since a record that lives on the failed platform can't help recover it. A project folder the operations team can't open fails for the same reason.

The same blueprint names the [Planning & Preparation workbook as a good source](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-instance-recovery.html). Start there, but the workbook holds what was planned. Query the platform's APIs for names, versions and addresses wherever you can, so the tables show what is running and can be regenerated at the next upgrade.

## Who owns what

The [fleet management blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint.html) gives three personas: architects decide the models, platform engineers maintain SSO, certificates, passwords and configuration management, and cloud operations engineers run daily operations and compliance checks. Use those as the first draft of the owner column.

<Callout type="analysis" title="Two owners the personas miss">
Broadcom's [licensing overview](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/licensing-overview/v9-licensing-overview.html) and [identity blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/identity-and-access-management.html) describe tasks and assign no team, so the pack has to. Name who holds access to the VCF Business Services console (vcf.broadcom.com), where license files and activation codes come from, and to [My Entitlements on the support portal](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs). Name a contact for the external identity provider as well. If another team runs it, agree how they warn the platform team of changes, since the broker depends on that connection.
</Callout>

For credentials, the [password recommendations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) make an enterprise vault the source of truth when credentials are used through API or manual processes, and they call for alerts on retrieval from SDDC Manager, since direct retrieval of break-glass credentials is commonly considered a compliance risk. So the Access section says where the vault is and who may retrieve from it.

Before the project team leaves, check the runbooks against one aim of the blueprint: [day-2 work run through API or workflow automation via VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint.html), partly to reduce "dependency on individual operator accounts". Any script still tied to a departing engineer's account should move to something the receiving team holds.

## The calendar

| Duty | Interval | Basis |
|---|---|---|
| License update | [At least every 180 days](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/update-licenses/updatelicenses.html). Automated mode updates every 24 hours; manual mode needs a person | Broadcom |
| Confirm "Last Usage Report Generated" in Registration Details | Weekly, with the health check | [The field](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/update-licenses/updatelicenses.html) is Broadcom's, the interval this site's advice |
| Certificate expiry | Continuous, once alerts reach the receiving team | [Built-in alerts need the notification plugin](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html) |
| Password expiry and rotation | Your own password standard; SDDC Manager auto-rotation for inter-component accounts that only it can manage [offers 30, 60 or 90 days](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) | Broadcom for the auto-rotation intervals |
| Backups run, and manual ones before a change | Set your own: the blueprint says [regularly, with no interval, and before an upgrade or certificate update](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/security-modernization/vcf-backup-and-restore.html) | Broadcom for the triggers |
| Services runtime disk and volumes | Weekly, this site's advice | Dashboard grades up to 80% good, 80 to 90 warning, 90 to 95 severe, above 95 critical; volumes resize through Lifecycle (<KB id={417255} />, which names no release) |

Licensing carries the sharpest deadline. Licenses that miss the window are [treated as expired and hosts disconnect from vCenter](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/update-licenses/updatelicenses.html), and a [License Server outage blocks daily reports and imports](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/license-server-overview/license-server-downtime-impact.html), so that outage belongs in the escalation runbook even on a connected platform. This is an operational view and isn't legal or purchasing advice; the [licensing overview](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/licensing-overview/v9-licensing-overview.html) is the primary source.

## Warnings for the receiving team

Put these under Open items.

- [Don't move management services VMs to another resource pool or folder](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) in vCenter. The 9.1.1.0 release notes warn that the runtime configuration goes out of sync, later deployment and scale-out fail, and reconciling placement takes Broadcom Support.
- [Run certificate rotations one at a time](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html), because the 9.1.1.0 release notes report instability from concurrent operations <AsOf date="2026-11-07" />.
- [Manage certificates only through VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html) once it manages them. Working from vCenter leaves orphaned CSRs and a conflict over the source of truth.
- [Don't change inter-component account passwords directly on a component](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html). That can break the integration and cause an outage.
- Keep vCenter root expiry on the calendar by hand. VCF Operations 9.1.1.0 [can show "No Expiry" for an expired root account](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) with vCenter 9.1 or earlier, and no workaround is listed <AsOf date="2026-11-07" />.

## Handing it over

1. Walk through it with the receiving team on the live platform, and have them open the pack from its secondary storage while you do.
2. Let them run one runbook while you watch, and fix whatever confused them.
3. Check that every calendar row has a person who has confirmed they hold the access it needs.
4. Agree an end date for support from the project team.

[Runbooks that get used](/vcf/library/leadership/runbooks-that-get-used/) covers how to write the runbooks. [Backups](/vcf/library/day-2/backups/) and [the 180-day cycle](/vcf/library/licensing/180-day-cycle/) carry the detail behind those calendar rows.
