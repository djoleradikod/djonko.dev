<InShort>
Run **instance mode** for anything in production. Embedded is scoped to labs and proofs of concept in Broadcom's 9.1 design library, the first instance broker arrives with the install or upgrade anyway, and the vIDM migration only targets instance. Start with **one broker for the fleet**, and add one only when a sign-on outage or an identity realm has to stop at an instance. Moving up is easier than moving back: embedded to instance is a documented migration in VCF Operations, while instance to embedded deletes your SSO configuration. On 9.0 with an appliance broker, get it onto the same network and datastore as management services before you upgrade VCF Operations, or the broker upgrade fails.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to say there is no migration from vIDM and that moving from embedded to an external broker requires an SSO reset. Both are out of date for 9.1: Broadcom documents a scripted vIDM migration and [an embedded-to-instance migration](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/managing-vmware-cloud-foundation-operations-sso/migration-of-vcf-identity-broker-embedded-to-vcf-identity-broker-appliance.html) that it says "ensures no data loss". It also said SDDC Manager is local accounts only. [That holds for its UI](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/points-to-consider-while-setting-up-vmware-cloud-foundation-sso.html); its APIs accept SSO users.
</Callout>

## The questions, in order

**1. Is this a lab or a proof of concept?** If so, embedded is ["intended for"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-instance-models/embedded-vidb.html) that use: one node inside the management vCenter, no deployment, restored with vCenter. Otherwise choose instance and stop weighing the mode. Instance is [Broadcom's recommendation for production](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-instance-models/external-vidb.html) <AsOf date="2026-11-07" />. Broadcom gives two warnings about embedded: [vCenter maintenance also hits authentication](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-instance-models/embedded-vidb.html), and it ["will be deprecated in later versions of VCF"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/setting-up-sso/choose-the-deployment-mode.html), with a migration to instance required before it reaches end of support.

<Callout type="analysis" title="Broadcom's pages don't line up">
The [9.0 page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/fleet-management/what-is/deployment-models-for-sso.html) steered a single instance to embedded. The [9.1 SSO models page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models.html) still says both broker models are supported under every SSO model, and no 9.1 page calls embedded in production unsupported. This note follows the stricter design pages, partly because embedded saves little: [the first broker is deployed automatically in the first management domain](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-instance-models/external-vidb.html).
</Callout>

**2. Is vIDM in the picture?** Then the mode is settled, because ["Instance only"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/migrating-vmware-identity-manager-to-vcf-identity-broker.html) is the migration's supported target. Without vIDM, the one thing favouring embedded is small: Okta, Entra or Ping already set up in vCenter is [retained on embedded and redone on instance](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/points-to-consider-while-setting-up-vmware-cloud-foundation-sso.html). Users and groups are provisioned again in both modes, so the saving stops at the provider setup.

**3. Are management services highly available?** Settle that first, since an instance broker is only as resilient as what it runs on. Broadcom's [Simple model](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/vmware-cloud-foundation-concepts/vcf-management-services-models.html) has one control plane node, is aimed at testing, and needs a redeploy and restore if that node is lost. That a production broker belongs on the High Availability model is an inference from that page.

**4. More than one instance?** If not, you are done: one broker.

**5. Must sign-on survive the loss of one instance?** If a second site has to keep signing in while the first is down, add a broker there. If an outage across the fleet is acceptable, take fleet-wide, which has the smallest footprint and one realm. Local accounts and the emergency API client [keep working during a broker outage](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models/single-single-sign-on-deployment-per-vcf-instance.html), so store those credentials in a vault and test them.

**6. Must instances use different identity providers?** Separate vCenter and NSX sign-on fits in a fleet, because [each instance's components share one broker](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models.html), while separate console sign-on means [a second fleet](/vcf/library/architecture/one-fleet-or-several/) (that note also has the latency bounds for a broker). The limit is the console: VCF Operations and VCF Automation ["can connect to only one"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models/one-sso-deployment-per-vcf-estate.html) broker. That split is an inference from those two rules. One fleet can hold several providers because SSO is configured per instance, as [William Lam laid out on 9 October 2025](https://williamlam.com/2025/10/multiple-vcf-sso-identity-providers-for-vmware-cloud-foundation-vcf-fleet.html) for 9.0. His cheap route, embedded per instance, doesn't carry over to production on 9.1 given question 1, and each added instance broker is a day-N deployment that [needs more worker nodes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/vmware-cloud-foundation-concepts/vcf-management-services-models.html).

| SSO model | Brokers | An outage hits | Moving between instances | Restoring the broker |
|---|---|---|---|---|
| [Fleet-wide](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models/vcf-fleet-wide-sso-model.html) | One per fleet, on the primary instance | The fleet | No new login | Losing the primary means restoring that instance |
| [Cross-instance](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models/one-sso-deployment-per-vcf-estate.html) | One per set of instances | That set | No new login within a set | To another instance in the same realm is supported |
| [Single-instance](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models/single-single-sign-on-deployment-per-vcf-instance.html) | One per instance | One instance | Credentials again | Across realms is not supported |

Broadcom [prefers scaling up](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-instance-models/external-vidb.html) over adding a broker when one large broker meets your security, resilience and performance standards, and each broker is "managed separately" for tasks such as backup and restore, [the cross-instance page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models/one-sso-deployment-per-vcf-estate.html) says. All three models are written for one fleet: that page has each broker serve instances "in the same VCF fleet", and none of these pages describes a broker spanning fleets.

## What switching costs

| Change | Documented? | What it costs |
|---|---|---|
| Embedded to instance | Yes: [guided migration in VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/managing-vmware-cloud-foundation-operations-sso/migration-of-vcf-identity-broker-embedded-to-vcf-identity-broker-appliance.html), source at 9.1 | Needs a target instance broker already deployed, and an SFTP account you delete afterwards. ## The 9.1 network and datastore rule

The rule binds a 9.0 **appliance** broker, because 9.1 moves it into VCF management services and the two ["must be deployed on the same network and on the same datastore"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/deploy-vcf-identity-broker-on-the-management-network.html). The target is the VCF management network or a custom VLAN-backed network, since management services can't sit on an NSX overlay. An embedded broker is exempt: it [upgrades with vCenter](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/upgrade-vcf-identity-broker.html).

- **Compliant:** use the dedicated upgrade, which <KB id={440630} /> says needs no downtime on the management network, and check the broker can reach your provider from its new home.
- **Not compliant, VCF Operations still on 9.0:** run the redeploy procedure first. It needs a maintenance window, and configured permissions aren't affected. Back up, power off, delete the component (the first attempt fails, then retry with Skip task set to True), repoint DNS if the network changes, deploy at the same build with the same FQDN and certificate, restore.
- **Not compliant, VCF Operations already on 9.1:** the broker upgrade fails and <KB id={444734} /> takes over. Choose its backup-and-restore method, because the other one rebuilds every IAM setting by hand. The backup-and-restore scripts run for up to 15 and then 5 to 30 minutes, and downtime starts when the VMs power off.

In both procedures the certificate's SAN must hold only the FQDN, which agrees with [the trust model](/vcf/library/architecture/trust-model/). <KB id={440630} /> still tells non-management-network brokers to contact Support, while the two procedures above document the fix. Two checks afterwards: in 9.1.1 the runtime must be on 9.1.1 before the broker's pre-check passes (<KB id={457245} />), and VCF Operations can mislabel a migrated broker as embedded after a 9.0.2 upgrade (<KB id={444003} />).

For a new 9.1 build there's nothing to place separately. The first broker [installs with VCF management services on the services runtime nodes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/points-to-consider-while-setting-up-vmware-cloud-foundation-sso.html), and the [network model](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/vmware-cloud-foundation-concepts/fleet-level-component-backing-networking-models.html) requires a distributed port group for those services.

## What happens to vIDM

vIDM has no upgrade, but 9.1 adds a way out <AsOf date="2026-11-07" />. From 5.2 the broker is [deployed with management services during the upgrade](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html), but vIDM keeps serving VCF Automation until you move it, so Broadcom says to preserve Aria Suite Lifecycle 8.x for vIDM's day-N work. The way out has two parts:

- **[The script](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/migrating-vmware-identity-manager-to-vcf-identity-broker.html)** needs vIDM 3.3.7 GA. Tenant organizations, NSX Global Manager, vIDM local accounts and multifactor authentication with Active Directory are unsupported, so check those first. It moves users and groups, then updates VCF Operations, the VCF Automation provider organization and NSX. It leaves behind provider configuration, OAuth clients and previous roles, and it doesn't remove vIDM from the components. The page doesn't state whether the run is disruptive.
- **[VCF Automation's own procedure](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/phase-3-import-and-upgrade-aria-automation-8-to-vcf-automation-9/migrate-vcf-automation-single-sign-on-configuration-from-vmware-identity-manager-to-vcf-identity-broker.html)** covers Provider Management and the Organization for VM Apps, configured separately. Remove the vIDM configuration only after every user and group has signed in through the new provider.

NSX may not wait for you. <KB id={454567} /> says NSX 9.1.0 requires the broker and loops on the old vIDM login, and <KB id={455402} /> describes a redirect loop during a partial upgrade, so keep NSX local admin credentials to hand. [The vIDM note](/vcf/library/upgrades/vidm-to-identity-broker/) has the sequencing.

## Outside SSO in any mode, and the vCenter prerequisite

SDDC Manager's UI [takes only local admin accounts](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/points-to-consider-while-setting-up-vmware-cloud-foundation-sso.html), though its APIs accept SSO users, and ESX is excluded too. [Enhanced Linked Mode must be off](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/points-to-consider-while-setting-up-vmware-cloud-foundation-sso.html) on participating vCenters, and vCenter can't join SSO later until it is.
