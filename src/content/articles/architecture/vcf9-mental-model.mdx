<InShort>
In VCF 5.x, the biggest thing you managed was an SDDC Manager and its domains. VCF 9 puts two layers above that. A **fleet** shares one VCF Operations and, once deployed, one VCF Automation. Inside a fleet, each **VCF instance** is a management domain with its own SDDC Manager, plus its workload domains. The domain still exists and still means one vCenter. What changed is that the fleet now owns the console, identity, licensing and the lifecycle of the management components. Start any 9.x design question by asking "is this fleet-level or instance-level?"
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note called all fleet management components mandatory and said a fleet has exactly one VCF Automation. VCF Operations is required, but VCF Automation is optional at deployment: the Installer can skip it and you can add it later, up to one per fleet. [Consolidated or standard](/vcf/library/architecture/consolidated-vs-standard/) sets out the sources and dates.
</Callout>

### Fleet

A fleet is the operational boundary. It has exactly one VCF Operations, which [Broadcom requires per fleet](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs), and from 9.1.1 that instance [must sit in the first instance's management domain](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/deploy-a-new-vcf-fleet-or-a-new-vcf-instance.html). It can have one VCF Automation, which [the Installer lets you skip](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/deploy-a-new-vcf-fleet-or-a-new-vcf-instance.html) and add later (<KB id={441816} />). It shares log management and, in the [fleet-wide SSO model](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/single-sign-on-models/vcf-fleet-wide-sso-model.html), one identity broker. Licensing hangs off VCF Operations and its license server, and [a license server can't be shared between fleets](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/license-server-overview.html), so the fleet is also your licensing boundary. You can run more than one fleet, for example one per region or per regulatory zone. Broadcom's [fleet deployment models](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/vmware-cloud-foundation-concepts/vcf-operations-deployment-models.html) count "more management overhead" against multiple fleets, so treat a second fleet as a decision that needs a reason, not a default.

### VCF instance

An instance is what a 5.x engineer would recognise: a management domain with its own SDDC Manager, plus zero or more workload domains. In 9.1 each instance also gets its own services runtime, which runs instance-level services such as SDDC lifecycle, a Salt master and telemetry. The **first** instance is special. Its runtime also hosts the fleet-level services: fleet lifecycle, Salt RaaS and log management.

### Domain

A domain is unchanged in meaning: one vCenter, with NSX either dedicated or shared. The management domain still hosts the management plane. Workload domains still host the workloads.

## Why the layers matter in practice

**Upgrades go top-down.** The fleet is upgraded before any instance, and an instance's management plane before its domains. In 9.1, VCF Operations must be upgraded first (<KB id={440630} />). A useful rule of thumb from [humbledgeeks](https://humbledgeeks.com/vcf-91-lifecycle-one-control-plane-and-the-real-work-to-get-there/) is "Fleet gates instance, never the reverse." In 5.x, the order started at SDDC Manager because there was nothing above it.

**The blast radius follows the layer.** If one domain's vCenter goes down, the damage stays inside that domain. If the first instance's management domain goes down, every instance loses the fleet-level services that live there. When VCF Operations itself is unavailable, workloads keep running and existing licences stay valid, but new licence assignments and capacity updates are blocked (<KB id={443240} />). The lifecycle and configuration screens are also unavailable.

**Day-2 tasks moved up a layer.** Certificates, passwords, backup configuration, DNS and NTP settings for an instance, and workload domain creation all start in VCF Operations now. Host commissioning, network pools, cluster creation and edge clusters moved into vCenter. The <a href="/vcf/library/day-2/where-did-that-button-go/">Day-2 task map</a> lists them all.

<Callout type="field">
When a 9.x ticket or design question is vague, the first thing to settle is which layer it is about. "Certificates are failing" means something different for a fleet management component, such as VCF Operations or the identity broker, than it does for an instance's core infrastructure, such as vCenter, NSX or ESX. Different services own them, and they log to different places.
</Callout>

## Design questions to settle early

- **How many fleets?** Start with one. A second fleet makes sense for hard separation, such as sovereignty, a separate operator team or a contract that demands separately administered licences. A second site alone is not a reason for one. [One fleet or several](/vcf/library/architecture/one-fleet-or-several/) gives the deciding questions.
- **How many instances?** An instance is a failure and lifecycle boundary with its own SDDC Manager. Separate sites or regions can justify a second instance. For separate business units, consider a workload domain instead.
- **Where will the first instance live?** It carries the fleet services, so put it on the most resilient site you have.
- **What identity scope?** Fleet-wide SSO is the simplest. Cross-instance or single-instance scopes limit the blast radius but add brokers to run. See <a href="/vcf/library/architecture/identity-broker/">Identity in VCF 9</a>.

## Pitfalls

- **Treating "instance" as a 9.x name for "domain".** It is not. An instance contains domains.
- **Planning a 5.2 upgrade without planning the fleet.** VCF Operations is [required with each fleet](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs), so a 5.2 estate with no Aria components gets it [as part of the upgrade](https://blogs.vmware.com/cloud-foundation/2025/12/18/upgrading-vmware-cloud-foundation-5-2-to-9-0-the-top-10-questions-answered/), according to McDonald's December 2025 answers for 9.0. The [9.1 upgrade](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation.html) also deploys VCF management services and the license server. Their sizing, IP addresses and DNS records need to be ready before the window.
- **Assuming the fleet-level services are spread out.** In 9.1 they sit in the first instance's services runtime. If you lose that runtime, you lose fleet lifecycle and log management for every instance.
