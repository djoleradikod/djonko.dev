<InShort>
**When two VCF components stop talking, check trust first, and don't take the error text at face value.** On VCF Operations 9.0.1 the NSX connection reports "an incorrect username or password" when the real fault is [CA certificates that never reached the adapter](https://knowledge.broadcom.com/external/article/443511), fixed in 9.0.2.

**On 9.1, run every supported certificate operation through VCF Operations.** Broadcom's [blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html) keeps SDDC Manager APIs "only for backward compatibility", and recommends against vCenter's own API, UI and CLI once VCF Operations manages an ESX or vCenter certificate. Leave internal service accounts to the platform as well, because external PAM tools [must not rotate, change or manage them](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html).
</InShort>

The split in 9.0 was among issuers, and VCF Operations already held the [auto-renewal switch](https://blogs.vmware.com/cloud-foundation/2025/06/19/automatic-certificate-renewal-in-vcf-9/). The [October 2026 post by Firth and Hah](https://blogs.vmware.com/cloud-foundation/2026/10/14/managing-certificates-at-scale-with-vmware-cloud-foundation-9-1-1/) says 9.0 management components "can only use Microsoft CAs", which leaves out the fleet management CA in Gray's post. Comparing only the CAs you configure would reconcile them, though that's an inference, so on 9.0 read the certificate list for what actually signed each component.

If you stay on a VMware-issued CA, add its certificate to administrator systems and mark it trusted, or [browsers will warn](https://blogs.vmware.com/cloud-foundation/2025/06/19/automatic-certificate-renewal-in-vcf-9/).

On 9.1 the fleet management CA [isn't among the CA types](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/certificate-management-9-0/configure-a-certificate-authority_9-0.html), and the choice of CA now has a recommended answer. Default certificates on management components [should be replaced with enterprise CA certificates before production](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html), while ESX goes the other way, with default VMCA described as ["The default and recommended option for VCF fleets"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/vsphere-certificate-management/esx-certificate-management.html). OpenSSL is [meant for testing or development](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/certificate-management-9-0/configure-a-certificate-authority_9-0.html) and can't chain into an external hierarchy. [The CA table in the certificates note](/vcf/library/day-2/certificates-in-9/#ca-type-against-renewal-behaviour) weighs each option on 9.1 and 9.1.1.

## How trust is recorded

Trust is recorded in several places, and each one goes stale in its own way.

Trust bundles can fail quietly. Each appliance trusts a set of CA roots, and on 9.1 the services runtime distributes trust through a `platform-trust` configmap. On 9.1.x, an ingress TLS certificate issued through the automated Microsoft CA URL can leave the intermediate CA out of that configmap, and the Log Management integration then hits a silent handshake error (<KB id={441515} />). Log Management shows as installed while Operate > Logs offers the install screen, and its backup fails. The interim workaround is to sign the CSR at the CA by hand and import the full chain.

Thumbprints can fail loudly. NSX [keeps the previous thumbprint](https://knowledge.broadcom.com/external/article/323341) and holds the compute manager connection down until it is updated, whether the vCenter certificate was replaced manually or automatically.

Service account credentials, stored by the caller, can fail without anyone touching them. Repeated rotations, scheduled or on demand, can delete the 9.1 SDDC lifecycle account from SDDC Manager or vCenter and leave its stored credentials stale, so VMSP upgrades and `post_upgrade_inventory_sync` fail and runtime addresses can get locked out (<KB id={450375} />). The recovery is that KB's two scripts, which create a new account and patch the Kubernetes secret. On VVF the same symptoms come from an administrator password changed out of band. So the rule against external PAM tools reduces this risk without removing it, and an upgrade that fails on credentials should send you to this KB even when nobody changed anything. Both points are inferences from the KB's cause, and Broadcom states neither.

|---|---|---|
| NSX compute manager | Connection Status Down (<KB id={323341} />). <Callout type="analysis" title="Where this list stops">
Broadcom's certificate pages don't gather these holders in one place (checked 7 Nov 2026), so the table is assembled from KBs and the 9.1.1 notes and won't be complete for your estate. Add backup tools and third-party integrations, using their vendors' documentation, and [vSphere Client plugins](/vcf/library/integrations/vsphere-client-plugins/). Write the list before the change, because a later failure is quickest to trace to whatever it missed.

Two known issues in the 9.1.1 notes affect when you schedule the change. A certificate change during relocate initiation [fails the vMotion, with no workaround listed](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html), so avoid replacing during migrations. For a management component, VCF Operations may not re-trust the new certificate until the next inventory sync, 24 hours by default, so allow for that before you call a failure a new fault. [The certificates note](/vcf/library/day-2/certificates-in-9/) has the wider failure table.

## The 9.1 rules to plan for

The FQDN rule is the one that can stop an upgrade. Component certificates [must carry the FQDN in the SAN](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/certificate-management-9-0.html), an IP is optional, and hostname verification follows RFC 6125, so an IP-only certificate fails. A certificate without FQDNs breaks automated inventory migration into Fleet Lifecycle and blocks the move from 5.2 or 9.0.x to 9.1, so check before you start and replace any with incomplete SANs (<KB id={449907} />). The same strictness reaches outward: the log forwarder [no longer falls back to the Common Name](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/known-issues/vcfoperations-91-known-issues.html), so forwarding destinations need valid SANs too.

The identity broker has its own SAN limit. If a 9.0.x broker has to be moved by backup and restore because it sits on a different network or datastore from the 9.1 management services, a certificate with an IP in its SAN must be replaced with one [that contains only the FQDN](https://knowledge.broadcom.com/external/article/444734).

Auto-renewal has more preconditions than its toggle suggests. It covers [TLS certificates signed by VMCA, Microsoft CA or OpenSSL, on components that support non-disruptive updates](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/certificate-management-9-0/set-up-automatic-renewal-of-certificates-in-vmware-cloud-foundation.html). Root, intermediate, external CA and self-signed certificates stay manual, and anything within 60 days of expiry needs a manual renewal before you switch it on. Keep expiry alerts running regardless: the [blueprint recommends them](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html), and outbound alerting needs the notification plugin.

ESX carries a lasting side effect. Any ESX certificate operation through VCF Operations [changes the mode in vCenter to Custom, so later renewals must go through VCF Operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/vsphere-certificate-management/esx-certificate-management.html). The separate renewal configured in vCenter on VVF 9.0.2 or vCenter 8.0 Update 3h needs mode `vmca` and stops working on `custom` (<KB id={427937} />), and in `custom` mode each new host needs a CA-signed certificate before it joins inventory. That's another reason to leave ESX on VMCA unless policy says otherwise.
