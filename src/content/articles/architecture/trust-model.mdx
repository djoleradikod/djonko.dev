<InShort>
VCF components trust each other in two ways. The first is **certificates**: the TLS identity each component presents, and the trust stores and thumbprints the others keep for it. The second is **service accounts**: system-generated credentials that one component uses to call another. In 5.x, SDDC Manager handled both for everything it managed. In 9.x the work is split. Fleet management, now part of VCF Operations, looks after the management components. vCenter's VMCA and SDDC Manager look after the infrastructure. 9.1 adds a services runtime with its own ingress certificate and trust bundle, and it enforces FQDN SANs strictly. When something "stops talking", check certificates and service accounts before anything else.
</InShort>

If you use a VMware-issued CA, distribute its root to administrator workstations, or every browser session will start with a warning.

## How trust is recorded

Trust is recorded in several places, and every one of them can go stale:

- **Trust stores.** Each appliance trusts a set of CA roots. In 9.1 the services runtime distributes trust through a `platform-trust` configmap. A missing intermediate CA there silently breaks the VCF Operations to log management integration (<KB id={441515} />).
- **Thumbprints.** NSX stores the vCenter thumbprint for its compute manager registration. VCF Operations adapters and VCF Automation cloud accounts store the thumbprints of what they connect to. Replace a vCenter certificate, and each of these needs re-trusting (<KB id={431963} />, <KB id={441506} />).
- **Service account credentials.** These are stored by the caller and rotated by VCF. Change one out of band and the caller fails. For example, a 9.1 SDDC lifecycle account that drifts breaks upgrades and inventory sync (<KB id={450375} />), and a drifted NSX integration account breaks the VCF Operations NSX adapter (<KB id={443511} />).

## The 9.1 rules to plan for

- **FQDN SANs are mandatory.** Certificates that identify a node only by IP address, or that are missing node FQDNs, block migration of management components into fleet lifecycle during the 9.1 upgrade (<KB id={449907} />).
- **The identity broker certificate must not carry an IP SAN** during the 9.0 to 9.1 transition (<KB id={444734} />).
- **Auto-renewal has preconditions.** It must be turned on at the instance level. Native vCenter auto-renewal works only when vCenter's certificate mode is VMCA, not `custom` (<KB id={427937} />).

<Callout type="field">
A good habit after any certificate change: list everything that stores the old certificate or its thumbprint, then walk the list. For a vCenter replacement that means NSX compute managers, VCF Operations adapters, VCF Automation cloud accounts, backup tools and any third-party integration. If something breaks after the change, look first for an item missing from that list.
</Callout>

## Pitfalls

- **Replacing certificates outside VCF.** It works until the next lifecycle operation, which compares what it expects with what it finds. Use the VCF Operations workflows.
- **Hand-managing service accounts.** VCF rotates them, and external PAM tools must not touch them.
- **Forgetting that 9.0 is a transition.** Some management component passwords and certificates are not fully automated in 9.0. Check the release you are on before promising auto-renewal or auto-rotation.
