<InShort>
VCF Operations is the renamed and expanded Aria Operations. In 9.x it is mandatory, and it is where you build, operate, license and secure the fleet. A 5.2 upgrade deploys it if it is missing. Because so much now depends on it, it needs the same design attention you would give a management vCenter: a deployment model, sizing, cloud proxies, backup, and a plan for what happens if it is down.
</InShort>

## What it does now

The 9.x VCF Operations console groups its work into a few areas, which are worth learning by name because KBs and documentation refer to them:

- **Build.** Lifecycle for the management components and for each VCF instance: plans, prechecks, upgrades and deployments. In 9.1 this drives fleet lifecycle and SDDC lifecycle on the services runtime.
- **Operate.** Health, alerts, VCF Health, topology and, in 9.1, log search through Operate > Logs.
- **Fleet Management.** Certificates, passwords, identity and access (VCF SSO), and fleet settings.
- **Licensing.** Licences and registration, usage reporting and, in 9.1, License Servers.
- **Inventory > VCF Instance.** Per-instance actions such as workload domain creation, backup settings and network settings.

## Deployment models

VCF Operations has three deployment models:

- **Simple:** a single node.
- **High availability:** in practice a primary, a replica and a data node, with a load balancer FQDN.
- **Continuous availability:** listed in the 9.1 design guidance for stretched designs.

The VCF Installer UI applies a single choice of Simple or HA to VCF Operations, VCF Automation and NSX together. The JSON method lets you choose per component, and William Lam shows how to mix them.

Size it from the official sizing guide (<KB id={397782} />) against the number of objects you will monitor. Then add headroom, because the console now carries lifecycle and licensing work as well as monitoring.

## Cloud proxies are part of the design

The cloud proxy is not optional plumbing. The VCF adapter that reads SDDC Manager runs on it, as do the vCenter and NSX adapters. If the management domain's cloud proxy is offline, even the SSO configuration page fails to load (<KB id={437258} />). In 9.1 a cloud proxy must exist in the first instance before management services are deployed. The upgrade guide names a *unified* cloud proxy of Small or Standard size for this (<KB id={440630} />).

Plan at least one cloud proxy per instance. Put it on the management network, give it DNS records, and include it in backups.

## What happens when it is down

<Callout type="field">
Write this into the operations runbook before go-live, because it is the first question a customer asks after their first outage.
</Callout>

- **Workloads:** unaffected.
- **Licensing:** existing licences stay valid, but new assignments and capacity updates are blocked. An environment still in evaluation, or waiting on a renewal, is at risk if the outage lasts past the evaluation window (<KB id={443240} />).
- **Lifecycle and configuration:** there is no lifecycle UI, and you cannot make certificate, password, SSO or fleet DNS and NTP changes.
- **Monitoring:** alerts and dashboards are lost. In 9.1, log ingestion continues but log search is unavailable.
- **SSO:** users can still sign in, because the identity broker is a separate service.

## Pitfalls

- **Sizing for monitoring only.** The console now also runs lifecycle and licensing. Choose HA for production unless you have a strong reason not to.
- **Treating a 5.2 upgrade as "Aria is optional, so skip it".** The upgrade will deploy VCF Operations and fleet management if they are not there. Prepare IP addresses, DNS records and certificates for them in advance.
- **Forgetting the cloud proxy in firewall and DNS plans.** A proxy that can resolve and reach everything is the difference between a working console and a confusing "Failed" status on every adapter (<KB id={443680} />).
