<InShort>
VCF 5.x introduced the Express Storage Architecture (ESA). 5.2 added vSAN Max and ESA stretched clusters. In 9.x, ESA is the default for new clusters and the base for every new capability: global deduplication, vSAN-to-vSAN snapshot replication, and storage clusters, which are the renamed vSAN Max. The Original Storage Architecture (OSA) is **not deprecated** in 9.0, and Broadcom says plainly that you can keep using qualifying OSA hardware through the upgrade. Decide on ESA by hardware and features, not by fear that OSA is about to disappear.
</InShort>

## How to decide

**Start with hardware.** ESA has much stricter requirements than OSA: NVMe-based ReadyNodes and fast networking. Check whether existing OSA hosts qualify. If they don't, the decision is already made for this hardware generation. Upgrade to 9.x on OSA and plan ESA with the next hardware refresh.

**Then ask which 9.x features you need.** The features worth paying for are ESA-only: global deduplication, cluster-to-cluster snapshot replication with short recovery points, and the newer storage cluster capabilities. If none of them matter to the customer this year, OSA on supported hardware is a defensible design.

**Then plan the move.** 9.1 makes migration much easier. OSA clusters, ESA clusters and compute-only vSphere clusters can now mount remote vSAN datastores of either architecture. You can mount a new ESA storage cluster from the old OSA cluster, vMotion or Storage vMotion the workloads across, and decommission the OSA cluster without a big-bang cut-over. The VCF blog describes both the HCI-to-HCI and the HCI-to-disaggregated patterns.

## Related 9.x storage changes that affect designs

- **vVols are deprecated.** Removal is planned in a later 9.x release. Do not design new vVols dependencies, and plan to move vVols workloads to VMFS or vSAN.
- **NPIV is removed** in 9.0. Some storage features are also cut back: Storage DRS I/O load balancing and the per-datastore Storage I/O Control components are gone. Space-based balancing and SPBM limits remain.
- **4Kn NVMe** devices are supported on ESA but not on OSA.
- **NFS** gains space reclamation through the VAAI plugin and Kerberos encryption for NFS 4.1.

<Callout type="field">
In an upgrade assessment, settle hardware before ESA or OSA: check that every host, controller and firmware combination is on the 9.x compatibility list. What the hardware supports narrows the architecture choice.
</Callout>

## Pitfalls

- **Assuming 9.x forces ESA.** It does not. Upgrading on OSA is a supported path.
- **Turning on limited-availability features in production.** Global deduplication was limited availability in 9.0, gated by approval and not supported on stretched clusters. Check its current status in the release notes before designing around it.
- **Missing vVols during discovery.** A vVols datastore found late in an upgrade project becomes a migration project of its own. Inventory storage types on day one of the assessment.
