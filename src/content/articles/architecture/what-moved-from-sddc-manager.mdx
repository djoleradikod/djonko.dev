<InShort>
Keep SDDC Manager in the design and stop building on its console. In 9.1 lifecycle, workload domain and password work starts in VCF Operations, while SDDC Manager [still provides](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/vcf-management-appliances.html) core lifecycle for ESX, vCenter, HCX and NSX behind it. Its UI has been [deprecated since 9.0](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes.html), and its APIs are shrinking too, so move runbooks and scripts now. The appliance itself still needs planning, credentials and care.
</InShort>

## Why it stays in the design

The 9.1 components page calls SDDC Manager ["a part of VCF Operations"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/vcf-management-appliances.html) that supports four functions there: lifecycle for ESX, vCenter, HCX and NSX, workload domain deployment, import of vCenter instances as workload domains, and vSAN stretched cluster configuration. Plan one per instance. The [9.1 design requirements](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-library/vcf-operations-design/sddc-manager-design.html) place it in the first availability zone of the management domain, on the VM management network, and justify that by saying creating workload domains and patching and upgrading depend on it. Its service accounts on vCenter, NSX and ESX, the `svc-sddc-manager-…` and `svc-vcf-…` entries in the [accounts table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html), are what make the lifecycle work possible. Disk space, its services and its certificates still matter, and a failed SDDC Manager stops core upgrades. For what an outage takes down, use the [failure impact matrix](/vcf/library/architecture/failure-impact-matrix/).

The 9.0 sources look contradictory until you separate screen from execution. The [product support notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes.html) say SDDC Manager's lifecycle capabilities moved to VCF Operations, and Brandon Hahn's [September 2025 list](https://blogs.vmware.com/cloud-foundation/2025/09/18/10-vmware-cloud-foundation-9-enhancements-simplifying-your-day-2-operations/) says new workload domains deploy through VCF Operations, yet the [9.0 design page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/design/design-library/vcf-operations-design/sddc-manager-design.html) has SDDC Manager using binaries to deploy those domains and to patch and upgrade them. The console moved and the work stayed. That reading is an inference for 9.0, and the 9.1 components page states it outright.

Two ties between VCF Operations and SDDC Manager matter here, and public KBs show both failing.

**The service account.** In 9.1, lifecycle requests that start in VCF Operations pass through SDDC lifecycle, running on the services runtime, and arrive at SDDC Manager as API calls. The [accounts table](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) gives SDDC lifecycle an administrator account on SDDC Manager, `svc-vcf-sddc-lcm-SDDC_MANAGER-<uuid>`, system managed, rotated every 30 days by default and expiring in 90. On VCF, multiple rotations, scheduled or on-demand, delete the SDDC lifecycle service accounts. Upgrades then fail at `post_upgrade_inventory_sync` or `vmsp_upgrade`, and repeated 401s can lock the runtime nodes out of SDDC Manager with `CLIENT_IP_BLOCKED`. The recovery is a pair of scripts run from a runtime control-plane node (<KB id={450375} />, 3 Nov 2026). When a management upgrade fails at either step, check this account first.

**The VCF adapter.** VCF Operations reads the instance through the VCF adapter on a cloud proxy, which calls the SDDC Manager API. On 9.0.x, a communication timeout between the adapter and SDDC Manager services blanks the SDDC Manager page in VCF Operations, stops cloud proxy collection and marks the adapter Failed (<KB id={443680} />, 23 Jun 2026). On 9.1.1, a secondary instance running a newer version than VCF Operations [may not appear as a VCF adapter](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) until the versions match, so upgrade VCF Operations first.

[Hahn's list](https://blogs.vmware.com/cloud-foundation/2025/09/18/10-vmware-cloud-foundation-9-enhancements-simplifying-your-day-2-operations/) is the best single account of where each task went in 9.0, and the 9.1 pages below update it for DNS and NTP.

- **To VCF Operations:** workload domain deployment, backup configuration, certificate authority configuration, certificate management with auto-renewal, and [password management](/vcf/library/day-2/passwords-service-accounts/). Importing a vCenter as a workload domain [also starts here](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs). DNS and NTP moved in 9.0, and 9.1 changes the model: you create a named setting under Manage > Fleet management > Fleet settings and assign it to instances ([DNS](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-external-infrastructure-services/update-dns-server-configuration.html), [NTP](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-external-infrastructure-services/update-ntp-server-configuration.html)).
- **To vCenter:** network pools, host commissioning and decommissioning, cluster creation and expansion, and NSX edge cluster deployment. The 9.1 tasks for [commissioning](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/host-management/commission-hosts.html) and [adding a cluster](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/building-your-private-cloud-infrastructure/working-with-workload-domains/expand-a-workload-domain/add-a-cluster-to-a-workload-domain-using-the-sddc-manager-ui.html) need access to the management domain vCenter, or VCF SSO with vCenter linking. Both pages still name the SDDC Manager UI as an alternative, which can help while SSO and linking aren't ready, but don't write it into a new runbook.
- **To the software depot:** binaries. The [9.0 design page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/design/design-library/vcf-operations-design/sddc-manager-design.html) gives SDDC Manager connected, disconnected and manual modes for them. In 9.1 the depot [handles binaries for all VCF components](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/lifecycle-management.html).
- **To fleet lifecycle and SDDC lifecycle:** what Aria Suite Lifecycle did. VCF Installer and VCF Operations [replaced SDDC Manager's Aria deployment](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes.html) in 9.0, and the [9.1 mapping](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/vcf-management-appliances.html) splits the 9.0 fleet management appliance into those two components. <a href="/vcf/library/architecture/aria-lifecycle-to-services-runtime/">From Aria Suite Lifecycle to the services runtime</a> has the detail.

## What to do with scripts

Anything that calls SDDC Manager's password, certificate or identity APIs is on deprecated ground from 9.0 ([password and certificate](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes/product-support-notes-installer.html), [identity](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/release-notes/vmware-cloud-foundation-90-release-notes/platform-product-support-notes.html)), and `/v1/system/precheck` is already gone. [9.1 marks 21 more operations](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/vcf-91-product-support-notes.html) as deprecated, mainly edge cluster operations, domain overlays, system DNS and NTP, and upgrade prechecks. Those notes don't name the 21, so diff your scripts against the "What's changed in SDDC Manager API" changelog they point to. Scripts that commission hosts or rotate passwords through old SDDC Manager API calls can still work in places, but they bypass the 9.x workflows and can leave VCF Operations out of step.

For certificates the 9.1 fleet management blueprint is blunt: ["Avoid using the SDDC Manager for certificate management"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/certificate-management/recommendations-for-vcf-certificate-management.html), with SDDC Manager's APIs kept only for backward compatibility during the transition.

<Callout type="analysis" title="How far the deprecation reaches">
The 9.1 page on using SDDC Manager for passwords goes further than the release notes: ["SDDC Manager will be deprecated in a future VCF release"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords.html). The notes name the UI and specific APIs, and the 9.1 components page still gives the appliance four functions. No removal date or replacement for those functions appears in the pages reviewed for this note <AsOf date="2026-11-07" />. So write no new dependency on SDDC Manager's interfaces, and keep sizing, protecting and upgrading the appliance as a required component.
</Callout>

## Passwords: where SDDC Manager stays in the runbook

VCF Operations is [the preferred method](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords.html) in 9.1, and its action is Update. Rotate, which auto-generates a password on server and client, is [only available in SDDC Manager](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/using-sddc-manager-to-manage-passwords.html), so a runbook that needs a generated value still lands there. The same blueprint also recommends [enabling SDDC Manager auto-rotation](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) for inter-component accounts that only SDDC Manager can manage, at 30, 60 or 90 days, and alerting on credential retrieval from SDDC Manager through its API or CLI, which needs Log Management deployed. Turn on both.

Two older KBs describe an earlier split. <KB id={435599} /> (VCF 9.x, 13 Apr 2026) calls SDDC Manager's password subsystem the authoritative source for account lifecycles, and the 9.1 passwords page, dated 5 Nov 2026, prefers VCF Operations, so on 9.1 follow the newer page. <KB id={426872} /> (9.0.x, 29 Jan 2026) shows the 9.0 limit: no Rotate on the VCF Operations Passwords page, and no configurable rotation for Fleet Management, VCF Operations, its logs and networks products, or VIDB. <KB id={435599} /> puts those same five outside automated rotation.

SDDC Manager's own passwords changed in a point release. On 9.1 you change the `root` and `vcf` passwords in the OS and the `admin@local` password through its API. [From 9.1.1](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html) all three can be managed from the VCF Operations UI or API, as [the release notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) confirm, so update the runbook in the same change window as the upgrade.

<Callout type="warn" title="Don't let a PAM tool change these accounts">
Internal service accounts ["must not be rotated, changed, or managed by external Privileged Access Management (PAM) tools"](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/manage-passwords/accounts-in-vmware-cloud-foundation.html), because changes outside VCF Operations or SDDC Manager workflows can break lifecycle and cause outages. The [password blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/fleet-management-blueprint/vcf-password-management/recommendations-for-vcf-password-management.html) wants all VCF credentials in an enterprise vault when you use API or manual processes, and calls the vault the source of truth. Those fit together if the vault records what VCF generated and never drives the change. That's an inference, since Broadcom doesn't reconcile them.
</Callout>

## Identity: set up both paths

[VCF SSO excludes SDDC Manager and ESX](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/fleet-management/managing-identity-and-access-using-vcf-single-sign-on/what-is/points-to-consider-while-setting-up-vmware-cloud-foundation-sso.html), and after you configure it in the management domain vCenter the SDDC Manager UI accepts only local admin accounts such as `@vsphere.local` users. Keep those credentials where a break-glass process can reach them. The APIs do take SSO users. Some actions you start in the vSphere Client run on SDDC Manager behind the scenes, so when you configure SSO, grant Administrator in SDDC Manager to the same SSO group you use in vCenter, as Eric Gray's [June 2025 post](https://blogs.vmware.com/cloud-foundation/2025/06/19/streamline-administrative-access-with-vcf-single-sign-on/) advises.

An upgrade from 5.2 needs SDDC Manager's API once more: the same considerations page requires that API to deactivate Enhanced Linked Mode on upgraded vCenter instances, and removing the link outside SDDC Manager blocks some workflows until you reconcile the drift through that API.
