<InShort>
**Go** when memory runs out before CPU, peak active memory stays at or below 50% of host DRAM with a host or site already failed, and the cluster runs 9.1.1 on a percentage or failover-host HA policy. **Buy hosts** otherwise. In the constructed example below, tiering removes 3 of 8 hosts when active memory is 25% of consumed memory, 1 at 50%, none above 51%, and costs an extra host at 60%. Read vendor savings of 40 to 45% as ceilings. The one figure with itemised prices, commissioned by Intel, is 35% on memory and 20% on the whole server.
</InShort>

For how tiering works, read Duncan Epping's [FAQ on Yellow Bricks](https://www.yellow-bricks.com/2026/07/16/memory-tiering-considerations-and-frequently-asked-questions/) (16 July 2026). It covers the mechanism, large pages, RAID-1 and per-VM settings.

## The checks, in order

Work down in order, because row 4 feeds row 3. Rows 1 and 2 can end the case; the rest send you to a fix.

| Test | Threshold and source | If it fails |
|---|---|---|
| 1. Does memory bind before CPU? | Hosts needed for memory on DRAM alone must exceed hosts needed for CPU. [Lenovo](https://lenovopress.lenovo.com/lp2518.pdf) says keep host CPU below 75%. The [9.1 performance guide](https://www.vmware.com/docs/vsphere-esxi-vcenter-server-9-1-performance-best-practices) says only "enough CPU headroom". | Stop. No hosts come out. |
| 2. Will hosts reach 80% of DRAM? | Pages move only from about 80% DRAM consumed (<KB id={449016} />), and the threshold can't be changed (Epping). | The tier idles. Buy it only as failover capacity. |
| 3. Peak active memory at or below 50% of DRAM, per surviving host? | 50% ideally, though some workloads hold until about 75% (performance guide). | Add hosts or buy DRAM. Use 50 to 75% only after testing your workload. |
| 4. Counted the VMs that won't tier? | High latency sensitivity, "Reserve all guest memory", `sched.mem.enableTiering` FALSE (<KB id={448305} />, written for 9.0). FT and passthrough (Epping). | Count them in full against DRAM, then redo row 3. |
| 5. Does the device qualify? | At least DRAM size ([TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vsphere/vsphere/9-1/vsphere-resource-management/memory-tiering-over-nvme/memory-tiering-considerations-and-best-practices.html)). 3 DWPD, 100,000 writes per second, read latency ideally below 200 µs (performance guide). 4 TB partition limit (Epping, [Morera](https://blogs.vmware.com/cloud-foundation/2025/12/02/nvme-memory-tiering-design-and-sizing-on-vmware-cloud-foundation-9-part-3/)). | Change the device. The 4 TB limit stops 1:1 above 4 TB of DRAM and 1:4 above 1 TB. |
| 6. Is HA tier-aware? | 9.1.1, percentage or dedicated failover hosts policy, DRS on. | On 9.1 or earlier, check DRAM by hand. On slot policy, switch. |
| 7. If stretched, is normal running low enough? | Normal-running active memory at or below 25% of DRAM (worked below). | Add hosts per site or stay on DRAM. |

Measure rows 1 and 3 with [MTAT](https://blogs.vmware.com/cloud-foundation/2026/07/31/meet-mtat-your-zero-friction-path-to-memory-tiering-in-vmware-cloud-foundation-9-0/) on its 30-day lookback, at statistics level 2, so month-end runs are included. Morera's post doesn't mention host failure or stretched clusters, so divide active memory by surviving hosts yourself.

## Worked example

This example is constructed, so replace each number with your own.

- **Hosts:** 32 cores, 1,024 GB of DRAM, 1:1, so 2,048 GB presented.
- **Workload:** 6,000 GB consumed, 80 cores of CPU demand, all VMs tier.
- **Limits:** fill to 90% of presented memory, one spare host, 512 GB active per surviving host (the 50% limit).

On DRAM alone, 6,000 ÷ 921.6 = 6.51, so 7 + 1 = **8 hosts, 256 cores**. Tiered, memory asks for 6,000 ÷ 1,843.2 = 3.26, so 4 + 1 = 5 hosts. Active memory sets its own floor: active GB ÷ 512, rounded up, plus 1. The higher floor wins.

Active share means share of the 6,000 GB consumed. Bracketed figures are shares of one host's DRAM, the 50% limit's base, and every row clears that limit because the active floor adds hosts.

| Active share | Active GB | Active floor | Tiered hosts | Active per host, one failed | Hosts saved | Cores saved |
|---|---|---|---|---|---|---|
| 25% | 1,500 | 3 + 1 = 4 | 5 | 375 GB (37%) | 3 | 96 |
| 40% | 2,400 | 5 + 1 = 6 | 6 | 480 GB (47%) | 2 | 64 |
| 50% | 3,000 | 6 + 1 = 7 | 7 | 500 GB (49%) | 1 | 32 |
| 60% | 3,600 | 8 + 1 = 9 | 9 | 450 GB (44%) | **−1** | **−32** |

The saving ends at 3,072 GB active (6 × 512), or 51% of consumed. Past 3,584 GB (7 × 512, 60%), tiering costs a host. CPU can end it sooner: at a 75% ceiling each surviving host gives 24 cores, so demand above 144 cores needs 8 hosts anyway.

Count two things against the 25% row's saving: five NVMe devices, ten if mirrored, and on VCF a [vSAN entitlement](/vcf/library/value/vsan-entitlement/) that falls from 256 to 160 TiB, 96 TiB less, at 1 TiB per core (<KB id={313548} />).

Now suppose active memory turns out higher than measured and you've kept the 5-host design. At 40% active, hosts run 480 GB (47%) and pass, then reach 600 GB (59%) with one failed, over the 50% limit. At 60%, they run 720 GB (70%), then 900 GB (88%), past the 75% the performance guide mentions.

<Callout type="analysis" title="The failure is slowness, and HA won't report it">
HA's [percentage policy](https://techdocs.broadcom.com/us/en/vmware-cis/vsphere/vsphere/9-1/vsphere-availability/creating-and-using-vsphere-ha-clusters/vsphere-ha-admission-control/cluster-resources-percentage-admission-control.html) sums each VM's reservation plus overhead, uses 0 MB where no reservation is set, and asks only overhead of a tiered VM in DRAM. That page doesn't list active memory as an input. The inference from those rules is that both cases can restart every VM on green status, then run slowly while the cluster is already degraded.
</Callout>

## What 9.1.1 changes for HA

Through 9.1, HA treated DRAM and NVMe as one pool, so restarts could fail for lack of DRAM while status stayed green, which [Broadcom's page](https://techdocs.broadcom.com/us/en/vmware-cis/vsphere/vsphere/9-1/vsphere-availability/creating-and-using-vsphere-ha-clusters/vsphere-ha-admission-control/memory-tiering-and-ha-admission-control.html) calls a "silent failure".

From 9.1.1, a VM is admitted only if total memory and DRAM both pass, and a non-tiered VM needs reservation plus overhead in DRAM. [In auto mode](https://techdocs.broadcom.com/us/en/vmware-cis/vsphere/vsphere/9-1/vsphere-availability/creating-and-using-vsphere-ha-clusters/vsphere-ha-admission-control/cluster-resources-percentage-admission-control.html), the DRAM reservation is the DRAM of the n largest hosts. In manual mode, your percentage applies to each pool. Stay off the slot policy, which Broadcom says not to use with tiering. Two limits come from [Epping](https://www.yellow-bricks.com/2026/09/22/memory-tiering-aware-vsphere-ha-admission-control-in-vcf-vsphere-9-1-1/) and aren't on the TechDocs page: the logic needs DRS on, and it "does not work when vCenter is unavailable and the SPE is used" (his abbreviation, unexplained).

<Callout type="analysis" title="Design consequences">
Re-run capacity after the upgrade, because the non-tiered DRAM check is new, so a cluster green on 9.1 may refuse power-ons on 9.1.1.

A healthy cluster may also trip the violation check. In the 5-host example, auto mode reserves 20% of DRAM, and tiering begins with 20% free. HA raises a configuration issue when "actual DRAM utilization", a term the TechDocs page doesn't define, drops available DRAM below the reservation, and the FailoverResource violation check runs every 5 minutes. If the term means consumed memory, a working tiered cluster sits on that line. Check on a non-production cluster.
</Callout>

## Stretched clusters: size for site loss yourself

Tiering makes no allowance for a stretched cluster typically run at or below 50% consumed: "Currently memory tiering does not take that scenario into consideration," Epping's FAQ says <AsOf date="2026-11-06" />.

<Callout type="analysis" title="Site loss doubles active memory per host">
Constructed again, same workload, no spare host per site. Each site must carry everything: 4 tiered hosts per site (6,000 ÷ 1,843.2), so 8 against 14 on DRAM.

Failover doubles active memory per host, so 50% of DRAM after failure means 25% before it. At 40% active share, normal running shows 300 GB (29%) and passes an assessment, then site loss gives 600 GB (59%). Five hosts per site fixes it at 480 GB (47%), 10 hosts against 14.

In normal running each host holds 750 GB, 73% of DRAM, so the tier stays empty. With a site lost, each holds 1,500 GB and the tier takes its first pages during the outage, so include that state in failover tests.
</Callout>

Lenovo's brief conflicts with itself. Its outcomes list claims "more than 90 percent performance retention" at double density, and its results table shows 80 to 90% of DRAM-only throughput for SQL Server and 76 to 82% for MongoDB. Its one dollar example, credited to VMware, is about $205,000 against $318,000. It calls that "close to 40 percent"; the arithmetic gives 35.5%.

None of the five figures above comes from an independent study. Enter your own quotes in MTAT, which Morera says covers chassis and memory media only, then add licensed cores from your host count.

## Device failure and health

Without RAID-1, losing the device is like a DIMM failure with an HA restart, Epping says. RAID-1 also works in software from 9.1, he says, but a mirrored pair means a second device per host. Plan replacement when Available Spare reaches 10%, William Lam suggests in his [note](https://williamlam.com/2026/09/quick-tip-improved-nvme-tiering-device-health-monitoring-in-vcf-9-1.html) on the health report (22 September 2026).
