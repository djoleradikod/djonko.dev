<InShort>
Memory tiering adds an NVMe device to each host as a second, slower tier of memory. ESX keeps frequently used ("hot") pages in DRAM and moves rarely used ("cold") pages to NVMe. The default ratio is **1:1**, so a host with 1 TB of DRAM presents 2 TB of memory to VMs, and the ratio can be raised to 1:4. It works when the **active** memory of the workloads fits comfortably in DRAM: the guidance is 50% of DRAM or less. Memory is not licensed, so the gain is fewer hosts, and therefore fewer licensed cores, for clusters that run out of memory before CPU. It is available in VCF and VVF.
</InShort>

## How it works

ESX tracks how recently and how often each memory page is touched. Tiering starts when host DRAM consumption reaches about **80%**. Below that, nothing moves to NVMe, so a host at 70% shows no tier-1 use at all (<KB id={449016} />). Above it, ESX scans for cold pages and moves them to the NVMe partition, and the scan rate rises with memory pressure. When a VM reads a page that sits on NVMe, the page comes back to DRAM.

The cost of a cold page access is the NVMe latency, roughly a hundred microseconds against well under a microsecond for DRAM. That is acceptable for pages that are rarely touched and harmful for pages that are touched constantly, which is why the active memory figure decides whether tiering suits a workload.

## Requirements and limits

| Item | Guidance | Source |
|---|---|---|
| Active memory | 50% of DRAM or less. Some workloads tolerate up to about 75%. | Performance best practices, 9.0 |
| NVMe read latency | Under 200 µs ideally, up to about 400 µs for tolerant workloads | Performance best practices, 9.0 |
| Device | At least 100,000 writes per second and 3 drive writes per day, listed in the compatibility guide | Performance best practices, 9.0 |
| Partition size | Up to 4 TB. Buy at least as much NVMe as DRAM, more for higher ratios. | Design and sizing, part 3 |
| Encryption | Optional, per VM or per host, with a host-generated key. No key provider needed. | Design and sizing, part 2 |

Without mirroring, an NVMe device failure affects only VMs whose cold pages were on that device, and only when those pages are next read. The host keeps running. Decide whether that risk is acceptable for the cluster, or use mirroring in 9.1.

## Which VMs do not tier

Some VM settings stop a VM from placing pages on NVMe even when the host is tiering (<KB id={448305} />):

- Latency sensitivity set to High.
- "Reserve all guest memory" selected.
- Nested hardware virtualisation (`vhv.enable`) in 9.0. 9.1 supports nested virtualisation with tiering.
- `sched.mem.enableTiering` set to FALSE in the VM's advanced settings.

Linux guests that use the page cache heavily, the KB uses RHEL 8 as the example, can keep most pages active, so little or nothing moves to NVMe. That is correct behaviour, not a fault, but it means those VMs gain nothing from the tier and should be counted at their full size in a sizing exercise.

## Measuring before you buy

The Memory Tiering Assessment Tool (MTAT) reads vCenter performance history and reports, per VM and per host, whether active memory sits below the 50% threshold. It also estimates NVMe size for a chosen ratio. It needs read access to vCenter and statistics level 2 or higher for the history to be complete. Collect at least a month of data covering month-end or any other peak, because the active memory figure that matters is the one at the busiest time.

On a host already tiering, check per-VM figures with:

```bash
memstats -r vmtier-stats -u mb -s name:memSize:active:tier1Target:tier1Consumed
```

## Worked example: a memory-bound cluster

This example is constructed. Each host has two 16-core CPUs and 1,024 GB of DRAM. The workloads need **6,000 GB** of configured memory and **80 physical cores** of CPU demand. Planning assumptions: hosts are filled to 90% of their presented memory, the cluster tolerates one host failure, and measured active memory is **25%** of configured memory (1,500 GB). That last figure must come from your own data.

| | DRAM only | Tiered 1:1 |
|---|---|---|
| Memory presented per host | 1,024 GB | 2,048 GB |
| Usable per host at 90% | 922 GB | 1,843 GB |
| Hosts for 6,000 GB, plus one | 7 + 1 = 8 | 4 + 1 = 5 |
| Licensed cores | 256 | 160 |
| CPU use in normal running | 31% | 50% |

Check the tiered design with one host failed. Four hosts carry 1,500 GB of active memory, 375 GB each, which is 37% of DRAM and inside the 50% guidance. CPU demand is 80 of 128 cores, or 62.5%. Both are acceptable, so the design removes three hosts and 96 licensed cores. It adds five NVMe devices of at least 1 TB, or ten if they are mirrored.

Two cautions. The saving exists because CPU had headroom: if the same cluster were CPU-bound, tiering would not remove a host. And the cluster's vSAN entitlement falls from 256 to 160 TiB with the cores, so recheck storage against the [vSAN entitlement](/vcf/library/value/vsan-entitlement/).

## What the vendor results say

Broadcom's published benchmarks at 1:1 report twice the VM density with performance losses of 0 to 8% for VDI, about 5% for VMmark and Oracle, and 5 to 10% for HammerDB on SQL Server and MySQL. Broadcom also quotes "up to 40%" lower total cost of ownership without publishing the model behind it. Use the benchmarks as an indication of the overhead and build the cost case from your own host counts.

## Pitfalls

- **Sizing on allocated instead of active memory.** Allocated memory tells you whether tiering is worth considering. Active memory tells you whether it will work.
- **Consumer-grade NVMe.** The tier writes continuously under pressure. Endurance below the guidance wears out devices early.
- **Sharing a vSAN device.** The design series advises caution. Keep tiering devices separate from vSAN ESA devices.
- **Raising the ratio without data.** 1:2 and 1:4 suit workloads with low active memory, such as some VDI pools. Move to them only after measuring.
