<InShort>
A cluster that must survive a host failure keeps a host's worth of capacity in reserve, and that reserve is licensed like any other core. Two four-host clusters hold two hosts in reserve. One seven-host cluster running the same work holds one. Merging small clusters, where nothing forces them apart, is one of the simplest ways to remove a host. In 9.x two further levers apply: 9.1 lets compute-only clusters mount remote vSAN storage, so compute and storage can grow separately, and fewer VCF instances means fewer management stacks to run.
</InShort>

## The reserve is per cluster

HA admission control holds back capacity so that VMs from a failed host can restart elsewhere. With the cluster resource percentage policy you set that reserve directly. With one host failure to tolerate, the reserve is roughly one host's share of the cluster, which is a quarter of a four-host cluster and an eighth of an eight-host one.

### Worked example: merging two clusters

This example is constructed. Two clusters of four hosts each, every host with two 16-core CPUs. Each is designed for one host failure, so each runs on three hosts' worth of capacity.

| | Two clusters | One merged cluster |
|---|---|---|
| Hosts | 4 + 4 = 8 | 7 |
| Usable hosts with one failure | 3 + 3 = 6 | 6 |
| Licensed cores | 256 | 224 |

The merged cluster delivers the same usable capacity with one host fewer, 32 cores less to license. The calculation holds only if nothing requires the two clusters to stay separate. Check for:

- **Separation required by someone else's licence.** Some database and operating system vendors license by the hosts a VM could run on. Moving those VMs into a larger cluster can raise that cost by more than the host saved.
- **Compliance boundaries.** Payment card or classified workloads may need their own cluster by policy.
- **Hardware mismatch.** Different CPU generations need EVC, and vSAN clusters need compatible devices and the same architecture.
- **Failure tolerance.** A larger cluster loses the same single host, but a cluster-wide problem now affects more workloads. Consider whether one larger failure domain is acceptable.

## Choose the capacity model deliberately

VCF Operations can plan capacity by **demand**, from measured use, or by **allocation**, from configured sizes and overcommit ratios such as 8 vCPUs per core. Demand-based planning usually fits more work on each host. Allocation-based planning is easier to explain to application owners and protects against everyone using their full allocation at once. Neither is wrong, but the ratio you choose sets the host count. A cluster planned at 4 vCPUs per core needs twice the cores of one planned at 8 for the same VMs. Pick the ratio from measured CPU ready time and contention at current density, then raise it in steps while watching those figures.

## Grow storage and compute separately

In an HCI cluster, more storage means more disks in the same hosts, and when the hosts are full it means more hosts, each with cores to license. The 9.1 storage cluster model lets compute-only and HCI clusters mount remote vSAN datastores of either architecture. A cluster that needs capacity but not CPU can take it from a storage cluster. Check how storage cluster hosts are licensed under your agreement before relying on this, since the comparison depends on it.

## Fewer management stacks

Each VCF instance carries its own management domain with SDDC Manager, vCenter and NSX. VCF Operations and VCF Automation are shared across a fleet. Every instance therefore costs management hosts, cores and patching effort before it runs a single workload. Before creating a new instance for a new site or team, check whether a workload domain in an existing instance meets the need. The [VCF 9 mental model](/vcf/library/architecture/vcf9-mental-model/) explains the fleet, instance and domain boundaries.

## Power

The default host power policy is Balanced, which saves energy at little performance cost for most workloads. The vSphere performance guide recommends setting the BIOS to OS-controlled power management so ESX can use the processor's power states. Distributed Power Management can power off hosts that are not needed and bring them back as load rises. It reduces energy cost, not licence cost, because the powered-off hosts remain licensed.

## Pitfalls

- **Removing the reserve to hit a target.** A cluster with no failover headroom turns the next host failure into an outage. Show the reserve in the business case rather than hiding it.
- **Consolidating before right-sizing.** Merge after [right-sizing](/vcf/library/value/rightsizing-with-vcf-operations/) and [reclamation](/vcf/library/value/reclaiming-idle-capacity/), or you will plan the merged cluster around waste.
- **Forgetting maintenance.** Patching takes a host out of service. A cluster sized exactly for one failure cannot tolerate a failure during patching.
