<InShort>
A VCF 9 subscription is priced per **physical core**, with at least 16 cores counted for every CPU, and it includes **1 TiB of raw vSAN capacity per core** (<KB id={313548} />). Memory is not licensed. Neither is the number of VMs. That gives the cost model its shape: anything that lets the same workloads run on fewer cores, or on less raw disk, reduces the subscription. Anything that reduces the hours spent keeping the platform running reduces the other large cost, which is people. The notes in this section take one lever each, explain the mechanism, and work an example with the assumptions written down.
</InShort>

## The cost lines and what moves them

The table below lists the recurring costs of a VCF estate in rough order of size for a typical on-premises deployment. The order is a generalisation. Your own split depends on hardware prices, staff costs and contract terms, so measure it before deciding where to start.

| Cost | What drives it | Lever | Covered in |
|---|---|---|---|
| Core subscription | Physical cores, with the 16-per-CPU floor | CPU choice, consolidation, fewer hosts | [Counting cores](/vcf/library/value/core-counting-and-cpu-choice/), [consolidation](/vcf/library/value/consolidation-and-headroom/) |
| vSAN add-on capacity | Raw TiB claimed by vSAN above the entitlement | Protection scheme, compression, deduplication | [vSAN entitlement](/vcf/library/value/vsan-entitlement/), [space efficiency](/vcf/library/value/vsan-esa-space-efficiency/) |
| Memory hardware | DRAM per host | NVMe memory tiering | [Memory tiering](/vcf/library/value/nvme-memory-tiering/) |
| Wasted allocation | Oversized and idle VMs holding capacity | Right-sizing and reclamation | [Right-sizing](/vcf/library/value/rightsizing-with-vcf-operations/), [reclamation](/vcf/library/value/reclaiming-idle-capacity/) |
| Separate tools | Monitoring, logging, self-service bought outside VCF | Use what the VCF licence already includes | [What VCF includes](/vcf/library/value/using-what-vcf-includes/) |
| Administration hours | Manual lifecycle, certificates, passwords | Fleet management automation | [Admin effort](/vcf/library/value/cutting-admin-effort/) |

## Why fewer cores is the main lever

Because the licence counts cores and not memory, VMs or storage performance, the subscription grows with the number of hosts you need. A cluster is sized by whichever resource runs out first. Where that resource is memory, cores are bought and licensed to carry DIMMs. Memory tiering, right-sizing and reclamation all attack that pattern from different directions. Each one lowers the memory or CPU you need to provision, and the saving only reaches the licence bill when it lets you remove or not buy a host.

The second point follows from the first. A saving that stays inside an existing cluster, such as reclaiming 200 GB of memory from idle VMs, has no licence value until it changes a purchase. Record reclaimed capacity against the next growth request or hardware refresh, so the saving turns into hosts not bought.

## Where administration time goes

The Google SRE book defines toil as work that is manual, repetitive, automatable and grows with the size of the service. Certificate replacement, password rotation, per-component patching and licence key management were all toil in 5.x. VCF 9 moves most of them into VCF Operations fleet management, where they can be scheduled or automated. The [admin effort note](/vcf/library/value/cutting-admin-effort/) lists what changed and how to measure the time it gives back.
