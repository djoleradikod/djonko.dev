<InShort>
Run right-sizing as a performance and cost review, and count only memory as capacity unless the cluster uses the allocation model. Under the default demand model, [removing vCPUs from an oversized VM reclaims 0 MHz, and memory counts only where consumed memory sits above the new size](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/). A single recommendation [moves a VM down by at most half or up by at most double](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/how-does-vmware-aria-operations-calculate-and-forecast-capacity.html), so the work recurs. [The 9.1 Rightsize page says workloads must restart to accommodate resizing](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/how-to-optimize-capacity-and-improve-performance/using-rightsize-to-adjust-resource-allocation.html), so each round needs a change window.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note gave the default recommendation window as 60 days, from a 2025 blog post. TechDocs for 9.1 gives a 120-day default warning threshold and a 150-day window. It also said cutting memory frees capacity under both models, but under the demand model memory counts only where consumed memory exceeds the new size.
</Callout>

## What a smaller VM frees

[Reclaimable capacity and cost impact depend on the capacity model of the parent cluster, not on the VM](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/). [Only the demand model runs by default, and the allocation model is switched on in the active policy](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/allocation-and-demand-model-in-workload-optimization.html). Kelcey Lemon's August 2025 post sets out the difference, and the table below follows it.

| | Demand model (default) | Allocation model (optional) |
|---|---|---|
| Judges a cluster by | What usage would have been without contention | Configured resources against overcommit ratios, such as 8:1 vCPU:core |
| Cutting vCPUs on an oversized VM | Reclaims 0 MHz, however many are removed, because the VM wasn't using them | Counts in cost impact as the recommended change |
| Cutting memory on an oversized VM | Reclaims consumed memory minus recommended size, and nothing if consumed is lower | Counts in cost impact as the recommended change |
| Potential savings | Reported when allocation is off | Replaces the demand figure once allocation is on |

This example is constructed, so replace each number with your own. A VM has 32 GB configured, 20 GB consumed and a 24 GB recommended size. The recommendation removes 8 GB, and the allocation model's cost figure counts all 8. The demand model reclaims nothing, because consumed memory is already under 24 GB.

Settle which model the capacity plan uses before the first review. If hosts are bought against overcommit ratios, for example when application owners request VM sizes from a catalogue, turn allocation on, since that is where vCPU cuts show up. If the plan is demand-based, report memory only and present vCPU cuts as performance work.

<Callout type="analysis" title="From reclaimed capacity to a smaller bill">
Neither figure is a licence saving by itself. VCF is [licensed on cores](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs), so a smaller VM changes the bill only when the reclaimed capacity removes a host or avoids buying one, and [core floors and order minimums](/vcf/library/value/core-counting-and-cpu-choice/) can absorb some of that. This is reasoning from public licensing material, and it isn't legal or purchasing advice. Check the terms in your own agreement.
</Callout>

Read dollar figures from a patched system. Before 9.1.1, [the Cluster CPU Base Rate used total cores instead of usable cores](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vcfoperations-9-1-1-0-release-notes.html) on clusters with the allocation cost model and the usable-capacity-after-HA-and-buffer model, which made VM cost metrics low. The same notes fix a $0 Potential Savings widget for reclaimable hosts on vCenter instances integrated through the VCF Management Pack.

The performance case is real but modest, and it should be pitched that way. The 9.1 guide says surplus vCPUs [might cause "slightly increased resource usage", potentially affecting performance on very heavily loaded systems](https://www.vmware.com/docs/vsphere-esxi-vcenter-server-9-1-performance-best-practices). A cut that brings a VM inside one physical NUMA node is also worth naming, because [wide VMs might see higher average memory access latency](https://www.vmware.com/docs/vsphere-esxi-vcenter-server-9-1-performance-best-practices), though the guide calls the advantage of fitting a node slight and limits it to some environments. Broadcom's own dashboard offers [CPU Ready and CPU Run Queue as the evidence to check](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/predefined-dashboards-in-vrealize-operations-manager/performance-dashboards/vm-rightsizing-dashboard.html), so bring those to the VM owner.

## What sets the number

Recommended Size is [the maximum projected utilization from now to 30 days beyond the time-remaining warning threshold](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/how-does-vmware-aria-operations-calculate-and-forecast-capacity.html). Lemon's post and TechDocs disagree on the defaults, so read your own policy before explaining a recommendation to anyone.

| | Lemon's post, August 2025 | 9.1 TechDocs, updated 5 Nov 2026 |
|---|---|---|
| Default warning threshold | 30 days | 120 days |
| Default Recommended Size horizon | 60 days | 150 days |
| Projection refresh | Every 5-minute collection cycle | Collected every 5 minutes, processed every 24 hours, recalculated at once on a policy or total-capacity change |
| Risk settings | Conservative, Aggressive, Peak Focused | [Slider from Aggressive to Conservative](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/configuring-policies/using-the-monitoring-policy-workspace/policy-workspace/policy-workspace-capacity-details.html), with all peak values under Conservative |
| Restart on resize | None with hot-add enabled | Workloads must restart |

The versioned page is the one to trust: the 120-day figure also appears in the [9.0](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-0/cost-and-capacity-management/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/how-does-vmware-aria-operations-calculate-and-forecast-capacity.html) and [Aria Operations 8.18](https://techdocs.broadcom.com/us/en/vmware-cis/aria/aria-operations/8-18/vmware-aria-operations-configuration-guide-8-18/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/how-does-vmware-aria-operations-calculate-and-forecast-capacity.html) pages, so the gap doesn't look like a change that came with a release. A longer horizon includes more projected growth, so a growing VM should get a larger recommendation at 150 days than at 60. That's an inference from the definition. Set the threshold to suit how often you resize, as Lemon advises. Since [some policy settings affect all object types](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/), give VMs their own policy.

Risk level picks the part of the projection used. [Conservative takes the upper bound and Aggressive the mean of the upper and lower bounds](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/how-does-vmware-aria-operations-calculate-and-forecast-capacity.html), and the [policy page](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/configuring-policies/using-the-monitoring-policy-workspace/policy-workspace/policy-workspace-capacity-details.html) assigns Conservative to production and Aggressive to non-critical workloads. The 9.1 release notes say the [configuration for conservative workloads was simplified](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/what-s-new/whats-new-vcf-ops.html) and the capacity algorithms updated, so a runbook that names Peak Focused needs checking against the 9.1 screen.

The inputs are [CPU demand, which excludes contention such as ready, co-stop and hyper-threading, and memory utilization from inside the guest, which accounts for swapping and paging](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/). [Without guest metrics from VMware Tools, the configured memory value is used instead](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/predefined-dashboards-in-vrealize-operations-manager/performance-dashboards/vm-rightsizing-dashboard.html). That suggests such a VM can't look oversized on memory, which is an inference, so fix Tools before trusting a clean result.

History decides how far to believe a recommendation. Lemon says to [review 6 months or more](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/), and the [recommendation view shows one to 12 months](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/how-to-optimize-capacity-and-improve-performance/using-rightsize-to-adjust-resource-allocation.html). [Recent data weighs most, momentary peaks don't affect the projection, sustained peaks fade unless they recur, and periodic peaks don't decay](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/how-does-vmware-aria-operations-calculate-and-forecast-capacity.html). The weighting is exponential decay, and the projection extends a year ahead. A month of data misses quarter-end and year-end peaks, and six months can miss a once-a-year event, so a VM sized for one belongs on the exclusion list until the engine has seen it.

The caps turn this into a recurring job. Broadcom's example is [an 8-vCPU VM that never passes 10%, which is recommended 4 rather than 1](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/capacity-optimization-concepts/how-does-vmware-aria-operations-calculate-and-forecast-capacity.html). A 32-vCPU VM that needs 1 takes five passes: 16, 8, 4, 2, 1.

## Plan a restart for every action

The 9.1 Rightsize page makes you [acknowledge a restart for oversized and undersized actions alike](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/how-to-optimize-capacity-and-improve-performance/using-rightsize-to-adjust-resource-allocation.html), and the action needs [Operational Actions activated in the vCenter cloud adapter](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/how-to-optimize-capacity-and-improve-performance/using-rightsize-to-adjust-resource-allocation.html). Plan on it for reductions: <KB id={335048} /> lists both CPU and memory hot-remove as unsupported. Its stated environment is ESXi 7.0, so treat that as the working assumption on 9.x unless your version's documentation says otherwise.

Lemon's post offers [resizing with no reboot when hot-add is enabled](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/), which applies to growth only. Don't enable hot-add to get it. The 9.1 performance guide says [activating CPU Hot Add deactivates vNUMA, and to activate it only if you expect to use it](https://www.vmware.com/docs/vsphere-esxi-vcenter-server-9-1-performance-best-practices). <KB id={321931} /> limits the vNUMA loss to hardware version 19 or earlier, a limit the guide doesn't state, and recommends disabling CPU Hot Add in production templates unless online resizing is a strictly validated requirement. Follow the KB's recommendation either way, and record the hardware version of any large VM that already has it on.

## What to keep out of the recommendations

Exclude by tag rather than by hand. The Rightsize page offers [tag-based exclusion rules and a minimum number of days of data before a VM is included](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/how-to-optimize-capacity-and-improve-performance/using-rightsize-to-adjust-resource-allocation.html), and [9.1 adds VM age and history, plus automatic exclusion of Broadcom appliances](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-0-0-release-notes/what-s-new/whats-new-vcf-ops.html). Record the reason for each one.

Three groups belong there:

- **Applications that manage their own memory.** Databases and Java heaps are the usual cases. The memory metric sees what the guest has handed over, not what the application needs inside it, so it can't tell you how much is spare. That's an inference from the metric's definition, and these VMs are better sized from the application's own counters.
- **VMs sized for an event that hasn't happened**, for the history reason above.
- **VMs whose real work runs at night, if the policy uses business hours.** [Recommendations under a business-hours schedule ignore spikes after hours](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/configuring-policies/using-the-monitoring-policy-workspace/policy-workspace/policy-workspace-capacity-details.html), so give them a separate policy.

Guest software licensed per vCPU needs one more check before any cut. Reducing vCPUs can lower third-party licence costs, which may be worth more than the infrastructure saving, and the performance guide calls [virtual socket and core layout "potentially relevant for software licensing"](https://www.vmware.com/docs/vsphere-esxi-vcenter-server-9-1-performance-best-practices). Read the vendor's terms first, because this note isn't licensing advice.

## A review cycle

[Broadcom's 9.1 design blueprint index](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for.html) has no entry on cost, capacity or VM sizing <AsOf date="2026-11-07" />, so this sequence is advice from this site, built from the pages above.

1. Run reclamation first. The [Oversized list includes idle VMs and VMs with snapshots](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/how-to-optimize-capacity-and-improve-performance/using-rightsize-to-adjust-resource-allocation.html), and [the cost method on this site](/vcf/library/value/building-the-cost-case/) explains why an idle VM shouldn't be counted twice.
2. Schedule the [two out-of-the-box Optimization Reports for oversized and undersized VMs](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/) monthly, by email.
3. Work per cluster, starting where capacity is tightest. The dashboard page says [analysis belongs at cluster level, with the focus on clusters low on capacity remaining](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/predefined-dashboards-in-vrealize-operations-manager/performance-dashboards/vm-rightsizing-dashboard.html).
4. Take undersized VMs to their owners first, since those VMs are already short of resources and the fix builds the trust you need for the reductions. [The VM's capacity tab and the VM Rightsizing Details dashboard](https://blogs.vmware.com/cloud-foundation/2025/08/12/vmware-cloud-foundation-helps-you-optimally-size-vms-and-keep-your-infrastructure-and-workloads-running-smoothly/) are the evidence to show them, including the cost increase.
5. Apply in a change window with Schedule Action, which [creates a job managed in Automation Central](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/cost-and-capacity-management/optimizing-capacity-and-improving-performance/how-to-optimize-capacity-and-improve-performance/using-rightsize-to-adjust-resource-allocation.html). Recurring jobs exist, and [failed ones run again at the next scheduled time](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/infrastructure-operations/configuring-automation-using-jobs/automation-central.html). Because each run restarts workloads, keep unattended recurrence away from anything an owner hasn't agreed to.
6. Record memory reclaimed against the next capacity request, and report allocation figures on a separate line. Then review the catalogue and template sizes, or new VMs will bring the same waste back.
