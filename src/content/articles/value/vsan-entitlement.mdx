<InShort>
**Add-on TiB is needed only when raw device capacity across the vSAN clusters in a pool exceeds it.** [Each VCF core brings 1 TiB and each VVF core 0.25 TiB](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/licensing-overview/add-on-licenses-in-vcf-9-0.html) <AsOf date="2026-11-07" />, usage is measured on raw capacity, and the capacity is shared between clusters. Protection overhead and data reduction never enter the count, so they change the bill only through the drives they make you install. The 9.1 Effective Capacity view [shows about half of raw](https://www.vmware.com/docs/vmw-vsan-space-efficiency) before data reduction, so the licence figure can't be read from it. Size the first purchase on a ratio measured on similar data, or on 1:1.
</InShort>

## What the licence counts

Broadcom [bases usage on the raw storage of the vSAN clusters](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/licensing-overview/add-on-licenses-in-vcf-9-0.html): add up physical device capacity across every ESX host in each cluster. Usage is recalculated when a host joins or leaves or the cluster's TiB changes, so adding a storage host is a licensing event. A half-empty 15.36 TB device counts in full, which makes drive size a licensing choice. Drives are sold in TB and licensed in TiB, and [one TB is about 0.909 TiB](https://lenovopress.lenovo.com/lp1265-vmware-software-solution-product-guide), so a 7.68 TB device contributes about 6.98 TiB.

Protection acts on the count indirectly, through the devices it makes you install. Auto-RAID in 9.1 [sets overhead at 1.5x on standard clusters, 3x on stretched and 2x on 2-node](https://blogs.vmware.com/cloud-foundation/2026/05/08/auto-raid-in-vsan-for-vcf-9-1/), according to Pete Koehler's May post, before compression and deduplication.

Get the raw figure from a tool rather than a capacity screen. [KB 313548](https://knowledge.broadcom.com/external/article/313548/counting-cores-for-vmware-cloud-foundati.html) says the product UI has no raw view, calls manual calculation from the UI inaccurate and supplies a PowerCLI counting tool, but its version list stops at 8.0 and VCF 5.1, and on vSAN 8.0 U3 it fails, so use the updated script in <KB id={400416} />. On 9.x, use the [Total Raw Physical Storage that VCF Operations reports](https://knowledge.broadcom.com/external/article/411654/error-vsan-addon-license-assignment-fail.html), the value that KB 411654 tells you to verify before comparing it with the license. In 9.1 the gap between screen and licence is wide: Koehler's example has [10 hosts with 394 TB raw showing 203 TB effective](https://www.vmware.com/docs/vmw-vsan-space-efficiency).

OSA estates have one more check. [Lenovo's guide excludes OSA cache devices from raw capacity](https://lenovopress.lenovo.com/lp1265-vmware-software-solution-product-guide), but it covers VCF 5 and VVF 8 and dates from April 2025, and Broadcom's 9.1 page speaks only of physical device capacity. Run the count on an OSA cluster before relying on the exclusion under 9.x.

The [vSAN 9.1.1.0 release notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes/vsan-9-1-1-0-release-notes.html) (3 Sep 2026) list no licensing or capacity change, so this note applies these rules to 9.1.1 too.

## How the pool behaves

A [500-core VCF subscription produces a separate 500 TiB vSAN license, and a 200 TiB add-on takes it to 700](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/licensing-overview.html). That default license pools all active subscriptions for the product under one Site ID. A second Site ID therefore has its own pool, which is an inference from that definition, so check where surplus sits before counting on it. Add-on capacity is still a separate purchase, listed among the Advanced Services in the [4 Nov 2026 FAQ](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs).

Surplus can cover other clusters inside the pool. Capacity is [shared between clusters on the TiB license, and VVF capacity pools with VCF and add-on capacity](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/licensing-overview/add-on-licenses-in-vcf-9-0.html). Cores in a compute cluster with no vSAN still bring their TiB, so count the whole estate before buying add-on capacity for one storage-heavy cluster. To place capacity deliberately, see [assigning licenses](/vcf/library/licensing/assigning-licenses/).

vSAN 8.x estates can't assume this. <KB id={440956} /> describes renewed keys that fail with "The license capacity is insufficient" on a second or third cluster, because standalone TiB keys and core-based entitlement can't be combined. Its fix is a non-technical support case and a merged key, so raise that before buying more capacity. [Lenovo's 2025 guide](https://lenovopress.lenovo.com/lp1265-vmware-software-solution-product-guide) also limits VVF capacity to VVF core licenses, so on those versions don't plan to cover a VVF cluster's shortfall from VCF surplus. The 9.1 page lets VVF and VCF capacity pool.

## Worked example: does this cluster need add-on TiB?

This example is constructed, so replace each number with your own. A six-host VCF 9.1 vSAN ESA cluster has two 16-core CPUs per host, so 192 licensed cores and **192 TiB** of entitlement. It must hold **120 TiB** of VM data after thin provisioning. [Auto-RAID uses RAID-6 4+2 at 1.5x on six or more hosts](https://www.vmware.com/docs/vmw-vsan-space-efficiency).

| Data reduction | Raw, 30% free | VCF add-on | VVF add-on | Raw, Broadcom estimate | VCF add-on |
|---|---|---|---|---|---|
| None (1.0:1) | 257.1 TiB | 66 TiB | 210 TiB | 240 TiB | 48 TiB |
| 1.5:1 | 171.4 TiB | none | 124 TiB | 160 TiB | none |
| 2.0:1 | 128.6 TiB | none | 81 TiB | 120 TiB | none |

The 30% columns use 120 ÷ reduction × 1.5 ÷ 0.7, with add-on as raw minus 192 TiB (VCF) or 48 TiB (VVF, 0.25 × 192), rounded up. The 30% is this site's planning margin for rebuilds, growth and policy changes, not a Broadcom figure. The estimate column uses [Broadcom's single-site table](https://www.vmware.com/docs/vmw-vsan-space-efficiency), where 1.5:1 gives roughly 0.75x of raw and 2:1 gives roughly 1x. That table starts at 1.5:1, so the 1:1 row is this site's extension of the same scale to 0.5x.

<Callout type="analysis" title="Which margin to use">
Broadcom's pages disagree on reserves. The [9.1 single-rack ESA blueprint](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/vcf-fleet-in-a-single-site-with-minimal-footprint-blueprint/management-domain-design-selections/virtual-infrastructure-layer/vsan-single-rack-hci-esa-storage-model.html), updated 5 Nov 2026, says to enable Reserved Capacity because it avoids "a generic 30% capacity overhead", with Host Rebuild Reserve at 25% on four nodes and 8% on twelve. The [space-efficiency paper](https://www.vmware.com/docs/vmw-vsan-space-efficiency) says those reserves are no longer relevant or available in the Effective Capacity view, and [Koehler's post](https://blogs.vmware.com/cloud-foundation/2026/05/11/effective-capacity-view-in-vsan-for-vcf-9-1/) says you can safely use all the free capacity it advertises.

The two fit if the paper governs Auto-RAID clusters and the blueprint's reserves govern clusters on the legacy view. That's an inference, and Broadcom doesn't state it. New clusters [get Auto-RAID by default, while upgraded ones keep their policies](https://blogs.vmware.com/cloud-foundation/2026/05/08/auto-raid-in-vsan-for-vcf-9-1/) until switched. So use the estimate column for a new Auto-RAID cluster and treat this site's 30% as a deliberate buffer of about 7% more raw, which a purchase that can't easily be topped up may justify. Run the [vSAN Sizer](https://vcf.broadcom.com/tools/vsansizer/home) that the blueprint names on the final design.
</Callout>

Drive size then decides whether you pay. At 1.5:1 with 30% free, each host needs 171.4 ÷ 6 = 28.6 TiB:

- Four 7.68 TB drives give 27.9 TiB per host, which is short.
- Five give 34.9 TiB per host and 209.5 TiB in total, 17.5 TiB over the entitlement.
- Nine 3.84 TB drives give 31.4 TiB per host and 188.6 TiB in total, 3.4 TiB under it.

On Broadcom's estimate, four 7.68 TB drives would pass, since 167.6 TiB raw × 0.75 holds about 125.7 TiB. Nine 3.84 TB drives pass on both margins and need no add-on, so on this site's reading they are the safer option at 1.5:1. The blueprint allows [up to 24 drives per node, from 1.6 TB](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/vcf-fleet-in-a-single-site-with-minimal-footprint-blueprint/management-domain-design-selections/virtual-infrastructure-layer/vsan-single-rack-hci-esa-storage-model.html). Device count also sets the component limit, which [the space-efficiency note](/vcf/library/value/vsan-esa-space-efficiency/) works through for this same cluster.

The ratio moves the answer more than either margin does. With no measured ratio this cluster needs 48 to 66 TiB of add-on. Broadcom [recommends a conservative estimate of compression on real data](https://www.vmware.com/docs/vmw-vsan-space-efficiency), and [deduplication results depend on how alike the data is](https://blogs.vmware.com/cloud-foundation/2025/06/19/global-deduplication-in-vsan-esa-for-vmware-cloud-foundation-9-0/). The paper's table runs to 8:1, but that is capacity arithmetic rather than a forecast. Treat any ratio you haven't measured as headroom. On a running ESA cluster, take the overall data reduction ratio from the capacity view, which the paper recommends over the separate compression and deduplication figures because those shift as deduplication runs.

A stretched version of this cluster is a different purchase. It has 3x overhead and no global deduplication, and the paper's stretched table gives roughly 0.38x of raw at 1.5:1. That means about 316 TiB raw and about 124 TiB of add-on, even if compression alone reaches 1.5:1.

## VVF is a different calculation

The same 192 cores bring 48 TiB on VVF, so this cluster needs 81 to 210 TiB of add-on with 30% free, or 72 to 192 TiB on Broadcom's estimate. When comparing VCF and VVF quotes, include add-on vSAN at the expected raw figure, because that line can outweigh a lower per-core price. These figures support a comparison and aren't legal or purchasing advice. Your order and the [licensing pages](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/licensing/licensing-overview/add-on-licenses-in-vcf-9-0.html) decide what you are entitled to.

## Pitfalls

- **Expecting deduplication to lower the count on hardware you already own.** VCF 9.x [validates vSAN add-on licenses against raw storage rather than logical data usage](https://knowledge.broadcom.com/external/article/411654/error-vsan-addon-license-assignment-fail.html), so enabling a feature changes nothing until the next purchase installs fewer drives.
- **Leaving no slack in a hand-built license file on 9.0.x.** A rounding gap of 1 TiB between reported raw and the entitlement [can grey out Assign](https://knowledge.broadcom.com/external/article/411654/error-vsan-addon-license-assignment-fail.html), and the fix runs through your Broadcom account team and a new license file, so check the reported raw figure before importing.
