<InShort>
William Lam's lab scripts are the reference here. The 9.1 version deploys **three nested ESX VMs**, initialises the **VCF Installer**, syncs from an **offline depot**, generates the deployment **JSON** and starts the **fleet deployment**, for either VCF or VVF. The nested part takes about 25 minutes. Configuration is a single environment file passed with `-EnvConfigFile`. Earlier scripts cover VCF 9.0, VVF 9.0, the 5.2 import workflow and 5.1, so you can build the starting point of an upgrade as easily as the target.
</InShort>

## Getting a first run right

1. **Read the repository README** for the current prerequisites: nested ESX appliance version, PowerCLI version, and the depot.
2. **Use the Nested ESX virtual appliance** for 9.1. It no longer ships with a default password, so set one during deployment.
3. **Prepare the offline depot** before the first run. See [an offline depot for your lab](/vcf/library/labs/offline-depot-in-a-lab/).
4. **Set PowerCLI to ignore invalid certificates** in the lab session, or the script can hang on the first connection.
5. **Create DNS records** for every name in your environment file, lowercase, forward and reverse.
6. **Keep one environment file per lab variant** under version control, without passwords.

## Ideas for using it

- **Upgrade rehearsals**: build the 5.2 lab with the import script, then run the real upgrade steps against it.
- **Customer mirrors**: copy the customer's naming and network shape into an environment file, using placeholder addresses.
- **Demo resets**: rebuild the morning of a workshop rather than nursing a lab that has drifted.

<Callout type="field">
Write down how long each phase takes on your hardware. When a customer asks how long a deployment window should be, a measured number from a rehearsal is worth far more than a guess.
</Callout>

## Pitfalls

- **Expecting every component on day one.** Log management, for example, is a Day-N deployment from VCF Operations.
- **Download token changes** between releases. Check the current depot authentication method for the version you're building.
- **Hard-coded names** in older versions of the script. Pull the latest before reporting a bug.
