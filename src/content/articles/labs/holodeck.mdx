<InShort>
Holodeck is a toolkit that deploys a **complete nested VCF** environment, including the management domain and workload domains, onto a single ESX host or a cluster with enough capacity. Each environment brings its own **DNS, NTP, BGP and DHCP** and needs only **one external IP**, so it avoids VLAN and routing conflicts with your network. Holodeck 9.0 supports both **VCF 5.2.x and 9.0**, which makes it useful for upgrade rehearsal. A typical 9.0 build with a four-node management domain and a three-node workload domain needs about **30 cores, 325 GB of memory and 1.1 TB of disk**. Binaries come from the support portal and need a VCF entitlement.
</InShort>

## Using it well

- **Training**: one environment per student, reset between sessions. Everyone sees the same names and addresses, which makes exercises easy to write.
- **Upgrade rehearsal**: deploy at 5.2.x, practise the move to 9.0, then repeat until the runbook is boring.
- **Day-2 practice**: adding clusters and hosts is covered in the Holodeck blog series, which mirrors the real vCenter-based workflow.
- **Break-fix**: snapshot, break something on purpose, and let the team diagnose. See [break-fix exercises](/vcf/library/labs/break-fix-exercises/).

## What to check first

- Host capacity for the layout you want, especially memory.
- The current Holodeck documentation for supported VCF versions. 9.1 support depends on the toolkit release you download.
- A download token or entitlement for the offline depot.

<Callout type="field">
For internal enablement, write the exercises against Holodeck's standard names. A session can then start with "everyone open the same vCenter at the same address".
</Callout>

## Pitfalls

- **Treating Holodeck performance as representative.** Nested environments are slower. Use it for workflows, not benchmarks.
- **Running it on a host that also runs your daily tools.** One build can take most of a large host.
- **Skipping the documentation** for version-specific steps. The toolkit changes with each release.
