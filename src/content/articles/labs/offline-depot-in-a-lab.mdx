<InShort>
An offline depot is a web server with a specific folder layout: **metadata** (the VCF manifest, product catalogue and compatibility data) at the root, and **binaries** under product folders. Get the layout from the metadata archive or the **VCF Download Tool** output and don't rearrange it (<KB id={421477} />). In a lab, plain **HTTP** is acceptable and avoids certificate trust work. With HTTPS, import the depot's certificate into the installer's trust store (<KB id={448839} />). Keep caching off on the web server, or the installer can read a stale manifest (<KB id={447589} />). In 9.1, authenticate downloads with the **depot activation code** (<KB id={443647} />).
</InShort>

## Layout rules

- **Metadata at the depot root**: manifest, product catalogue and compatibility files, unchanged from the tool or archive.
- **Binaries in their product folders**, as the metadata expects them.
- **Point the download tool's store at the root**, not a subfolder (<KB id={446454} />).
- **ESX images are UPGRADE type** in the download tool, not INSTALL (<KB id={442857} />).

## A minimal web server

```bash
# On a lab utility VM with the depot at /srv/vcf-depot
cd /srv/vcf-depot
python3 -m http.server 8080
# Then in the VCF Installer, set the offline depot URL to http://<utility-vm>:8080/
```

For anything longer-lived, use nginx or Caddy with caching disabled, and a basic auth user if the depot is shared.

<Callout type="field">
Keep one depot per major version and share it across every lab and every colleague on the team. Downloads become a one-time cost, and everyone tests against identical binaries.
</Callout>

## Pitfalls

- **A caching proxy** between the installer and the depot.
- **Mixing releases** in one tree without refreshing the metadata.
- **Pasting the licensing activation code** where the depot expects its own. See [two activation codes](/vcf/library/licensing/two-activation-codes/).
