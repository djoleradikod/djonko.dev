<InShort>
Lab hardware may not be on the compatibility guide, so VCF 9 can need help to run on it. The common adjustments fall into four groups: **CPU** (entropy and NVMe tiering behaviour on consumer AMD processors), **NICs** (hardware offloads on some consumer 10 GbE cards), **nested vSAN** (SCSI reservations, unmap pass-through, device monitoring and swap) and **vSAN compression** on CPU-constrained hosts. Each is an advanced setting with a documented reason. Use them in labs only, and keep a list so they never appear in a production build.
</InShort>

## The settings, by group

| Group | Setting | Why |
|---|---|---|
| vSAN compression | `/VSAN/Vsan2ZdomCompZstd = 0` | Uses LZ4 instead of Zstd on CPU-constrained hosts |
| Nested vSAN on physical vSAN | `/VSAN/FakeSCSIReservations = 1` | Required for nested vSAN on vSAN |
| Nested vSAN space | `/VSAN/GuestUnmap = 1` | Passes TRIM and UNMAP down to the physical vSAN |
| Nested vSAN tuning | `/LSOM/VSANDeviceMonitoring = 0`, `/LSOM/lsomSlowDeviceUnmount = 0`, `/VSAN/SwapThickProvisionDisabled = 1` | Device monitoring and swap suited to virtual disks. Not needed with the nested ESX appliance. |
| NVMe tiering for nested ESX | VM setting `sched.mem.enableNestedTiering = true` | Lets the physical host tier the nested VM's memory |
| Consumer NIC offloads | `/Net/TcpipDefLROEnabled = 0`, `/Net/UseHwTSO = 0` | Avoids performance loss on some 10 GbE cards |
| Consumer AMD CPUs | entropy source and APIC virtualisation settings | Avoids high CPU from slow entropy and VMs failing to start with NVMe tiering |

The full list, with the exact procedures for each processor family and the edge deployment workaround, is in the source article. Read it for your hardware rather than copying settings blind.

```bash
# Example: apply and verify one advanced setting on a lab host
esxcli system settings advanced set -o /VSAN/GuestUnmap -i 1
esxcli system settings advanced list -o /VSAN/GuestUnmap
```

<Callout type="field">
Keep lab-only settings in one script with a header that says "LAB ONLY", and never in a host profile or a configuration template shared with production. A lab kickstart copied into a production build would turn these settings into a support case.
</Callout>

## Pitfalls

- **Applying everything at once.** Apply only what your hardware needs, and note why.
- **Benchmarking a nested lab.** These settings make it work, not fast.
- **Carrying settings across releases.** Some are fixed or unnecessary in later builds. Re-check after each upgrade.
