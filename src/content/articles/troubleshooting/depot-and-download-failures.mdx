<InShort>
In 5.x and 9.0, SDDC Manager downloaded bundles with a download token. In 9.1, the **fleet depot** runs on the services runtime, authenticates with a **depot activation code** (<KB id={443647} />), and its traffic leaves from **runtime node addresses**. Allow outbound 443 from every runtime node to `eapi.broadcom.com`, `dl.broadcom.com`, `vvs.broadcom.com` and `vsanhealth.vmware.com`, as well as from SDDC Manager (<KB id={443166} />). Offline depots fail on structure and metadata: the manifest must be fresh and at the root, and the download tool's store must point at the root too.
</InShort>

## Online depot (9.1)

| Message | Cause and fix |
|---|---|
| "Depot returned authentication/authorization failure. Expected HTTP status 200 but received 403" | The allowlist covers SDDC Manager only. Allow all runtime nodes. The registered name must be lowercase (<KB id={443166} />). |
| "Failed to connect to Broadcom OAuth Authorization server", then "Bundle ... not found" | Egress to `eapi.broadcom.com` blocked. Read the depot service logs and curl from a node (<KB id={453116} />). |
| Depot "Disconnected" while VCF Operations on the same subnet connects | NSX hasn't pushed state for the runtime pods. Allowlist, then force an NSX resync (<KB id={447632} />). |
| VCF Operations 9.0 shows 9.1 but no binaries | Expected. Upgrade VCF Operations first (<KB id={440282} />). |

```bash
# From a runtime control-plane node
kubectl get pods -A | grep -iE 'depot|lcm|fleet'
kubectl logs -n vcf-fleet-depot <depot-service-pod> --all-containers --tail=200
curl -I -v https://eapi.broadcom.com
```

## 9.0 and earlier

- **403 from dl.broadcom.com**: a stale token or one for the wrong Site ID. Generate a new token, wait about ten minutes, update depot settings (<KB id={420374} />).
- **"handshake_failure(40)"** on the 9.0 fleet appliance: no path to `dl.broadcom.com` (<KB id={416358} />).

## Offline depots

| Problem | Fix |
|---|---|
| Installer can't connect to an HTTPS offline depot | It doesn't trust the depot's certificate. Import it into the installer trust store and reboot (<KB id={448839} />). |
| Stuck at "Initializing binary database" | A stale `vcfManifest.json` or cached metadata. Refresh the files and disable web caching (<KB id={447589} />). |
| 9.0 local depot not recognised | Metadata missing at the root, or binaries in the wrong folders (<KB id={421477} />). |
| Download tool UMDS sync fails | `--depot-store` points at a subfolder instead of the root (<KB id={446454} />). |
| Download tool lists zero ESX install binaries | ESX is published as UPGRADE, not INSTALL (<KB id={442857} />). |

<Callout type="field">
Put the depot path in the network design document as its own flow: source addresses (the runtime pool), destinations, ports, proxy and TLS inspection exemptions. A firewall request written for 5.x won't cover this flow.
</Callout>

## Pitfalls

- **TLS inspection** on the depot path. Exempt it.
- **Caching proxies** in front of an offline depot. They serve stale manifests.
- **Mixing up the two activation codes.** See [two activation codes](/vcf/library/licensing/two-activation-codes/).
