<InShort>
For a failed 9.1 fleet task, start on SDDC Manager in `/var/log/vmware/vcf/domainmanager/domainmanager.log`, copy the Fleet LCM task ID from the FAILED line, and search the SDDC build service console log for it. Broadcom's 9.1 examples show what reads as the same ID there, masked, beside a separate `taskId` and next to the call that failed. For other failed tasks, find the failed subtask, choose the file by service, search for the ID or exact message, and read to the last "Caused by". Treat that exception as a lead, because one message can have different causes and fixes.
</InShort>

<Callout type="note" title="Corrected on 7 November 2026">
This note used to say that a fleet build payload names the SDDC task, that only failed tasks retry and resume at the failed step, that logs are UTC, that `lcm-activity.log` is an upgrade log, and that each exception maps to one cause, including a `PKIX path building failed` string its cited KB doesn't contain. Those claims are removed or narrowed below, and the spec API is now scoped to 9.1 password retrieval.
</Callout>

## Task log or Workbench first

Broadcom's Troubleshooting Blueprint recommends [Workbench's "Potential Evidence" tab over scanning logs by hand](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/troubleshooting-guide/troubleshooting-methods.html), with log data coming in once the issue is narrowed to a component or timestamp.

<Callout type="analysis" title="Where this note departs from the blueprint">
The blueprint's [four scenarios](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/troubleshooting-guide/troubleshooting-scenarios.html) are workload performance, connectivity, intermittent problems and reboots, and none is a failed lifecycle task. A failed task already names a component and a time, so this site's call is to go straight to the logs for that case and follow the blueprint for an incident with no task ID.
</Callout>

Intermittent problems have to be isolated from historical data, so the blueprint's advice to [deploy Log Management before an incident, and set retention by how far back you may need to look](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/design/design-blueprints-for/infrastructure-modernization/troubleshooting-guide/environment.html), is a decision to make now. The [9.1.1 release notes](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/release-notes/vmware-cloud-foundation-9-1-1-0-release-notes.html) announce no logging or task ID change <AsOf date="2026-11-07" />.

## Which file

Broadcom's service-by-service map, <KB id={397253} />, is scoped to 5.2. Fleet task results and the installer's validation and deployment failures in the first row come from 9.1 sources, and the last column shows where 9.x sources confirm a path. On 9.x, use the "work" column as a starting point and move to the next file if your ID isn't there.

| Work | Log under `/var/log/vmware/vcf/` | 9.x evidence |
|---|---|---|
| Validation and deployment, domains, clusters, hosts, network, storage, fleet task results | `domainmanager/domainmanager.log` | [TechDocs 9.1](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/deploying-a-new-vmware-cloud-foundation-or-vmware-vsphere-foundation-private-cloud-/troubleshooting-vmware-cloud-foundation-or-vmware-vsphere-foundation-deployments.html), <KB id={446831} /> |
| Host commission, credentials, certificates, backups, DNS and NTP, licences | `operationsmanager/operationsmanager.log` | <KB id={423908} />, <KB id={420736} />, <KB id={456587} /> (9.1.1 backup) |
| Prechecks, bundles, downloads, upgrades, depot | `lcm/lcm-debug.log` and `lcm/lcm.log` | [TechDocs 9.1](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/log-files.html), <KB id={447589} /> |
| Identity, inventory, credential store, tasks and workflow, network pools | `commonsvcs/vcf-commonsvcs.log` | <KB id={427523} />, <KB id={450375} /> |
| Web UI and developer center | `sddc-manager-ui-app/sddcManagerServer.log` | None cited |
| SoS output, by default | `sddc-support/` | <KB id={385749} />, <KB id={402476} /> |

Search both `lcm` files on 9.x, because Broadcom's material disagrees. [TechDocs](https://techdocs.broadcom.com/us/en/vmware-cis/vcf/vcf-9-0-and-later/9-1/deployment/upgrading-cloud-foundation/log-files.html) says everything goes to `lcm-debug` once SDDC Manager is on 9.x, yet <KB id={390934} />, which lists 5.x and 9.1.0, still reads an `lcm.log` excerpt. Those files cover core components, and fleet upgrades log in the runtime.

A log can also send you onward. In a failed workload domain import, `domainmanager.log` points to a per-import `brownfield/` folder, and its `vcf_brownfield.log` points to `vcf-commonsvcs.log` (<KB id={427523} />). It can also point to the vCenter installer log for a vCenter deployment, or to the host's own `lifecycle.log` and `hostd.log`.

1. Find the failed task on SDDC Manager. <KB id={446831} /> shows the line this catches, and `PUBLIC_FLEET_LCM_TASK_FAILED` marks the same failure:

   ```bash
   grep "Fleet LCM Task ID:" /var/log/vmware/vcf/domainmanager/domainmanager* | grep FAILED
   ```

   Note the failed step and component type.

2. Get the SDDC build service console log. Either read it from the runtime with the [services runtime kubectl commands](/vcf/library/troubleshooting/services-runtime-kubectl/), or collect `sos --sddc-manager-logs --vcf-mgmt-svcs-logs --zip` on 9.1 (<KB id={385749} />). In the bundle, the file is under `vcf-sddc-lcm/` and ends `sddcbuild/console-log-####.log` (<KB id={439240} />, <KB id={446831} />).
3. Search it for the ID, then read the lines around each hit. <KB id={439240} /> prints `[<BUILD_TASK_ID>, taskId=####-####-####-####]` beside the failure and uses the same placeholder in `domainmanager.log`. Broadcom masks the values, so reading them as one ID is an inference from that placeholder. Some neighbouring lines carry no ID at all (<KB id={446095} />), so a bare grep can hide the step that failed.
4. If the SDDC build log has nothing, look in the fleet build service's `vcf-fleet-lcm` pod log. <KB id={444075} /> puts one defect there: `domainmanager.log` shows `All 3 retry attempts failed for getSystemInfo API call`, while the stated cause is a null component version from Fleet Build Service, rejected with an HTTP 400 by the SDDC-LCM build service. These KBs quote no fleet build log line with the task ID, so attach those logs to the case if the ID doesn't appear in them.

A task that is stuck rather than failed may leave no FAILED line. Run the `lcm_service_support.sh` script from <KB id={435569} /> with `-t` and the task ID, and it reports whether the task is making progress.

## Reading the trace

Search for the ID, the reference token or the exact message, because a word like "error" matches too much:

```bash
grep -Ri "<reference-token>" /var/log/vmware/vcf/ | head
grep -n -B 20 -A 60 "<reference-token>" /var/log/vmware/vcf/domainmanager/domainmanager.log | less
```

Reading to the last "Caused by" is this site's advice, because wrappers repeat the same failure. The rows below are public examples and each holds only within its KB's scope, so check that scope before applying the fix.

| Log line | Log | What Broadcom found | Scope |
|---|---|---|---|
| `ConnectException: Connection refused` under `Error occurred while getting certificate chain` | `sddcbuild` console | Installer FQDN mapped to 127.0.0.1 in `/etc/hosts` | <KB id={446095} />, 9.1 |
| `ConnectException: Connection timed out` under the same message | `sddcbuild` console | No TCP path from runtime pods to VCF Operations | <KB id={446831} />, 9.1.0.0100 |
| `UnknownHostException` | `operationsmanager` | Wrong DNS for the NSX Manager FQDN, in host commission | <KB id={423908} />, 9.x |
| `SocketException: No route to host` | `domainmanager` | Failed uplink assignment cut off the management vCenter, when MANAGEMENT and VM_MANAGEMENT networks differ | <KB id={415550} />, 9.x |
| HTTP 403 with `the account specified has been locked` | `operationsmanager` | SDDC Manager's failed logins locked the NSX service account | <KB id={420736} />, 9.0 |
| `vim.fault.InvalidLogin` | `sddc-build-service` | Stale SDDC-LCM credentials after rotation or an out-of-band password change | <KB id={450375} />, VCF and VVF |
| `PKIXParameters failed`, `SDDC_TRUST_HOST_SSL_CERT_FAILED` | `operationsmanager` | New host on a default certificate where the management domain expects external ones | <KB id={415767} />, 5.2.x and 9.x |
| `Matching VCF release ... not found` | `lcm-debug` | Stale or partial `vcfManifest.json` on an offline depot | <KB id={447589} />, 9.x |

The first two rows are why the scope matters. Both messages read like a certificate problem, the fixes are an `/etc/hosts` edit and a firewall change, and neither touches a certificate. Put the last "Caused by" in the ticket next to the UI message, because `UnknownHostException` for the NSX Manager FQDN tells the next engineer where to start and "deploy failed" doesn't. If the case goes to Broadcom on 9.1, VCF Operations can [send support bundles from its console through Log Assist](https://www.vmware.com/docs/vmware-cloud-foundation-9-1-general-faqs).

## Times and retries

Check each log's offset before you line it up with a time from the UI. `lcm.log` excerpts carry `+0000` and vCenter's `applmgmt.log` lines say UTC (<KB id={390934} />), and SDDC build console lines end in `Z` (<KB id={446095} />). Those excerpts don't cover every log, so read the offset on the file you have open.

Broadcom's public documentation doesn't say where a manual fleet retry restarts <AsOf date="2026-11-07" />. The installer's automatic pass skips components already provisioned (<KB id={435569} />), but that KB doesn't extend it to a manual retry, so see what the failed step already changed before retrying. Some failures need more than the button: <KB id={446095} /> and <KB id={443128} /> add `fleetlcm.task.id.to.recreate` to the domainmanager properties and restart the service, so use that only under the KB that matches your symptom. The [triage note](/vcf/library/troubleshooting/seven-step-triage/) covers the retry decision.

## Recovering a deployment spec

The spec is findable on every release here, but the 9.1 route exposes passwords. On 5.x, search `domainmanager.log`. On 9.0.x, <KB id={414456} /> searches the installer log for `Create SDDC with the following spec`. On 9.1, <KB id={388719} /> calls `/v1/sddcs/<ID>/spec`, and the VCF Operations deployment JSON it returns contains the auto-generated passwords, so keep that output out of tickets.
