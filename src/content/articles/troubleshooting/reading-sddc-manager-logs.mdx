<InShort>
On SDDC Manager, everything is under `/var/log/vmware/vcf/`. **domainmanager** handles bring-up, domains, clusters and hosts, and in 9.x records fleet lifecycle task results. **operationsmanager** handles commissioning, passwords, certificates and backups. **lcm** handles prechecks, bundles and upgrades. **commonsvcs** handles tokens, SSH keys, inventory and the API. Find the failed subtask, open the right file, search for the ID, and read the **last "Caused by"** in the stack trace. In 9.1, a fleet task ID is not the same as the SDDC lifecycle task ID it triggered, so follow the trail rather than searching for one ID everywhere.
</InShort>

## Which file

| Subtask type | Log under /var/log/vmware/vcf/ |
|---|---|
| Bring-up, domains, clusters, add host, NSX or vCenter deploy, inventory sync | `domainmanager/domainmanager.log` |
| Host commission, passwords, certificates, backups | `operationsmanager/operationsmanager.log` |
| Prechecks, bundles, upgrades, depot | `lcm/lcm-debug.log` and `lcm/lcm-activity.log` |
| Tokens, SSH host keys, credential API, inventory | `commonsvcs/vcf-commonsvcs.log` |
| SoS output | `sddc-support/` |

`domainmanager.log` often points onward: to the vCenter installer log for a vCenter deployment, to a brownfield folder for an inventory sync, or to the host's own `lifecycle.log` and `hostd.log`.

## How to read a stack trace

```bash
# Find the reference token or task ID, with context
grep -Ri "<reference-token>" /var/log/vmware/vcf/ | head
grep -n -B 20 -A 60 "<reference-token>" /var/log/vmware/vcf/domainmanager/domainmanager.log | less
```

Look for the exception class, then scroll to the **last "Caused by"**. It points to the actionable cause:

| Last cause | Points to |
|---|---|
| `UnknownHostException` | DNS (<KB id={423908} />) |
| `SocketException: No route to host` | Network path or uplinks (<KB id={415550} />) |
| `InvalidLogin`, 403, `locked` | Credentials or account lockout (<KB id={420736} />) |
| `PKIX path building failed` | Certificate trust (<KB id={415767} />) |
| `Matching VCF release ... not found` in lcm-debug | Depot metadata or manifest (<KB id={447589} />) |

1. On SDDC Manager, find the fleet task result: `grep "Fleet LCM Task ID:" domainmanager* | grep FAILED`. Note the failed step and component type.
2. In the fleet build service pod log, search for that task ID. The payload names the SDDC lifecycle task it started.
3. In the SDDC build service pod log, search for that second ID or the step name. The call that failed, such as a "No route to host", is there.

The kubectl commands are in [services runtime and kubectl](/vcf/library/troubleshooting/services-runtime-kubectl/). Only failed tasks retry, and retries resume at the failed step.

<Callout type="field">
Paste the last "Caused by" line into the ticket summary, next to the UI message. "Deploy failed" tells the next engineer nothing. "UnknownHostException for nsx01b" tells them where to start.
</Callout>

## Pitfalls

- **Searching every log for a generic word** like "error". Search for the ID or the exact message.
- **Mixing time zones.** Logs are UTC. The UI shows local time.
- **Reading only the first exception.** Wrappers repeat the same failure several times. The cause is at the bottom.
