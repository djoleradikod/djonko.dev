<InShort>
**Start with disk on the analytics nodes, the cluster's state, and DNS from the cloud proxies.** A full `/storage/db` stops analytics, and the fix is to add a new disk to every analytics node rather than expand an existing one (<KB id={318768} />, <KB id={454593} />). A full root partition is a separate case (<KB id={410759} />). A cluster stuck at "Waiting for Analytics" is recovered by taking it offline in the admin UI, restarting each node in turn from vCenter, then bringing it online (<KB id={446447} />). Cloud proxies going offline every few hours, or 503s through haproxy, point to name resolution (<KB id={426042} />, <KB id={443900} />). Before reverting VCF Operations to a snapshot, check the set was taken offline and includes the cloud proxies. [The rollback note](/vcf/library/upgrades/rollback-checkpoints/) separates the documented revert after a failed upgrade from other cases (<KB id={402329} />, <KB id={436047} />).
</InShort>

<Callout type="note" title="Corrected on 6 November 2026">
This note said never to revert VCF Operations to a snapshot, citing KB 436047. That KB reports one environment and contains no such rule, and other Broadcom KBs tell you to revert after specific upgrade failures.
</Callout>

## Analytics nodes

| Symptom | Cause and fix |
|---|---|
| Cluster stuck "Waiting for Analytics" | Root partition full, for example from an outbound plugin writing to a temp folder (<KB id={410759} />). Or inter-node communication or GemFire heartbeat failures: snapshot, take offline (force only if that fails), restart nodes one by one, bring online (<KB id={446447} />). |
| "data retrieve is not initialized yet" | `/storage/db` low. Take the cluster offline, add a new disk to every analytics node so all keep the same capacity, bring it online (<KB id={318768} />). |
| PAK upload fails with "ensure there is an active connection" | Out of disk during staging (<KB id={454593} />). |
| "Service or view is not available" on Build > Lifecycle after 9.1 upgrade | A duplicate thumbprint in Trusted Certificates (<KB id={448522} />). |

```bash
# On each analytics node
df -h / /storage/db /storage/log
```

## Cloud proxies

| Symptom | Cause and fix |
|---|---|
| Proxy offline every 4 to 8 hours | haproxy can't resolve the VCF Operations node names. Run `nslookup` for each node from the proxy (<KB id={426042} />). |
| Periodic 503s, `NOSRV` in haproxy logs | haproxy's built-in resolver fails to resolve or refresh backend hostnames. Apply the KB, and recheck after a 9.0 to 9.1 upgrade, because the config can revert (<KB id={443900} />). |
| SSO page won't load, proxy shows "Outdated life status" | haproxy hung, DNS, or a certificate chain mismatch with the primary (<KB id={437258} />). |
| "Disk space on cloud proxy is low" with a huge catalina log | A corrupt or empty health status file (<KB id={443018} />). |
| "VCF Operations lost connection to SDDC Manager" | An expired token on the diagnostics adapter. Recreate it (<KB id={440916} />). |

<Callout type="analysis">
This site's advice is to treat VCF Operations like vCenter now, with image-level backups, disk monitoring and a change window for upgrades, because in 9.x it holds licensing and lifecycle for the whole fleet.
</Callout>

## Pitfalls

- **Expanding an existing VMDK** on analytics nodes. Add a new disk, identically sized, to all of them.
- **Reverting without the cloud proxies.** One public report describes a vCenter adapter duplicating thousands of times after a revert in an environment whose proxies had no backups or snapshots. Broadcom didn't determine the exact cause (<KB id={436047} />).
- **Testing DNS from your laptop.** Test from the proxy, against every node.
