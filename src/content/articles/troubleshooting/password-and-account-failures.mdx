<InShort>
Five patterns explain most password and account failures. **Lockout**: an NSX service account locked by repeated bad logins (<KB id={420736} />). **Re-lock**: services keep using a stale credential and lock the account again after you unlock it (<KB id={449684} />). **Expiry**: NSX `admin` expired, so SDDC Manager can't call the API (<KB id={438020} />). **Drift**: someone changed a password outside SDDC Manager, so the stored value is wrong (<KB id={436398} />). **Stale secrets** (9.1): a rotation changed a service account that the services runtime still holds in a Kubernetes secret (<KB id={450375} />). Each has a known fix, and none of them is "reset everything".
</InShort>

## 1. Lockout

**Symptom:** `The credentials were incorrect or the account specified has been locked`, a 403 in `operationsmanager.log`, and host commission or cluster creation failing at validation.

**Fix:** temporarily add SDDC Manager's IP to the NSX lockout-immune addresses, retry the rotation, then remove it (<KB id={420736} />, <KB id={449684} />).

## 2. Re-lock

**Symptom:** `Failure occurred in TEST_BEFORE_REMEDIATE stage`, and the account locks again within minutes.

**Fix:** with lockout immunity in place, rotate the service account, wait 5 to 10 minutes, verify the stored value (<KB id={327195} />), then rotate root, admin and audit (<KB id={449684} />).

## 3. Expiry

**Symptom:** NSX managers show disconnected and admin or audit rotation fails.

**Fix:** on the NSX node, reset `admin` as the KB describes, signal a cluster credential reset, then **Remediate** in SDDC Manager with the new value (<KB id={438020} />).

## 4. Drift

**Symptom:** ESX root shows **Disconnected** in password management, and `sos --health-check` reports "Failed to get details".

**Fix:** **Remediate** with the password that currently works on the host. Check what SDDC Manager holds with `lookup_passwords` (<KB id={436398} />). If a lock is also involved, follow <KB id={449686} />.

## 5. Stale secrets (9.1)

**Symptom:** `Step vmsp_upgrade failed`, `Failed to obtain SDDC Manager token`, `InvalidLogin`, `PERMISSION_NOT_FOUND` or `CLIENT_IP_BLOCKED`.

**Fix:** run the KB's re-establish scripts on a runtime control-plane node to update the secrets, restart the two SDDC lifecycle deployments, then restart `commonsvcs` on SDDC Manager (<KB id={450375} />). A precheck reporting the vCenter service account "not found" after a remediation has its own KB (<KB id={449131} />).

<Callout type="field">
Most of these tickets start with someone fixing a password by hand on the component. Make "change it through VCF, or remediate straight afterwards" a written rule for every team with root access. It is the cheapest control in this whole category.
</Callout>

## Pitfalls

- **Retrying a password task through the generic tasks API.** It isn't supported. Cancel it and start a new operation (<KB id={444986} />).
- **Unlocking without fixing the source.** If a service still has the old value, it locks the account again.
- **Assuming service accounts expire at 30 days.** They are rotated by default every 30 days. Rotation, not expiry, is what strands a stale secret.
